# Почему фреймворки с компиляцией на этапе компиляции неожиданно хорошо работают с нейро-агентами кодирования { #compile-time-frameworks-ai-agents }

**14 сентября 2026**

Об нейро-агентах кодирования часто говорят так, будто выбор фреймворка почти не имеет значения.

Дай агенту репозиторий, компилятор, несколько тестов и достаточно контекста — и он в конце концов разберётся, как устроено приложение.

На практике архитектура фреймворка имеет огромное значение.

Агент кодирования понимает кодовую базу не так, как старший инженер после шести месяцев работы в команде. Он действует через многократную реконструкцию. Он читает файлы, выводит соглашения, изменяет
код, вызывает инструменты, интерпретирует ошибки и обновляет свою модель системы. Качество этого цикла сильно зависит от того, насколько архитектура приложения видна в исходном коде и насколько быстро
неверные предположения превращаются в машиночитаемую обратную связь.

Именно здесь фреймворки с компиляцией на этапе компиляции становятся необычно интересными.

Архитектура Kora создаёт цикл, который выглядит почти идеальным для автономного агента кодирования:

```text
Агент пишет код
      ↓
компилятор проверяет
      ↓
сгенерированный код раскрывает поведение
      ↓
тесты запускаются быстро
      ↓
агент наблюдает результат
      ↓
агент исправляет
```

Важно не то, что LLM «понимает Kora» лучше, потому что Kora была спроектирована для нейро-технологий.

Более глубокая мысль в том, что несколько свойств, которые делают фреймворк приятным для опытных инженеров, оказываются ровно теми свойствами, которые снижают неопределённость для программного агента:

```text
явная архитектура
строгие типы
сгенерированный исходный код
точная обратная связь компилятора
один рекомендуемый способ
тонкие абстракции
быстрый запуск
быстрые компонентные тесты
```

Эти свойства превращают скрытое поведение фреймворка в проверяемые свидетельства.

Это меняет экономику агентной разработки.

Вместо того чтобы просить модель запоминать малопонятные правила выполнения, реконструировать скрытое состояние контейнера или угадывать, какая из нескольких моделей программирования активна,
фреймворк позволяет модели использовать инструменты, в которых она уже сильна:

```text
читать исходный код
следовать за типами
компилировать
изучать ошибку
изучать сгенерированный код
запускать тест
редактировать
повторять
```

В этой статье объясняется, почему это важно, откуда берётся преимущество, где оно заканчивается и почему фреймворки с компиляцией на этапе компиляции, такие как Kora, могут быть необычно хорошо
подобраны под следующее поколение инструментов кодирования.

## Агенты кодирования работают через циклы обратной связи { #feedback-loops }

Простейшая полезная модель автономного агента кодирования — это не:

```text
промпт
  ↓
идеальный код
```

А вот это:

```text
гипотеза
  ↓
правка
  ↓
обратная связь от инструмента
  ↓
уточнённая гипотеза
  ↓
снова правка
```

Сильному агенту редко нужно быть правильным с первой попытки.

Ему нужно быстро стать правильным.

Это различие критично.

Предположим, агент добавляет новый сервисный компонент. Он может изначально угадать конструктор неправильно. Может пропустить зависимость. Может неверно понять тип возвращаемого значения репозитория.
Может выбрать не ту аннотацию. Может предположить, что HTTP-эндпоинт асинхронный, тогда как фреймворк ожидает синхронную сигнатуру.

Если система немедленно возвращает точную ошибку, ошибка обходится дёшево.

Если ошибка переживает компиляцию и проявляется только после запуска приложения, удалённого вызова или конкретного пути выполнения, цикл исправления становится медленнее и менее детерминированным.

Поэтому продуктивность агента сильно связана с **задержкой обратной связи** и **качеством обратной связи**.

Компиляционная модель Kora выталкивает многие ошибки фреймворка в фазу, где обратная связь одновременно ранняя и структурированная.

## Компилятор — это внешняя система рассуждений { #compiler-external-reasoning }

Для человека-разработчика компилятор — это инструмент.

Для нейро-агента кодирования это также форма внешней инфраструктуры рассуждений.

Модель может не знать, верно ли её предположение, но компилятор часто знает.

Рассмотрим простую ошибку:

===! ":fontawesome-brands-java: `Java`"

    ```java
    @Component
    public final class OrderService {

        private final OrderRepository repository;

        public OrderService(
            OrderRepository repository,
            InventoryClient inventory
        ) {
            this.repository = repository;
        }
    }
    ```

=== ":simple-kotlin: `Kotlin`"

    ```kotlin
    @Component
    class OrderService(
        repository: OrderRepository,
        inventory: InventoryClient
    ) {

        private val repository: OrderRepository = repository
    }
    ```

Человек может сразу заметить, что `inventory` не используется или что поле отсутствует.

Агент может это упустить.

Компилятор Java, статический анализ или компиляция сгенерированного графа дают объективную обратную связь.

Тот же принцип действует на уровне фреймворка.

Если граф приложения компилируется, а не собирается динамически, отсутствующие зависимости становятся проблемами компилятора, а не проблемами контейнера во время выполнения.

Это значит, что компилятор проверяет не только синтаксис и типы Java.

Он проверяет архитектуру приложения.

Для агента это чрезвычайно ценно.

## Внедрение зависимостей на этапе компиляции превращает архитектуру во входные данные компилятора { #compile-time-di }

Внедрение зависимостей часто оказывается одной из самых трудных частей фреймворка для реконструкции агентом.

В контейнере, ориентированном на выполнение, фактический граф может зависеть от:

```text
сканирования classpath
аннотаций
условной конфигурации
профилей
рефлексии
создания прокси
постобработки бинов во время выполнения
автоконфигурации
правил порядка
```

Исходный код может показывать множество частей, не показывая итоговую композицию.

Опытный пользователь фреймворка может мысленно реконструировать этот механизм.

LLM приходится выводить его из контекста репозитория, документации и знаний о фреймворке.

Граф Kora гораздо более явный.

Структура приложения объявляется через такие конструкции, как:

```text
@KoraApp
@Component
@Module
конструкторы
интерфейсы
фабрики модулей
```

и граф проверяется во время компиляции.

Это даёт агенту два сильных источника информации:

```text
объявления в исходном коде
диагностика компилятора
```

Архитектура приложения становится больше похожа на обычную типизированную структуру программы и меньше — на состояние контейнера во время выполнения.

## Явные конструкторы — отличный контекст для агента { #explicit-constructors }

Рассмотрим:

===! ":fontawesome-brands-java: `Java`"

    ```java
    @Component
    public final class PaymentService {

        private final PaymentRepository repository;
        private final FraudClient fraudClient;

        public PaymentService(
            PaymentRepository repository,
            FraudClient fraudClient
        ) {
            this.repository = repository;
            this.fraudClient = fraudClient;
        }
    }
    ```

=== ":simple-kotlin: `Kotlin`"

    ```kotlin
    @Component
    class PaymentService(
        private val repository: PaymentRepository,
        private val fraudClient: FraudClient
    )
    ```

Структура зависимостей очевидна.

Агент может вывести:

```text
PaymentService
  ├── PaymentRepository
  └── FraudClient
```

не опрашивая контейнер.

Это не уникальное свойство Kora; внедрение через конструктор доступно повсеместно.

Важно то, что Kora держит модель фреймворка близко к этой явной структуре, а не окружает её большим объёмом интерпретации во время выполнения.

Чем меньше архитектуры агенту приходится выводить косвенно, тем надёжнее становятся его изменения.

## Ошибки графа на этапе компиляции лучше, чем загадки при запуске { #graph-errors }

Представьте, что агент добавляет:

===! ":fontawesome-brands-java: `Java`"

    ```java
    public FraudAnalyzer fraudAnalyzer(
        FraudClient client,
        RiskModel model
    ) {
        return new FraudAnalyzer(client, model);
    }
    ```

=== ":simple-kotlin: `Kotlin`"

    ```kotlin
    fun fraudAnalyzer(
        client: FraudClient,
        model: RiskModel
    ): FraudAnalyzer {
        return FraudAnalyzer(client, model)
    }
    ```

но в приложении нет `RiskModel`.

В графе, собираемом на этапе компиляции, сборка может завершиться ошибкой разрешения зависимости.

Это идеальная обратная связь для агента.

Цикл становится таким:

```text
агент добавляет компонент
  ↓
компиляция
  ↓
нет RiskModel
  ↓
агент ищет поставщика RiskModel
  ↓
добавляет или подключает поставщика
  ↓
снова компиляция
```

Не нужно:

```text
упаковывать приложение
запускать JVM
инициализировать фреймворк
ждать контейнер
читать исключение при запуске
реконструировать состояние выполнения
```

Чем меньше несвязанных шагов между ошибкой и обратной связью, тем проще задача и для людей, и для агентов.

## Локализация ошибок имеет значение { #error-locality }

Ошибка компилятора наиболее полезна, когда она указывает близко к неверному предположению.

Для агентов это особенно важно.

Сбой вида:

```text
Для FraudAnalyzer недоступен компонент типа RiskModel
```

создаёт узкое пространство поиска.

Сбой во время выполнения вида:

```text
Не удалось инициализировать ApplicationContext
вызвано BeanCreationException
вызвано ProxyFactory...
```

может быть вполне диагностируемым, но агенту приходится пройти через больше слоёв, специфичных для фреймворка, прежде чем добраться до реальной проблемы.

Системы с компиляцией на этапе компиляции, как правило, улучшают **локализацию ошибок**, потому что фреймворк проверяет структуру на уровне исходного кода, пока у него ещё есть прямой доступ к
объявлениям, которые её создали.

## Строгие типы сужают пространство возможных интерпретаций { #strong-types }

LLM работают лучше всего, когда среда ограничивает ответ.

Слабо типизированный API даёт модели много способов ошибиться.

Строго типизированный API убирает большую часть этого пространства поиска.

Предположим, HTTP-клиент возвращает:

===! ":fontawesome-brands-java: `Java`"

    ```java
    HttpResponse<OrderDto>
    ```

=== ":simple-kotlin: `Kotlin`"

    ```kotlin
    HttpResponse<OrderDto>
    ```

а не:

===! ":fontawesome-brands-java: `Java`"

    ```java
    Object
    ```

=== ":simple-kotlin: `Kotlin`"

    ```kotlin
    Any
    ```

или:

```text
Map<String, Object>
```

Теперь агент знает:

```text
какой тип существует
какие методы доступны
какой маппинг ожидается
какие ошибки компилятора появятся при неверной догадке
```

Строгая типизация превращает неопределённость в проверяемые контракты.

Kora распространяет этот принцип на внутренние и внешние границы.

## Сквозная типизация ценнее локальной { #end-to-end-typing }

Java и Kotlin уже дают сильную локальную типизацию.

Преимущество фреймворка проявляется, когда эти типы переживают границы фреймворка.

Например:

```text
HTTP-запрос
  ↓
типизированный DTO запроса
  ↓
типизированный метод сервиса
  ↓
типизированный результат репозитория
  ↓
типизированный HTTP-клиент
  ↓
типизированный ответ
```

Если задействована генерация по OpenAPI, внешний API может участвовать в той же типизированной цепочке.

Агенту не приходится выводить JSON-структуры из написанных вручную карт или магических строк-ключей.

Неверные предположения с большей вероятностью провалятся во время компиляции.

Это ровно то, что нужно автономному циклу.

## Строгие типы превращают галлюцинации в ошибки компилятора { #hallucination-compiler-errors }

LLM может галлюцинировать метод:

===! ":fontawesome-brands-java: `Java`"

    ```java
    repository.findAllActiveUsers();
    ```

=== ":simple-kotlin: `Kotlin`"

    ```kotlin
    repository.findAllActiveUsers()
    ```

когда реальный метод:

===! ":fontawesome-brands-java: `Java`"

    ```java
    repository.findActive();
    ```

=== ":simple-kotlin: `Kotlin`"

    ```kotlin
    repository.findActive()
    ```

В динамической среде такая ошибка может жить дольше.

В Java/Kotlin она проваливается немедленно.

Что ещё интереснее, агент может галлюцинировать контракт фреймворка:

===! ":fontawesome-brands-java: `Java`"

    ```java
    @SomeKoraAnnotation
    ```

=== ":simple-kotlin: `Kotlin`"

    ```kotlin
    @SomeKoraAnnotation
    ```

или вернуть неверный тип ответа.

Если сам фреймворк проверяется на этапе компиляции, больше таких галлюцинаций на уровне фреймворка становятся ошибками сборки, а не сюрпризами во время выполнения.

Фреймворк фактически преобразует неопределённость модели в структурированные сигналы исправления.

## Сгенерированный исходный код — необычно мощный интерфейс для нейро-технологий { #generated-source-ai-interface }

Одно из самых отличительных свойств Kora — то, что поведение фреймворка часто становится сгенерированным исходным кодом Java или Kotlin.

Это огромное значение имеет для агентов кодирования.

LLM по своей природе сильна в чтении исходного кода.

Она гораздо слабее, когда её просят вывести невидимое состояние выполнения.

Рассмотрим внедрение зависимостей.

Фреймворк, ориентированный на выполнение, может внутренне создавать прокси, разрешать метаданные и строить состояние контейнера, которого не существует как обычного исходного кода.

Kora может генерировать код связывания.

Рассмотрим репозитории.

Kora может генерировать реализации репозиториев.

Рассмотрим HTTP.

Kora может генерировать обработчики и клиенты.

Рассмотрим AOP.

Kora генерирует обёртки/подклассы.

Сгенерированный исходный код даёт агенту нечто конкретное для изучения.

## Сгенерированный код выносит контекст фреймворка наружу { #generated-code-context }

Люди-разработчики часто носят знания о фреймворке в голове.

Они знают:

```text
эта аннотация подразумевает прокси
этот метод репозитория становится подготовленным запросом
этот обработчик оборачивается промежуточным ПО
этот бин выбран, потому что совпало условие
```

У нейросетевой модели нет постоянного, безупречного внутреннего знания о каждом специфичном для проекта правиле фреймворка.

Сгенерированный исходный код выносит этот контекст наружу.

Вместо запоминания:

```text
что Kora, вероятно, здесь генерирует?
```

агент может прочитать:

```text
что Kora здесь фактически сгенерировала
```

Это глубочайшее различие.

Оно снижает зависимость от памяти модели и повышает зависимость от свидетельств в репозитории.

## Сгенерированный исходный код сужает поверхность угадывания { #shrinks-guessing-surface }

Представьте, что агент отлаживает проблему с повторами.

Он видит:

===! ":fontawesome-brands-java: `Java`"

    ```java
    @Retry("payments")
    public Payment load(String id) {
        return client.load(id);
    }
    ```

=== ":simple-kotlin: `Kotlin`"

    ```kotlin
    @Retry("payments")
    open fun load(id: String): Payment {
        return client.load(id)
    }
    ```

Без сгенерированного исходного кода агент должен знать:

```text
как реализован повтор
как работает порядок аспектов
как ведёт себя самовызов
какая стратегия прокси активна во время выполнения
```

Со сгенерированным исходным кодом он может изучить обёртку и увидеть фактическую структуру вызова.

Проблема превращается из археологии фреймворка в обычный анализ программы.

Это ровно тот тип задачи, с которым LLM справляются хорошо.

## Сгенерированный код — это специфичная для приложения документация { #application-specific-docs }

Общая документация говорит:

```text
Репозитории Kora генерируются.
```

Сгенерированный исходный код говорит:

```text
этот репозиторий
с этим SQL
отображает эти параметры
в этот конкретный код
```

Общая документация говорит:

```text
AOP генерируется на этапе компиляции.
```

Сгенерированный исходный код говорит:

```text
этот конкретный метод
обёрнут в этом конкретном порядке
с использованием этих конкретных зависимостей
```

Сгенерированный результат — это больше, чем артефакт реализации.

Для агента это **контекстная документация, синтезированная под текущее приложение**.

Это чрезвычайно ценно.

## Агенты могут следовать по реальным путям выполнения { #real-execution-paths }

Предположим, задача такая:

> Почему `GET /orders/{id}` возвращает 500, когда сервис платежей истекает по таймауту?

В прозрачной кодовой базе агент может проследить:

```text
HTTP-обработчик
  ↓
контроллер
  ↓
сервис
  ↓
сгенерированная обёртка повтора/таймаута
  ↓
HTTP-клиент
  ↓
маппинг ответа
```

Путь существует как читаемый код или легко прослеживаемые типизированные вызовы.

Модели не нужно реконструировать скрытую перехватку во время выполнения.

Это повышает уверенность в объяснениях и изменениях кода.

## «Никакой магии во время выполнения» — это на самом деле про уменьшение скрытого состояния { #no-runtime-magic }

Фраза «никакой магии» может звучать риторически.

Более точный инженерный смысл:

```text
меньше важного поведения существует только в метаданных времени выполнения
```

Kora по-прежнему выполняет сложную автоматизацию.

Процессоры аннотаций генерируют код.

Компилятор DI разрешает графы.

Генераторы OpenAPI создают типы.

Процессоры AOP строят обёртки.

Это всё ещё метапрограммирование.

Разница в том, что большая часть результата становится явным кодом до выполнения.

Для нейро-инструментов видимая автоматизация рассуждается гораздо легче, чем невидимая.

## Нейро-агенты слабы в фольклоре фреймворков { #framework-folklore }

Старший инженер может знать десятки неписаных правил:

```text
эта аннотация не работает при самовызове
этот профиль включает другой бин
этот прокси основан на интерфейсе, если только...
у имени этого метода репозитория есть особые правила разбора
этот перехватчик выполняется раньше того
эта конфигурация молча заменяет выбор по умолчанию
```

LLM может знать часть этих правил из обучающих данных.

Проблема в версионировании.

Какая версия фреймворка?

Какая модель программирования?

Какое соглашение проекта?

Какое исключение применимо здесь?

Чем больше поведение зависит от фольклора, тем выше шанс, что модель применит не то правило.

Kora намеренно уменьшает объём такого фольклора.

Это ценно для агентов по той же причине, по которой ценно для людей.

## Один рекомендуемый способ сужает пространство поиска { #one-recommended-way }

Гибкость фреймворка привлекательна для людей, потому что эксперты могут выбирать среди нескольких допустимых подходов.

Для автономного агента каждый дополнительный допустимый подход увеличивает пространство поиска.

Предположим, фреймворк поддерживает несколько способов доступа к данным:

```text
ORM
JDBC-шаблон
реактивный репозиторий
query DSL
active record
репозиторий, выводимый из аннотаций
пользовательский DAO
```

Теперь агенту нужно ответить:

```text
Какой из них предпочитает этот проект?
Какие API относятся к какой версии?
Можно ли смешивать эти стили?
Какие соглашения локальные?
```

Фреймворк с одним рекомендуемым путём сокращает эти решения.

Kora явно предпочитает меньший набор прямых подходов.

Для агентов это не просто эстетическая простота.

Это сокращение ветвления в пространстве решений.

## Меньше допустимых решений может дать лучше автономную работу { #fewer-valid-solutions }

Люди часто ценят выразительную свободу.

Агенты часто выигрывают от ограниченных сред.

Если есть одна идиоматическая модель репозитория, агент с большей вероятностью выберет правильную.

Если синхронные методы плюс виртуальные потоки — стандартная модель конкурентности, агент с меньшей вероятностью некорректно смешает реактивные и блокирующие API.

Если конфигурация следует одному типизированному шаблону, меньше несовместимых подходов можно изобрести.

Если AOP генерируется через один механизм, агенту не нужно определять, какая система прокси активна.

Более узкий фреймворк может быть более сильной средой для агента.

## Один способ также улучшает поиск { #one-way-retrieval }

Когда агент ищет примеры в репозитории, важна согласованность.

Предположим, каждый HTTP-контроллер использует один и тот же стиль Kora.

Поиск возвращает несколько примеров, которые подкрепляют один шаблон.

Модель может уверенно им подражать.

Если пять команд используют пять разных парадигм, поиск даёт противоречивые примеры.

Теперь модели приходится выводить, какой стиль актуален, а какой устарел.

Поэтому согласованность — это не только свойство поддерживаемости для людей.

Она улучшает машинные рассуждения на основе примеров.

## Тонкие абстракции сохраняют предобученные знания { #thin-abstractions }

LLM уже много знают о:

```text
Java
Kotlin
JDBC
HTTP
Kafka
gRPC
SQL
OpenTelemetry
```

Слой абстракций, специфичный для фреймворка, может сделать эти знания менее непосредственно полезными.

Если фреймворк заменяет SQL на замысловатый проприетарный DSL, модели нужен контекст, специфичный для фреймворка.

Если фреймворк остаётся близко к SQL, модель может использовать широкие знания об SQL.

Если HTTP-клиент выглядит как HTTP-клиент, модель может рассуждать об HTTP напрямую.

Если репозиторий использует явный SQL и типизированные параметры, агенту не нужно обратно восстанавливать состояние ORM.

Поэтому у тонких абстракций Kora есть неожиданное преимущество для нейро-технологий: они сохраняют ценность общих предобученных знаний.

## Семантическая дистанция важна для агентов { #semantic-distance }

Рассмотрим два стека.

Стек A:

```text
бизнес-код
  ↓
DSL, специфичный для фреймворка
  ↓
абстракция фреймворка
  ↓
адаптер
  ↓
нативная библиотека
```

Стек B:

```text
бизнес-код
  ↓
тонкая интеграция Kora
  ↓
нативная библиотека
```

В стеке A агент должен понимать семантический перевод фреймворка.

В стеке B знания о нижележащей технологии остаются непосредственно релевантными.

Чем ниже семантическая дистанция, тем меньше специфичного для проекта контекста нужно агенту.

Это улучшает и генерацию кода, и отладку.

## Явный SQL — хороший пример { #explicit-sql }

Агент, отлаживающий проблему с базой данных, может рассуждать напрямую о:

```sql
SELECT id, status
FROM orders
WHERE customer_id = :customerId
```

Он уже знает семантику SQL, индексы, соединения, транзакции и концепции плана выполнения.

Если слой данных прячет запрос за множеством уровней абстракции, агенту сначала приходится реконструировать фактическую операцию с базой данных.

Явный стиль репозиториев Kora делает границу персистентности проще для изучения.

То же свойство выгодно опытным людям.

## Виртуальные потоки снижают неоднозначность модели конкурентности { #virtual-threads }

Конкурентность — крупный источник ошибок агентов.

Фреймворк, который смешивает:

```text
блокирующие методы
реактивные издатели
корутины
callback-API
ограничения event-loop
```

требует от агента внимательно отслеживать семантику выполнения.

Синхронная модель Kora 2, ориентированная на виртуальные потоки, сужает выбор по умолчанию.

Код приложения в целом выглядит как привычный синхронный Java/Kotlin.

Это не делает конкурентность тривиальной.

Пулы баз данных, дедлайны, структурированная конкурентность, отмена и потокобезопасность по-прежнему важны.

Но модель программирования легче выводится из обычного кода.

Для агента меньше моделей выполнения означает меньше возможностей смешать несовместимые предположения.

## Знакомые стеки вызовов помогают агентам отладки { #familiar-call-stacks }

Предположим, запрос делает:

===! ":fontawesome-brands-java: `Java`"

    ```java
    var user = repository.findById(id);
    var recommendations = client.load(user);
    return mapper.map(user, recommendations);
    ```

=== ":simple-kotlin: `Kotlin`"

    ```kotlin
    val user = repository.findById(id)
    val recommendations = client.load(user)
    return mapper.map(user, recommendations)
    ```

Этот синхронный стек вызовов легко проследить статически.

Глубоко реактивный конвейер тоже может быть полностью корректным, но поток управления представлен через операторы, колбэки, распространение контекста и границы планировщика.

LLM могут рассуждать о реактивном коде, но это требует больше контекста, специфичного для фреймворка и библиотек.

Когда виртуальные потоки позволяют синхронный код без возврата к ограничению «один поток платформы на запрос», простота снова становится операционно жизнеспособной.

Это помогает людям и агентам одновременно.

## Быстрый запуск меняет экономику агента { #fast-startup }

Проверка на этапе компиляции — только первая половина цикла.

Вторая половина — поведенческая проверка.

После компиляции кода агенту всё ещё нужны тесты.

Если каждый компонентный или интеграционный тест требует двадцати секунд запуска приложения, автономная итерация становится дорогой.

Если контекст приложения запускается быстро, цикл становится:

```text
правка
компиляция
запуск
тест
исправление
```

вместо:

```text
правка
компиляция
ожидание
ожидание
ожидание
тест
исправление
```

Разница накапливается за десятки итераций.

Для агентных рабочих процессов задержка запуска становится метрикой продуктивности.

## Нейро-агенты тоже потребляют реальное время { #wall-clock-time }

Легко думать, что вычисления агента дёшевы по сравнению со временем инженера.

Но длинные циклы обратной связи имеют реальную стоимость:

```text
риск таймаута инструмента
стоимость CI
бюджет выполнения агента
время ожидания разработчика
меньшее число попыток
```

Агент, который может выполнить тридцать реалистичных итераций компонентных тестов за то время, за которое другой стек позволяет пять, имеет гораздо больше шансов сойтись на надёжном решении.

Поэтому быстрый запуск косвенно повышает качество агента, позволяя больше циклов сбора свидетельств.

## Короткие циклы поощряют реальные тесты вместо статического угадывания { #short-loops-real-tests }

Когда тесты дороги, и люди, и агенты склонны рассуждать, не запуская их.

Когда тесты дёшевы, проверка становится выбором по умолчанию.

Это важно, потому что LLM вероятностны.

Правильный рабочий процесс — не:

```text
доверять модели
```

а:

```text
позволить модели предлагать
позволить инструментам проверять
```

Быстрый запуск контекста Kora поддерживает эту философию.

Агент может позволить себе часто запускать реальные проверки уровня приложения.

## Компонентные тесты особенно дружелюбны к агентам { #component-tests }

Компонентный тест даёт агенту средний путь между:

```text
крошечным изолированным модульным тестом
```

и:

```text
полностью развёрнутой системой
```

Граф приложения Kora может запускаться с выбранными тестовыми заменами и переопределениями конфигурации.

Это позволяет агенту проверить:

```text
связывание DI
сгенерированные репозитории
поведение AOP
HTTP-клиенты
конфигурацию
реальный жизненный цикл
```

без полного продакшн-окружения.

Это ровно тот уровень, где ловится множество ошибок фреймворка.

## Замена в тесте делает эксперименты дешёвыми { #test-replacement }

Предположим, агент изменяет:

```text
PaymentService
```

но ему не нужен реальный платёжный шлюз.

Тест может заменить:

```text
PaymentClient
```

детерминированным фейком.

Остальная часть графа остаётся реальной.

Это создаёт мощную среду отладки:

```text
реальное связывание фреймворка
+
контролируемая зависимость
+
быстрый запуск
```

Агенты работают хорошо, когда могут создавать такие контролируемые эксперименты.

## Testcontainers завершает цикл для реальной инфраструктуры { #testcontainers }

Некоторое поведение нельзя надёжно замокать.

Базы данных, Kafka, NATS, MinIO и другая инфраструктура имеют семантику протоколов и жизненного цикла, которую моки не воспроизводят.

Для таких случаев интеграционные тесты на базе Testcontainers дают реальные свидетельства.

Быстрый запуск приложения Kora по-прежнему важен, потому что запуск контейнера становится доминирующей стоимостью, а не инициализация фреймворка.

Фреймворк не добавляет ненужной задержки и без того дорогому интеграционному тесту.

## Агенты выигрывают от многоуровневой проверки { #layered-verification }

Полезный автономный рабочий процесс:

```text
1. компилятор
2. модульные тесты
3. компонентные тесты
4. интеграционные тесты
5. black-box тесты
```

Каждый уровень ловит разные классы ошибок.

Компилятор ловит структурные и типовые ошибки.

Модульные тесты ловят локальное поведение.

Компонентные тесты ловят интеграцию графа и фреймворка.

Интеграционные тесты ловят семантику реальных технологий.

Black-box тесты ловят публичное поведение.

Архитектура Kora естественно поддерживает эту прогрессию.

## Компилятор может научить агента фреймворку { #compiler-teaches-framework }

Это удивительно важное свойство.

Агенту не нужно полное знание до первой правки.

Он может учиться, пробуя правдоподобную реализацию и наблюдая обратную связь компилятора.

Например:

```text
агент угадывает сигнатуру репозитория
  ↓
процессор отклоняет неподдерживаемый тип
  ↓
агент читает диагностику
  ↓
агент ищет документацию/пример
  ↓
исправляет сигнатуру
```

Фреймворк становится частично самообучающимся через свою диагностику.

Это работает, только если ошибки конкретны и выполнимы.

Поэтому у фреймворков с компиляцией на этапе компиляции есть стимул серьёзно вкладываться в диагностику.

Эти инвестиции непропорционально выгодны агентам.

## Сообщения об ошибках становятся API для автономных инструментов { #error-messages-api }

Авторы фреймворков традиционно оптимизируют сообщения об ошибках для людей.

Те же сообщения теперь обслуживают агентов кодирования.

Хорошая диагностика имеет:

```text
точное местоположение
точные имена типов
понятный ожидаемый контракт
минимальный нерелевантный стек-трейс
выполнимое описание
```

Например:

```text
Для параметра `foo` нет компонента типа Foo
в конструкторе BarService
```

агенту гораздо легче действовать, чем по длинному общему сбою инициализации.

По мере роста агентной разработки качество диагностики становится функцией фреймворка.

## Обратная связь компилятора — детерминированное свидетельство { #deterministic-evidence }

LLM генерируют вероятностные ответы.

Результаты компилятора детерминированы.

Эта комбинация мощна.

Модель предлагает.

Компилятор выносит решение.

Модель пересматривает.

Это похоже на формальный поиск с оракулом.

Фреймворк увеличивает число архитектурных вопросов, по которым компилятор может выносить решение.

Это улучшает сходимость.

## Сгенерированные исходники дают второй оракул { #second-oracle }

Компилятор говорит агенту, что код структурно корректен.

Сгенерированный исходный код говорит агенту, что фреймворк фактически построил.

Это разные формы свидетельств.

Полезный цикл агента:

```text
написать объявление
  ↓
компиляция
  ↓
изучить сгенерированную реализацию
  ↓
проверить предположение
  ↓
запустить тест
```

Если связывание SQL в сгенерированном репозитории неверно, агент может это увидеть.

Если вложенность AOP отличается от ожидаемой, сгенерированная обёртка это раскрывает.

Если граф приложения выбирает другую реализацию, сгенерированное связывание это показывает.

Это необычно прозрачная среда для автоматизированных рассуждений.

## Документация становится эффективнее, когда совпадает со сгенерированной реальностью { #docs-match-generated-reality }

Одной документации агентам недостаточно.

Репозитории часто содержат:

```text
старые примеры
устаревший код
смешанные версии фреймворка
внутренние соглашения
```

Модель может извлечь не тот шаблон.

Сгенерированный исходный код даёт специфичную для приложения истину.

Лучший рабочий процесс сочетает:

```text
документацию
примеры из репозитория
компилятор
сгенерированный исходный код
тесты
```

Каждый источник сужает неоднозначность.

Официальная документация и навыки Kora улучшают первые два.

Архитектура фреймворка усиливает последние три.

## Сфокусированная документация снижает шум при поиске { #focused-docs-retrieval }

Производительность агента сильно зависит от качества поиска.

Если знания о фреймворке разбросаны по:

```text
старым постам в блоге
Stack Overflow
слайдам конференций
страницам вики под конкретные версии
```

агент может извлечь противоречивые указания.

Сфокусированный, актуальный набор документации снижает этот риск.

Это не чисто выгода от нейро-технологий.

Люди испытывают ту же путаницу.

Но агенты особенно чувствительны, потому что могут уверенно комбинировать несовместимую информацию, если среда не даёт сильных корректирующих сигналов.

## Дрейф версий — режим отказа агента { #version-drift }

LLM может знать несколько версий фреймворка.

Предположим, версия 1 использовала:

```text
API A
```

а версия 2 использует:

```text
API B
```

Модель может случайно их смешать.

Помогают один рекомендуемый способ плюс проверка на этапе компиляции.

Если старого API больше не существует, компилятор его отклоняет.

Если фреймворк вечно держит несколько параллельных стилей, у модели больше шансов выбрать не то поколение.

Сокращение исторической поверхности улучшает надёжность агента.

## Более узкая модель Kora 2 помогает здесь { #kora-2-narrower-model }

Поколение фреймворка, которое намеренно убирает старые конкурирующие модели программирования, может быть проще для агентов, чем то, которое бессрочно сохраняет каждый исторический подход.

Обратная сторона — работа по миграции.

Выгода — меньшее активное пространство решений.

Как только проект перешёл на текущую модель, у агента меньше устаревших веток для рассмотрения.

Это одна из причин, почему чистая эволюция фреймворка может иметь значение для нейро-инструментов.

## Явная архитектура упрощает навигацию по репозиторию { #explicit-architecture-navigation }

Агент часто начинает с задачи высокого уровня:

> Добавить новый эндпоинт, который загружает заказ и вызывает сервис ценообразования.

Ему нужно найти:

```text
точку входа приложения
стиль HTTP-контроллера
сервисные компоненты
репозиторий
HTTP-клиент
конфигурацию
тесты
```

В явной архитектуре эти связи видны через типы и конструкторы.

Модель может искать:

```text
@KoraApp
@Component
@Repository
@Module
```

и быстро построить карту.

Если архитектура в основном неявна в соглашениях времени выполнения, навигация требует больше рассуждений, специфичных для фреймворка.

## @KoraApp — полезный архитектурный якорь { #koraapp-anchor }

У приложения Kora есть явный корень.

Это даёт агенту естественную отправную точку.

Из `@KoraApp` он может изучить включённые модули и объявления графа.

Из конструкторов — проследить зависимости.

Из сгенерированного исходного кода графа — изучить фактическое связывание.

Это даёт чёткую стратегию архитектурного обхода.

Агенты огромно выигрывают от очевидных отправных точек.

## @Module раскрывает логику конструирования { #module-construction-logic }

Фабрики внутри модулей показывают, откуда берутся инфраструктурные компоненты.

Если агенту нужно изменить:

```text
конфигурацию HTTP-клиента
пользовательские учётные данные
телеметрию
интеграцию внешней библиотеки
```

он может искать поставщиков модулей и видеть конструирование напрямую.

Меньше потребности знать скрытые API расширения контейнера.

Это делает изменения на уровне платформы более доступными для агентов.

## Репозитории явно раскрывают доступ к данным { #repositories-data-access }

Сгенерированная модель репозитория с явными запросами даёт агенту сильные сигналы:

```text
сигнатура метода
SQL/CQL
имена параметров
тип возвращаемого значения
маппинг
```

Агент может рассуждать через границы базы данных и Java.

Ему не нужно в той же степени выводить поведение запроса из состояния сущности или генерации запроса во время выполнения.

Это особенно полезно для задач, связанных с производительностью или корректностью.

## OpenAPI распространяет строгую типизацию на границы сервисов { #openapi-strong-typing }

Когда API сервера и клиента генерируются из контракта OpenAPI, агент получает ещё один сильный источник истины.

Вместо изобретения:

```text
имён JSON-полей
кодов состояния
типов ответов
```

он может изучить сгенерированные типы и определения контракта.

Изменение, нарушающее контракт, с большей вероятностью провалит компиляцию.

Это идеально для автономных изменений, потому что поведение внешнего API выводить безопаснее, чем локальную деталь реализации.

## Сгенерированные клиенты снижают ручные ошибки протокола { #generated-clients }

Агент, пишущий сырой HTTP-код, может допускать тонкие ошибки:

```text
неверный путь
неверный заголовок
неверное JSON-поле
неверная обработка кода состояния
```

Сгенерированный типизированный клиент кодирует большую часть этой структуры.

Модель работает на более высоком уровне, оставаясь под проверкой типов.

Тот же принцип применим к сгенерированным репозиториям и мапперам.

Генерация кода убирает повторяющийся протокольный клей, в котором легко ошибиться и людям, и LLM.

## AOP на этапе компиляции снижает скрытые правила перехвата { #compile-time-aop }

AOP — классический источник сюрпризов фреймворка.

Аннотация может зависеть от:

```text
типа прокси
самовызова
видимости метода
порядка во время выполнения
правил контейнера
```

Сгенерированный на этапе компиляции AOP Kora раскрывает обёртку как исходный код.

Агент может изучить композицию:

```text
повтор
таймаут
транзакция
кеш
валидация
```

напрямую.

Это значительно проще, чем просить модель правильно запомнить каждое правило прокси во время выполнения.

## Самовызов становится выводимым { #self-invocation }

Если Kora генерирует переопределение подкласса, агент может рассуждать из обычной виртуальной диспетчеризации Java.

Правило видно в коде.

Для машинных рассуждений это гораздо лучше, чем скрытая топология вызовов.

В более широком смысле, всякий раз, когда поведение фреймворка сводится к обычной семантике языка, надёжность агента растёт.

LLM имеют огромную обучающую экспозицию к Java и Kotlin.

У них менее надёжные знания о невидимых соглашениях времени выполнения каждого фреймворка.

## Тонкое выполнение означает меньше скрытых переходов состояния { #thin-runtime }

Большой контейнер времени выполнения может выполнять:

```text
сканирование
постобработку
проксирование
условную регистрацию
позднее связывание
маппинг на основе рефлексии
```

между исходным кодом и фактическим поведением.

Каждый такой этап создаёт ещё одно место, где статическая интерпретация агента может разойтись с реальностью выполнения.

Генерация на этапе компиляции схлопывает большую часть этого пути в код.

Во время выполнения по-прежнему есть динамическое состояние там, где ему место.

Но структурные решения фреймворка разрешаются раньше.

Это сужает разрыв между «как выглядит репозиторий» и «что делает программа».

## Агенты предпочитают репозитории, которые объясняют себя { #self-explaining-repositories }

Кодовая база, очень дружелюбная к агентам, имеет желаемое свойство:

> На большинство архитектурных вопросов можно ответить, читая репозиторий плюс вывод инструментов.

Не должно требоваться, чтобы старший инженер устно объяснял скрытые соглашения.

Явный граф Kora, сгенерированный исходный код, сфокусированная документация и обратная связь компилятора подталкивают к этому свойству.

Это ценно, даже если нейро-агент не задействован.

Это снижает организационную зависимость от племенных знаний.

## «Вынеси контекст из головы» — это тоже принцип нейро-технологий { #context-out-of-head }

Люди компенсируют неявные системы памятью.

Старший инженер помнит:

```text
какой модуль побеждает
какая аннотация проксируется
какой ключ конфигурации что включает
какой обходной путь в тестах требуется
```

Нельзя предполагать, что у нейро-агента есть эта специфичная для проекта память, если она не записана где-то доступном для поиска.

Поэтому лучший способ сделать систему дружелюбной к нейро-технологиям — не давать больше инструкций в промпте.

А вынести архитектурный контекст в:

```text
типы
исходный код
сгенерированный исходный код
правила компилятора
тесты
документацию
```

Архитектура Kora естественно делает многое из этого.

## Агентам всё ещё нужна документация { #agents-need-documentation }

Прозрачность на этапе компиляции не отменяет документацию.

Агент не может эффективно вывести всё из сгенерированного исходного кода.

Ему всё ещё нужно знать:

```text
какая абстракция рекомендуется
что означает конфигурация
какая семантика жизненного цикла задумана
какая точка расширения стабильна
```

Документация сужает путь до экспериментов.

Идеальная среда сочетает хорошую документацию с сильной обратной связью компилятора/инструментов.

Документация говорит агенту, куда идти.

Компилятор говорит, правильно ли он туда попал.

## Официальные навыки могут улучшить поиск, но это не главное преимущество { #official-skills }

Специфичные для фреймворка навыки агента или пакеты документации могут быть очень полезны.

Они могут научить:

```text
текущему API
рекомендуемым шаблонам
именам модулей
указаниям по миграции
примерам
```

Но эти инструменты работают лучше всего, когда сам фреймворк остаётся проверяемым.

Навык может сказать агенту:

```text
используй @Module вот так
```

Затем компилятор это проверяет.

Сгенерированный исходный код раскрывает результат.

Тесты доказывают поведение.

Архитектура фреймворка даёт слой доверия под слоем поиска.

## Быстрая строгая обратная связь лучше огромного контекста промпта { #strict-feedback }

Один из ответов на сложность фреймворка — дать агенту огромный контекст промпта:

```text
50 страниц правил фреймворка
соглашения проекта
оговорки времени выполнения
заметки о версиях
```

Это может помочь, но дорого и хрупко.

Другой подход — сделать так, чтобы сама система быстро отклоняла ошибки.

Kora склоняется ко второму.

Агенту не нужно запоминать каждую возможную ошибку, если компилятор её ловит и объясняет.

Это более масштабируемая форма контекста.

## Ограничения могут заменить инструкции { #constraints-replace-instructions }

Предположим, инструкция проекта гласит:

```text
Всегда используй внедрение через конструктор.
```

Это полезно.

Но если структура фреймворка естественно поощряет зависимости через конструктор и проверку сгенерированного графа, сама архитектура подкрепляет инструкцию.

Предположим, другая инструкция гласит:

```text
Не используй реактивные репозитории.
```

Версия фреймворка, которая просто не раскрывает эту конкурирующую модель, полностью убирает выбор.

Для автономной разработки архитектурные ограничения часто сильнее текстовых инструкций.

## Машиночитаемый сбой лучше человеческого соглашения { #machine-readable-failure }

Агенты могут неправильно понимать прозаические соглашения.

Гораздо менее вероятно, что они проигнорируют:

```text
ошибку компилятора
провал теста
несовпадение типов
```

Это подсказывает важный принцип проектирования фреймворков, совместимых с нейро-технологиями:

> Кодируй как можно больше важных правил в исполняемых ограничениях, а не только в документации.

Фреймворки с компиляцией на этапе компиляции естественно хороши в этом.

## Быстрые тесты создают больше возможностей для самокоррекции { #fast-tests-self-correction }

Агенту может понадобиться несколько попыток, чтобы правильно реализовать функцию.

Попытка первая компилируется, но тест проваливается.

Попытка вторая исправляет поведение, но ломает другой тест.

Попытка третья работает.

Если каждая попытка занимает секунды, это нормально.

Если каждая попытка требует долгой загрузки приложения и дорогой настройки окружения, автономная итерация становится менее практичной.

Поэтому быстрый запуск фреймворка — это не только эргономика разработчика.

Он увеличивает возможное число автономных циклов исправления.

## Качество и частота обратной связи перемножаются { #feedback-multiply }

Полезная концептуальная модель:

```text
эффективность агента
≈
качество обратной связи
×
частота обратной связи
```

Точные ошибки компилятора улучшают качество.

Быстрые циклы сборки/тестов улучшают частоту.

Сгенерированный исходный код улучшает интерпретируемость.

Строгая типизация улучшает и то, и другое.

Один рекомендуемый способ снижает число необходимых итераций.

Эти свойства накапливаются.

Именно поэтому история Kora о нейро-технологиях архитектурная, а не про отдельную функцию.

## Пример цикла агента { #example-agent-loop }

Представьте задачу:

> Добавить эндпоинт, который возвращает активные заказы клиента и обогащает их данными ценообразования.

Агент может действовать так:

```text
1. Поискать существующие контроллеры.
2. Изучить @KoraApp / модули.
3. Найти OrderRepository.
4. Найти PricingClient.
5. Добавить DTO запроса/ответа.
6. Добавить метод сервиса.
7. Добавить эндпоинт контроллера.
8. Скомпилировать.
```

Компилятор сообщает:

```text
Нет маппера для PricingResponse → PriceDto
```

Агент ищет существующие мапперы, добавляет недостающий и снова компилирует.

Теперь компиляция графа сообщает:

```text
Неоднозначные компоненты PriceMapper
```

Агент удаляет дубликат или добавляет нужный тег.

Компиляция успешна.

Агент запускает компонентный тест.

Тест показывает:

```text
404 вместо 200
```

Агент изучает сгенерированную HTTP-маршрутизацию или существующий пример контроллера, исправляет аннотацию маршрута и перезапускает.

Тест проходит.

Ни один шаг не потребовал, чтобы модель обладала полным знанием фреймворка заранее.

Среда направила её к корректности.

## Фреймворк становится пространством поиска с отсечением { #search-space-pruning }

Это можно описать алгоритмически.

Агент исследует возможные реализации.

Фреймворк отсекает недопустимые ветки.

Строгие типы устраняют типоневалидные ветки.

DI на этапе компиляции устраняет недопустимые ветки графа.

Сгенерированные API устраняют протокольно-невалидные ветки.

Тесты устраняют поведенчески-невалидные ветки.

Один рекомендуемый способ снижает число веток, порождаемых изначально.

Это очень благоприятная среда для автоматизированного поиска.

## Динамические фреймворки тоже могут хорошо работать с агентами { #dynamic-frameworks }

Было бы неверно утверждать, что только фреймворки с компиляцией на этапе компиляции совместимы с нейро-технологиями.

Крупные динамические фреймворки часто имеют:

```text
огромные экосистемы документации
массивное присутствие в обучающих данных
отличную IDE-инструментацию
множество примеров
зрелую поддержку тестирования
```

Это значительные преимущества.

LLM может знать Spring чрезвычайно хорошо просто потому, что видела огромное количество кода Spring.

Поэтому аргумент не в том:

```text
компиляция = совместимо с нейро-технологиями
выполнение = несовместимо с нейро-технологиями
```

Более точный аргумент:

> Фреймворки с компиляцией на этапе компиляции могут компенсировать меньшую экосистему знаний, делая большую часть истины приложения непосредственно проверяемой и машино-верифицируемой.

Это другое преимущество.

## Обучающие данные и прозрачность выполнения — разные активы { #training-data-transparency }

Популярный фреймворк может иметь огромную знакомость у моделей.

Прозрачный фреймворк может иметь лучшие локальные свидетельства.

Эти активы могут дополнять или конкурировать.

Если агент хорошо знает фреймворк, сильная обратная связь на этапе компиляции всё равно помогает.

Если он плохо знает фреймворк, сгенерированный исходный код и диагностика компилятора становятся ещё ценнее.

Дизайн Kora особенно интересен тем, что снижает зависимость от заученного фольклора фреймворка.

## «Нейро-дружелюбно» не значит «легко для слабых моделей» { #ai-friendly-not-easy }

Сложная бэкенд-инженерия остаётся сложной.

Агенту всё ещё нужно понимать:

```text
транзакции
идемпотентность
индексы базы данных
конкурентность
распределённые сбои
безопасность
наблюдаемость
совместимость API
```

Проверка на этапе компиляции не может решить архитектурные суждения.

Сгенерированный исходный код не может решить, безопасен ли повтор.

Строгие типы не могут доказать SLO.

Быстрые тесты не могут гарантировать поведение в проде.

Фреймворк улучшает среду обратной связи.

Он не заменяет инженерию.

## Корректность компилятора — это не бизнес-корректность { #compiler-vs-business }

Агент может создать код, который идеально компилируется и всё равно неверен.

Например:

===! ":fontawesome-brands-java: `Java`"

    ```java
    @Transactional
    public void chargeAndPublish() {
        chargeCard();
        publishEvent();
    }
    ```

=== ":simple-kotlin: `Kotlin`"

    ```kotlin
    @Transactional
    open fun chargeAndPublish() {
        chargeCard()
        publishEvent()
    }
    ```

Типы могут быть корректны.

Граф может быть валиден.

Сгенерированная транзакционная обёртка может быть корректна.

Но у операции может быть проблема распределённой согласованности, требующая outbox или другого дизайна.

Фреймворки с компиляцией на этапе компиляции ловят структурные ошибки, а не каждую семантическую.

нейро-агентам всё ещё нужны тесты, архитектурные правила и человеческое ревью для высокорисковых изменений.

## Сгенерированный исходный код тоже может вводить в заблуждение, если читать без семантики { #generated-source-mislead }

Агент может изучить сгенерированный JDBC-код и заключить, что механизм корректен, упустив:

```text
отсутствующий индекс
неверный уровень изоляции
небезопасный повтор
неограниченный набор результатов
```

Прозрачность делает поведение видимым.

Она не делает интерпретацию автоматически корректной.

Преимущество в том, что у агента есть лучшие свидетельства для работы.

## Быстрые циклы могут ускорять и плохие решения { #fast-loops-bad-decisions }

Модель с неверной высокоуровневой целью может очень эффективно итерировать к неверному решению.

Например, она может быстро сделать все тесты зелёными, ослабив утверждения.

Это не проблема фреймворка.

Это общая проблема управления агентами.

Быстрая обратная связь должна сочетаться с:

```text
хорошими тестами
чёткими критериями приёмки
ревью кода
проверками безопасности
архитектурными ограничениями
```

Фреймворк даёт лучшую среду выполнения, а не полную систему надзора.

## Дизайн, совместимый с нейро-технологиями, — это в основном хороший дизайн фреймворка { #ai-friendly-good-design }

Это, возможно, самый важный вывод.

Функции, помогающие агентам кодирования, — не экзотические функции, специфичные для нейро-технологий.

Это то, чего хорошие инженеры фреймворков хотели годами:

```text
явная архитектура
строгая типизация
ранние ошибки
хорошая диагностика
читаемый сгенерированный код
мало скрытых правил
быстрый запуск
быстрые тесты
стабильные соглашения
```

Нейро-технологии просто меняют то, насколько ценными становятся эти свойства.

Человек может компенсировать запутанный фреймворк времени выполнения накоплением опыта.

Автономному агенту приходится многократно реконструировать большую часть этого опыта.

Поэтому прозрачность и детерминированная обратная связь становятся непропорционально ценными.

## Явная архитектура помогает и младшим инженерам { #junior-engineers }

Ориентированные на нейро-технологии свойства Kora зеркалят свойства адаптации.

Младший разработчик тоже выигрывает от:

```text
понятных конструкторов
одного рекомендуемого шаблона
ошибок компилятора
сгенерированного исходного кода
сфокусированной документации
быстрых тестов
```

Это не совпадение.

И новичок, и нейро-агент начинают с неполного контекста проекта.

Обоим нужно построить точную ментальную модель из свидетельств.

Фреймворки, которые выносят контекст наружу, снижают стоимость адаптации для обоих.

## Старшие инженеры выигрывают иначе { #senior-engineers }

Экспертам может не нужен компилятор, объясняющий базовое внедрение зависимостей.

Но они выигрывают от:

```text
более быстрого ревью
меньше археологии фреймворка
предсказуемого сгенерированного поведения
меньшей поверхности миграции
более лёгкой автоматизации
```

Поэтому совместимость с нейро-технологиями — это не функция, которая отнимает контроль у экспертов.

В случае Kora те же свойства поддерживают глубокую инспекцию.

## Сгенерированный код улучшает ревью кода с нейро-технологиями { #code-review-ai }

Представьте нейро-агент ревью, проверяющий пул-реквест, который добавляет транзакцию и аннотацию повтора.

Он может изучить:

```text
изменение, написанное вручную
сгенерированную AOP-обёртку
тесты
```

и рассуждать о фактическом порядке.

Ревью-агент, изучающий изменение репозитория, может изучить сгенерированную реализацию и связывание SQL.

Агент, ревьюящий изменения OpenAPI, может сравнить сгенерированные типы сервера/клиента.

Сгенерированные артефакты делают поведение фреймворка проверяемым инструментами за пределами исходного агента кодирования.

## Статический анализ сочетается с фреймворками компиляции { #static-analysis }

Поскольку Kora производит обычный исходный код и байткод Java/Kotlin, стандартные инструменты могут продолжать его анализировать:

```text
компилятор
Error Prone
SpotBugs
detekt
инспекции IDE
сканеры безопасности
анализаторы зависимостей
```

нейро-агент может использовать эти инструменты как дополнительные каналы обратной связи.

Фреймворку не требуется полностью отдельная система интроспекции времени выполнения для базовой структуры.

Это упрощает композицию инструментов.

## Репозиторий приложения становится более самодокументирующим { #self-describing-repository }

Высоко совместимый с агентами репозиторий должен отвечать:

```text
Какие компоненты существуют?
Что от чего зависит?
Как маршрутизируется HTTP?
Как осуществляется доступ к данным?
Как вызываются внешние сервисы?
Как применяются сквозные задачи?
Как тестируется приложение?
```

из файлов внутри репозитория.

Kora движется к этой модели через:

```text
@KoraApp
модули
конструкторы
сгенерированные репозитории
сгенерированный HTTP
сгенерированный AOP
типизированную конфигурацию
тесты
```

Это фактически исполняемая архитектурная документация.

## Сгенерированные исходники снижают потребность в инструментах интроспекции времени выполнения { #runtime-introspection }

В сильно динамическом фреймворке агенту могут понадобиться:

```text
эндпоинт actuator
дамп контейнера
граф бинов
инспекция прокси времени выполнения
отладочные логи
```

чтобы обнаружить конечную структуру.

Эти инструменты могут быть полезны.

Kora переносит больше обнаружения в артефакты сборки.

Агент может изучить архитектуру до запуска сервиса.

Это особенно ценно в ограниченных CI или песочницах, где запуск полного приложения может быть дорогим или невозможным.

## Знания на этапе компиляции помогают удалённым агентам { #remote-agents }

Многие агенты кодирования работают в эфемерных контейнерах с:

```text
ограниченным доступом к сети
отсутствием продакшн-учётных данных
отсутствием реальной инфраструктуры
ограниченным временем выполнения
```

Чем больше они могут проверить без запуска всего мира, тем лучше.

Проверка графа на этапе компиляции и сгенерированный исходный код дают полезные свидетельства, даже когда Elasticsearch, Kafka или реальная база данных недоступны.

Затем сфокусированные интеграционные тесты можно запускать только при необходимости.

Это делает рабочие процессы агентов более устойчивыми в ограниченных средах.

## Сильные артефакты сборки улучшают воспроизводимость { #build-artifacts-reproducibility }

Агент, работающий в CI, должен видеть ту же генерацию графа, которую используют продакшн-артефакты.

Если архитектура фреймворка кодируется во время сборки, среда проверки агента и продакшн-процесс сборки выровнены.

Меньше места для:

```text
работает в среде агента
падает при инициализации контейнера при развёртывании
```

исключительно из-за разного обнаружения во время выполнения.

Воспроизводимые структурные сборки ценны для автономных изменений.

## Сборка становится шагом архитектурного доказательства { #architectural-proof }

Не формального доказательства, но полезного.

Успешная сборка Kora устанавливает несколько фактов:

```text
типы валидны
зависимости разрешаются
в графе нет обнаруженной неоднозначности/цикла
сгенерированный код компилируется
контракты фреймворка приняли объявления
```

Это гораздо информативнее, чем «javac принял написанный вручную исходный код».

Для агента сборка — более богатая контрольная точка валидации.

## Быстрый запуск затем проверяет оставшуюся динамическую реальность { #fast-startup-dynamic-reality }

Компиляция обрабатывает статическую структуру.

Тесты обрабатывают поведение во время выполнения:

```text
база данных действительно отвечает
HTTP-маппинг действительно работает
значения конфигурации корректны
поведение транзакций соответствует ожиданию
таймауты ведут себя корректно
```

Это разделение элегантно для агентных рабочих процессов.

Используй компилятор для того, что можно знать статически.

Используй тесты для того, что требует выполнения.

Не откладывай статические ошибки до выполнения.

## Цикл можно моделировать как прогрессирующую уверенность { #progressive-certainty }

Агент начинает с неопределённого кода.

Каждый этап добавляет уверенности:

```text
исходный код сгенерирован
  ↓
проверка типов
  ↓
валидация графа
  ↓
инспекция сгенерированной реализации
  ↓
модульный тест
  ↓
компонентный тест
  ↓
интеграционный тест
  ↓
black-box тест
```

Это конвейер прогрессирующей уверенности.

Kora увеличивает объём полезной валидации, доступной рано в этом конвейере.

Это снижает стоимость неверных предположений.

## Короткие циклы обратной связи особенно важны для автономного рефакторинга { #short-loops-refactoring }

Небольшие добавления функций — это одно.

Крупные рефакторинги требуют множества промежуточных состояний.

Автономному агенту может понадобиться:

```text
изменить интерфейс
обновить реализации
изменить связывание
исправить тесты
мигрировать вызывающий код
```

Проверка графа на этапе компиляции даёт немедленную информацию о том, что осталось несогласованным.

Сгенерированный исходный код отражает новую структуру.

Быстрые тесты проверяют каждый этап.

Это делает инкрементальный рефакторинг безопаснее.

## Явные зависимости помогают автоматизированному анализу влияния { #automated-impact-analysis }

Если конструктор зависит от `FraudClient`, агент может искать ссылки и понимать влияние.

Если зависимости получаются динамически из глобального контейнера, анализ влияния сложнее.

Явные рёбра графа улучшают:

```text
рефакторинг
замену зависимостей
выделение модулей
обнаружение мёртвого кода
изоляцию тестов
```

Это типичные задачи агентов.

Архитектурой легче манипулировать механически.

## Один рекомендуемый способ делает крупномасштабную генерацию кода безопаснее { #large-scale-codegen }

Предположим, агенту нужно добавить двадцать похожих эндпоинтов или мигрировать пятьдесят сервисов.

Согласованность имеет огромное значение.

Если у Kora один стандартный шаблон контроллера, один шаблон репозитория и одна модель конфигурации, агент может систематически генерировать преобразования.

Если каждый сервис использует другой стиль абстракций, массовая автоматизация становится хрупкой.

Поэтому когерентность фреймворка улучшает не только локальное кодирование, но и автоматизацию масштаба флота с помощью нейро-технологий.

## Агенты могут надёжно учиться по соседнему коду { #nearby-code }

LLM часто подражают локальным примерам.

Это одно из их сильнейших практических поведений.

Если репозиторий последовательно использует:

```text
@Module
@Component
@Repository
типизированную конфигурацию
синхронные методы сервиса
```

соседний пример с высокой вероятностью будет корректным руководством.

Когерентный фреймворк усиливает ценность локального поиска.

Сильно гетерогенный фреймворк её ослабляет.

## Меньше абстракций означает меньший контекст промпта { #smaller-prompt-context }

Каждая абстракция фреймворка, которую нужно объяснить, потребляет контекст.

Если агенту нужно помнить:

```text
какое семейство репозиториев
какой менеджер транзакций
какой реактивный тип
какой режим прокси
какая подсистема конфигурации
```

контекст промпта/инструмента растёт.

Сфокусированная модель Kora снижает объём специфичного для проекта состояния фреймворка, которое нужно нести одновременно.

Это оставляет больше бюджета контекста под реальную бизнес-задачу.

Это может становиться всё важнее по мере работы агентов с более крупными репозиториями.

## Сгенерированный код можно читать выборочно { #generated-code-selectively }

Есть опасение: сгенерированный исходный код может быть большим.

Агент не должен вслепую поглощать весь сгенерированный код.

Полезный рабочий процесс целенаправленный:

```text
определить компонент
найти сгенерированную реализацию
прочитать нужный метод
```

Это работает, потому что генерация предсказуема и на уровне исходного кода.

Фреймворк обеспечивает проверяемость без требования, чтобы всё сгенерированное дерево было постоянным контекстом промпта.

## Фреймворки компиляции создают лучшие хуки для инструментов { #tool-hooks }

Платформа агента может автоматизировать:

```text
компиляцию проекта
разбор диагностики
поиск сгенерированного класса
запуск целевого теста
диф сгенерированного вывода
```

Это стабильные механические операции.

Фреймворки с тяжёлым выполнением могут раскрывать эквивалентную инструментацию, но часто требуют специфичных для фреймворка API интроспекции.

Артефакты этапа компиляции легче интегрировать в общие конвейеры агентов кодирования.

## Диагностику сборки можно разбирать программно { #build-diagnostics }

Диагностика компилятора достаточно структурирована для поддержки автоматизированных рабочих процессов:

```text
файл
строка
символ
тип
сообщение
```

Агент может напрямую сопоставлять ошибки с правками.

Длинные логи времени выполнения часто содержат больше шума:

```text
баннеры запуска
логи потоков
вложенные исключения
стек-трейсы фреймворка
несвязанный вывод инициализации
```

Хорошую диагностику выполнения всё ещё можно разбирать, но сбои на этапе компиляции в целом имеют лучшую локализацию.

Это важно для автономного исправления.

## Архитектура Kora создаёт полезную иерархию истины { #hierarchy-of-truth }

Когда агенту нужно что-то узнать, он может обратиться ко всё более конкретным свидетельствам:

```text
1. документация: что фреймворк должен делать?
2. исходный код, написанный вручную: что объявил разработчик?
3. сгенерированный исходный код: что построила Kora?
4. компилятор: валидна ли структура?
5. тесты: соответствует ли поведение ожиданию?
6. телеметрия выполнения: что происходит в проде?
```

Эта иерархия мощна, потому что разногласия можно локализовать.

Если документация и сгенерированный код расходятся, исследуй различия фреймворка/версии.

Если сгенерированный код выглядит правильно, но тесты падают, исследуй семантику выполнения.

Если тесты проходят, но прод падает, исследуй среду и масштаб.

Агенты выигрывают от систем, предоставляющих несколько независимых слоёв свидетельств.

## Наблюдаемость в проде расширяет цикл агента { #production-observability }

Та же прозрачность может продолжаться после развёртывания.

Kora интегрирует:

```text
метрики
трассировку
структурированные логи
пробы
```

через модули.

Операционный агент может проследить:

```text
span HTTP-сервера
  ↓
сервис
  ↓
HTTP-клиент / репозиторий
```

и сопоставить логи.

Это значит, что дружелюбная к агентам архитектура Kora не ограничивается генерацией кода.

Она также поддерживает автоматизированную диагностику, потому что поведение выполнения наблюдаемо через стандартные сигналы.

## Сгенерированная архитектура плюс телеметрия — сильная комбинация { #architecture-telemetry }

Статический исходный код отвечает:

```text
Что должно произойти?
```

Телеметрия отвечает:

```text
Что произошло?
```

нейро-агент отладки может сравнить их.

Например:

```text
сгенерированная обёртка клиента говорит таймаут = X
трейс показывает таймаут в Y
конфигурация показывает переопределение Z
```

Это гораздо сильнее, чем рассуждения только по логам.

Прозрачные артефакты сборки и прозрачные сигналы выполнения усиливают друг друга.

## Нейро-дружелюбная архитектура снижает риск галлюцинаций { #reduces-hallucination }

Галлюцинации нельзя устранить.

Но архитектура может снизить число неподтверждённых предположений, которые агенту приходится делать.

Строгая типизация снижает изобретённые API.

Явные модули снижают изобретённое связывание.

Сгенерированный исходный код снижает изобретённое поведение выполнения.

Диагностика компилятора снижает изобретённые правила фреймворка.

Тесты снижают изобретённое бизнес-поведение.

Наблюдаемость снижает изобретённые объяснения прода.

Среда постепенно заменяет угадывание свидетельствами.

## Лучший промпт для агента — часто лучшая кодовая база { #better-codebase }

Команды иногда пытаются решить надёжность агента гигантскими файлами инструкций.

Инструкции помогают.

Но репозиторий с:

```text
понятной архитектурой
согласованными шаблонами
хорошими типами
быстрыми тестами
сгенерированным исходным кодом
точными ошибками
```

может требовать меньше инструкций.

Сама кодовая база учит агента, как себя вести.

Это более долговечная инвестиция, потому что выгоду получают и люди.

## Совместимость с Нейро-технологии могут стать критерием выбора фреймворка { #framework-selection-criterion }

Исторически команды оценивают фреймворки по:

```text
производительности
экосистеме
продуктивности разработчиков
эксплуатационности
безопасности
сообществу
```

Совместимость с агентами может стать ещё одним критерием.

Вопросы могут включать:

```text
Могут ли инструменты статически реконструировать структуру приложения?
Читаемы ли сгенерированные внутренности?
Проваливаются ли недопустимые изменения рано?
Есть ли несколько несовместимых моделей программирования?
Как быстро может пройти полный компонентный тест?
Сколько скрытого состояния выполнения существует?
Может ли агент изучить реальные пути выполнения?
```

Фреймворки компиляции необычно хорошо набирают баллы по нескольким из этих измерений.

## Это не значит, что фреймворки должны оптимизироваться только под нейро-технологии { #not-only-for-ai }

Фреймворк, неприятный для людей, но лёгкий для агентов, был бы плохим дизайном.

Интересная часть подхода Kora в том, что свойства совпадают.

Явная архитектура помогает сопровождающим.

Строгие типы помогают IDE.

Сгенерированный исходный код помогает отладке.

Обратная связь компилятора помогает CI.

Быстрый запуск помогает облачным операциям.

Один рекомендуемый способ помогает адаптации.

нейро-агенты выигрывают от того же дизайна.

Нет нужды создавать чужеродную модель программирования, где нейро-технологии первичны.

## Лучшая абстракция, совместимая с нейро-технологиями, — часто обычная хорошая абстракция { #ordinary-good-abstraction }

Агенты уже хорошо знают мейнстримовые языковые конструкции.

Они понимают:

```text
интерфейсы
конструкторы
records/классы данных
вызовы методов
исключения
SQL
HTTP
```

Фреймворк становится для них проще, когда использует эти конструкции напрямую.

Поэтому акцент Kora на привычных идиомах Java/Kotlin имеет вторичную выгоду от нейро-технологий.

Фреймворк не просит модель учить совершенно другой язык, спрятанный внутри Java-аннотаций.

## Почему это важнее по мере роста автономности агентов { #agents-more-autonomous }

Инструменты автодополнения могут полагаться на человека, который сразу ловит ошибки.

Автономным агентам нужно, чтобы среда их контролировала.

По мере роста автономности архитектура, дающая детерминированные контрольные точки, становится ценнее.

Агент может работать несколько минут без вмешательства человека.

В это время компилятор, сгенерированный исходный код, тесты и статический анализ становятся его ревьюерами.

Фреймворк компиляции фактически встраивает больше логики ревью в цикл разработки.

## Фреймворк может действовать как ограждение, не становясь ограничительным { #framework-guardrail }

Есть полезное различие между:

```text
ограждением
```

и:

```text
произвольным ограничением
```

Строгий тип — это ограждение.

Граф на этапе компиляции — это ограждение.

Единая рекомендуемая модель репозитория — это ограждение.

Они снижают недопустимые состояния, всё ещё позволяя обычный дизайн приложения.

Для агентов такие ограждения улучшают автономию, потому что меньше ошибок требует человеческого спасения.

## Самые дружелюбные к агентам системы делают недопустимые состояния дорогими для выражения { #invalid-states-expensive }

Это перекликается с классическим дизайном систем типов.

Если фреймворк позволяет агенту легко выразить недопустимую конфигурацию и отклоняет её только в редких условиях выполнения, автономная работа хрупка.

Если недопустимая структура не может компилироваться, агент немедленно выталкивается обратно к валидному состоянию.

Компилятор-ориентированный подход Kora увеличивает набор недопустимых состояний, которые трудно успешно представить.

Это мощное свойство для машинно-сгенерированного кода.

## Конкретное сравнение { #concrete-comparison }

Рассмотрим два гипотетических рабочих процесса агента.

### Фреймворк с тяжёлым выполнением { #runtime-heavy-framework }

```text
Агент пишет компонент
  ↓
Java компилируется
  ↓
приложение запускается
  ↓
сканирование classpath
  ↓
контейнер выполнения строит граф
  ↓
создание прокси
  ↓
сбой при запуске
  ↓
агент разбирает вложенное исключение выполнения
  ↓
агент правит
```

### Фреймворк стиля Kora с компиляцией { #compile-time-kora-framework }

```text
Агент пишет компонент
  ↓
обработка аннотаций + компилятор
  ↓
валидация графа падает точно
  ↓
агент правит
```

Если компиляция успешна:

```text
агент может изучить сгенерированный граф
  ↓
запустить быстрый компонентный тест
  ↓
проверить поведение
```

Второй рабочий процесс не устраняет ошибки.

Он снижает стоимость их обнаружения.

Это главное преимущество.

## Ещё одно сравнение: скрытое поведение { #hidden-behavior }

Предположим, агенту нужно понять репозиторий.

### Скрытый маппинг выполнения { #hidden-runtime-mapping }

```text
аннотация
  ↓
метаданные выполнения
  ↓
вывод запроса фреймворком
  ↓
вызов прокси
  ↓
база данных
```

### Сгенерированный репозиторий Kora { #generated-kora-repository }

```text
объявление репозитория
  ↓
процессор этапа компиляции
  ↓
сгенерированная реализация
  ↓
база данных
```

Во втором случае агент может изучить реализацию, которая фактически выполняется.

Это огромное снижение неопределённости.

## Ещё одно сравнение: пространство выбора фреймворка { #framework-choice-space }

Предположим, задача требует доступа к базе данных.

Фреймворк A предлагает:

```text
JPA
JDBC-шаблон
R2DBC
реактивный репозиторий
репозиторий с выводимым запросом
query-by-example
DSL
нативный API сессий
```

Фреймворк B говорит:

```text
Используй модель репозитория с явным SQL.
```

Фреймворк A может быть гибче.

Фреймворк B даёт автономному агенту меньше возможностей выбрать технически валидный, но локально неподходящий путь.

Для команд, оптимизирующих согласованность и автоматизацию, такой обмен может быть очень привлекательным.

## Цена: фреймворки компиляции переносят сложность в сборку { #cost-build-complexity }

Бесплатного обеда нет.

Обработка аннотаций и генерация кода увеличивают сложность сборки.

Сгенерированные исходники могут быть большими.

Плагины/процессоры компилятора нуждаются в отличной диагностике.

Инкрементальные сборки должны хорошо работать.

Интеграция с IDE важна.

Агент выигрывает, только если сама сборка надёжна и достаточно быстра.

Фреймворк компиляции с медленными процессорами и непонятными ошибками мог бы быть хуже для агентов, чем отполированный фреймворк выполнения.

Архитектура создаёт возможность.

Качество реализации определяет, реализуется ли возможность.

## Производительность инкрементальной сборки важна для агентов { #incremental-build }

Агентная разработка может включать много мелких правок.

Бенчмарк чистой сборки — не единственное релевантное число.

Важный цикл часто такой:

```text
изменить один файл
скомпилировать затронутые модули
запустить один тест
```

Если обработка аннотаций инвалидирует весь проект при каждом изменении, архитектура компиляции теряет большую часть преимущества.

Хорошая инкрементальная обработка, кеширование Gradle, границы модулей и детерминированная генерация — важная инфраструктура, включающая нейро-технологии.

## Сгенерированные исходники должны быть читаемыми { #generated-sources-readable }

Сгенерированный код вида:

```text
a1.b2(c7,d9,x14)
```

технически раскрывал бы поведение, но был бы бесполезен для рассуждений.

Поэтому акцент Kora на человекочитаемом сгенерированном исходном коде важен.

Читаемый сгенерированный код имеет:

```text
стабильные имена
узнаваемые типы
обычный поток управления
минимум ненужной косвенности
```

Это выгодно и отладчикам, и LLM.

## Диагностика должна избегать археологии компилятора { #avoid-compiler-archaeology }

Фреймворк может перенести ошибки на этап компиляции и всё равно выдавать ужасные сообщения.

Например:

```text
AnnotationProcessorException at NodeResolverImpl line 492
```

не помогает.

Полезная цель:

```text
Не удаётся создать PaymentService:
не найден компонент PaymentRepository
```

Архитектура компиляции повышает важность инженерии диагностики.

По мере распространения агентов кодирования точная диагностика становится ещё ценнее.

## Агентам также нужна стабильная генерация имён { #stable-generated-naming }

Предсказуемые имена сгенерированных классов помогают навигации.

Если агент может вывести:

```text
PaymentService
→ сгенерированный AOP-прокси рядом
```

или:

```text
OrderRepository
→ сгенерированная реализация
```

он может программно находить вывод фреймворка.

Стабильные имена улучшают навигацию в IDE, скрипты отладки и автоматизированную инспекцию.

Это небольшая деталь дизайна с большими последствиями для инструментов.

## Артефакты сборки становятся входными данными для рассуждений с помощью нейро-технологий { #build-artifacts-ai-reasoning }

Традиционно сгенерированный исходный код считается деталью реализации.

В агентной разработке он может стать важным артефактом рассуждений.

Инструменты могут намеренно раскрывать:

```text
сгенерированный граф
сгенерированный репозиторий
сгенерированный HTTP-обработчик
сгенерированную AOP-обёртку
```

агенту, когда это уместно.

Это предполагает будущее, где выводы сборки фреймворка проектируются не только для JVM, но и для машинной инспекции.

Kora уже структурно близка к этой модели.

## Агенту не нужно запоминать фреймворк, если он может его допрашивать { #interrogate-framework }

Это, пожалуй, самое необычное следствие.

Традиционное владение фреймворком — отчасти память:

```text
знать аннотации
знать правила
знать исключения
знать модель выполнения
```

Дружелюбный к агентам фреймворк может заменить часть этой памяти допросом:

```text
компилировать
изучать
искать
тестировать
```

Агент спрашивает систему, что валидно и что было сгенерировано.

Это более надёжная модель взаимодействия, чем предположение, что предобученная память LLM всегда корректна.

## Прозрачность фреймворка становится ценнее его популярности в некоторых задачах { #transparency-vs-popularity }

Популярность остаётся важной.

Но для внутренних модулей, новых версий фреймворка или специфичных для организации расширений обучающие данные всегда будут неполными.

Прозрачность масштабируется там, где популярность — нет.

Внутренний модуль Kora, написанный на прошлой неделе, не может присутствовать в предобученных данных модели.

Но если он использует:

```text
@Module
типизированную конфигурацию
обычные конструкторы
Lifecycle
телеметрию
```

агент может изучить и понять его в любом случае.

Это большое преимущество для приватных кодовых баз.

## Приватный корпоративный код — где это может быть важнее всего { #private-enterprise-code }

Публичные обучающие данные помогают моделям с популярными open-source фреймворками.

Корпоративные кодовые базы содержат:

```text
внутренние библиотеки
пользовательские модули
соглашения компании
приватные API
новые сервисы
```

ничего из этого не было в предобучении.

Архитектура, которая явна и самодокументирующа, даёт агентам способ рассуждать локально.

Поэтому структура фреймворка компиляции особенно релевантна внутри приватных организаций.

## Внутренние модули могут стать читаемыми для агентов контрактами платформы { #internal-modules-platform }

Предположим, компания публикует:

```text
company-kora-nats
company-kora-auth
company-kora-storage
```

Если эти модули следуют тем же явным шаблонам Kora, агент может выучить их из исходного кода.

Компилятор проверяет использование.

Сгенерированный код графа показывает конечную интеграцию.

Тесты демонстрируют соглашения.

Команде платформы не нужно, чтобы каждая будущая модель имела предобученные знания о внутренней инфраструктуре.

Сама кодовая база предоставляет контракт.

## Нейро-дружелюбная архитектура помогает агентам миграции { #migration-agents }

Миграции фреймворков — естественная нагрузка для агентов.

Агенту миграции нужно:

```text
найти старый API
сопоставить с новым API
скомпилировать
исправить сбои
запустить тесты
повторить
```

Диагностика этапа компиляции здесь чрезвычайно полезна.

Чистая целевая архитектура «один способ» тоже помогает, потому что агенту не нужно выбирать среди множества эквивалентных новых стилей.

Сгенерированный исходный код позволяет проверить, как разрешаются мигрированные объявления.

Поэтому собственные миграции версий Kora могут выигрывать от тех же свойств.

## Крупномасштабный рефакторинг становится механически проверяемым { #large-scale-refactoring }

Представьте изменение контракта конструктора, используемого в пятидесяти модулях.

Компилятор идентифицирует все сломанные места вызовов и рёбра графа.

Агент может итерировать систематически.

Это гораздо безопаснее, чем полагаться на покрытие выполнения для обнаружения всего затронутого динамического связывания.

Сильная архитектура компиляции улучшает уверенность в автоматизированном рефакторинге.

## Ревью кода может больше фокусироваться на семантике { #code-review-semantics }

Если компилятор обрабатывает:

```text
валидность типов
полноту графа
валидность сгенерированного кода
```

ревьюеры могут уделять больше внимания:

```text
бизнес-поведению
безопасности
производительности
согласованности данных
дизайну API
```

То же применимо к ревью-агентам на основе нейро-технологий.

Механика фреймворка становится меньшим бременем ревью, потому что большая её часть сгенерирована и механически проверена.

## Преимущество Kora для нейро-технологий — это не отдельная функция { #not-an-ai-feature }

Не требуется никакого магического «режима выполнения LLM».

Преимущества возникают из обычного дизайна фреймворка:

```text
ориентированность на компилятор
типизированность
явность
генерация
скорость
согласованность
```

Это важно, потому что продуктовые функции, специфичные для нейро-технологий, могут быстро устаревать.

Принципы архитектуры устаревают гораздо медленнее.

Фреймворк, который легко изучать инструментам сегодня, с высокой вероятностью останется лёгким для будущих инструментов.

## Полезная ментальная модель: снижай энтропию { #reduce-entropy }

Агент начинает задачу с неопределённостью.

Дизайн фреймворка может либо увеличивать, либо снижать эту неопределённость.

Скрытые правила выполнения увеличивают энтропию.

Множество конкурирующих стилей увеличивают энтропию.

Динамическое состояние контейнера увеличивает энтропию.

Слабые типы увеличивают энтропию.

Длинные циклы обратной связи дольше сохраняют энтропию.

Дизайн Kora снижает её:

```text
явный граф
→ меньше скрытых связей

строгие типы
→ меньше возможных значений/контрактов

сгенерированный код
→ видимые решения фреймворка

обратная связь компилятора
→ недопустимые гипотезы отклоняются

один рекомендуемый способ
→ меньше веток решений

быстрые тесты
→ поведение проверяется быстро
```

Рассмотренная так, совместимость с нейро-технологиями — это задача теории информации.

Фреймворк делает состояние приложения легче наблюдаемым и ограничиваемым.

## Идеальный цикл агента в Kora { #ideal-agent-loop }

Зрелый рабочий процесс может выглядеть так:

```text
Агент читает задачу
  ↓
изучает соседние шаблоны Kora
  ↓
правит исходный код, написанный вручную
  ↓
запускает инкрементальную компиляцию
  ↓
читает диагностику типов / графа / процессоров
  ↓
исправляет структурные ошибки
  ↓
изучает сгенерированный исходный код, если важно поведение фреймворка
  ↓
запускает целевой компонентный тест
  ↓
запускает реальный интеграционный тест, где необходимо
  ↓
читает телеметрию / вывод сбоев
  ↓
исправляет семантические ошибки
  ↓
финальная проверка
```

Это сильная среда автономной разработки, потому что каждый этап даёт конкретные свидетельства.

Агенту не нужно быть всеведущим.

Ему нужно уметь задавать системе хорошие вопросы.

## Где люди всё ещё важны { #where-humans-matter }

Даже при отличной обратной связи есть решения, которые агенты не должны принимать вслепую.

Примеры включают:

```text
границы транзакций
политику безопасности
выборы по хранению данных
безопасность повторов
совместимость публичного API
стратегию миграции схем
компромиссы SLO
владение архитектурой
```

Компилятор не может на них ответить.

Сгенерированный код не может на них ответить.

Тесты могут кодировать только то, что команда уже подумала тестировать.

Человеческое суждение остаётся необходимым, особенно для изменений с высоким влиянием.

Нейро-дружелюбный дизайн фреймворка должен улучшать исполнение, а не убирать управление.

## Лучший исход — симметрия человека и агента { #human-agent-symmetry }

Особенно здоровая система — та, где люди и агенты используют одни и те же свидетельства:

```text
исходный код
компилятор
сгенерированный код
тесты
телеметрию
```

Нет отдельного «слоя объяснений с помощью нейро-технологий», оторванного от реальности.

Если Нейро-технологии говорят:

> Этот вызов репозитория обёрнут повтором вне таймаута,

человек должен иметь возможность открыть сгенерированный исходный код и подтвердить это.

Если компилятор говорит, что зависимость отсутствует, и человек, и агент видят одну и ту же ошибку.

Эта симметрия строит доверие.

## Почему Kora — интересный кейс { #kora-case-study }

Kora интересна не потому, что содержит специальный API для нейро-технологий.

Она интересна потому, что её ключевые инженерные решения необычно хорошо совпадают с агентной разработкой ПО.

Фреймворк строит граф приложения на этапе компиляции.

Он генерирует читаемый исходный код.

Он использует строгие типы Java/Kotlin.

Он предпочитает явные модули и конструкторы.

Он держит абстракции близко к JDBC, HTTP, Kafka, gRPC и другим знакомым технологиям.

Он намеренно снижает число конкурирующих стилей фреймворка.

Он запускает контексты приложения достаточно быстро, чтобы реалистичные тесты могли оставаться частью обычного цикла обратной связи.

Каждое из этих решений помогает инженерам.

Вместе они создают среду, где агент кодирования может работать с меньшим скрытым контекстом и большим количеством машино-проверяемых свидетельств.

## Заключение { #conclusion }

нейро-агентам кодирования не нужно, чтобы фреймворки становились проще в смысле снижения возможностей.

Им нужно, чтобы фреймворки становились более **читаемыми (legible)**.

Агент работает лучше всего, когда может видеть архитектуру, проверять свои предположения, изучать решения фреймворка и получать точную обратную связь, когда ошибается.

Фреймворки компиляции могут дать ровно такую среду.

Идеальный цикл прост:

```text
Агент пишет код
      ↓
компилятор проверяет
      ↓
сгенерированный код раскрывает поведение
      ↓
тесты запускаются быстро
      ↓
агент наблюдает результат
      ↓
агент исправляет
```

Kora усиливает каждый этап.

Явная архитектура говорит модели, откуда берутся компоненты и что от чего зависит.

Строгая типизация превращает изобретённые предположения в ошибки компилятора.

Сгенерированный исходный код выносит поведение фреймворка наружу, а не прячет его в состоянии выполнения.

Точная диагностика компилятора даёт детерминированные сигналы исправления.

Один рекомендуемый способ снижает число правдоподобных, но несогласованных путей реализации.

Тонкие абстракции позволяют модели переиспользовать то, что она уже знает о Java, Kotlin, JDBC, HTTP, Kafka, gRPC, SQL и OpenTelemetry.

Быстрый запуск держит полные компонентные и интеграционные тесты внутри обычного цикла итераций.

Ничто из этого не делает агента автоматически корректным.

Ему всё ещё нужны хорошие тесты.

Ему всё ещё нужны архитектурные ограничения.

Ему всё ещё нужно человеческое ревью для высокорисковых решений.

Он всё ещё может неправильно понимать бизнес-семантику.

Но он работает в среде, которая необычно хорошо превращает ошибки в свидетельства.

Это, возможно, самое важное свойство, которое может иметь фреймворк, поддерживающий нейро-технологии.

Будущее дружелюбной к нейро-технологиям бэкенд-разработки может зависеть не от специальных фреймворков, построенных вокруг LLM.

Оно может зависеть от фреймворков, которые уже практиковали более долговечную дисциплину:

```text
делай архитектуру явной
делай контракты строгими
делай ошибки ранними
делай сгенерированное поведение читаемым
делай цикл тестов быстрым
```

Эти принципы были хорошей инженерией ещё до того, как агенты кодирования стали практичными.

Агенты кодирования просто делают их ценность гораздо более заметной.
