# Стоимость первой отсутствующей интеграции: почему Kora не нужен стартер для всего { #cost-of-missing-integration }

**4 сентября 2026**

Экосистемы фреймворков часто сравнивают, подсчитывая интеграции.

У одного фреймворка есть стартер для конкретной базы данных, у другого — официальный модуль для облачной очереди, у третьего — обёртка вокруг SDK вендора, а у четвёртого — несколько конкурирующих
абстракций для одной и той же категории технологий. Получившееся сравнение выглядит объективным, потому что числа легко собирать: больше модулей, больше стартеров, больше поддерживаемых продуктов,
больше экосистема.

Эта метрика полезна, но она неполна.

Фреймворк не слаб потому, что у него нет готового стартера для каждой нишевой Java-библиотеки. Более важный вопрос — что происходит, когда появляется первая отсутствующая интеграция. Если подключение
неподдерживаемой библиотеки требует внутренних знаний фреймворка, недокументированных точек расширения, трюков с рефлексией, кастомных фаз бутстрапа или второго контейнера, скрытого внутри первого,
тогда отсутствующий стартер действительно дорог. Если интеграция — это просто обычный Java- или Kotlin-клиент, который можно сконфигурировать, сконструировать, поместить в граф приложения, наблюдать,
проверять на здоровье и завершать с помощью обычных примитивов фреймворка, тогда отсутствие выделенного стартера гораздо менее значимо.

Здесь у фреймворка Kora интересная история экосистемы.

Kora действительно предоставляет первоклассные модули для технологий, которые повторяются в производственных бэкенд-сервисах: HTTP-серверы и клиенты, OpenAPI, JDBC, Cassandra, Kafka, gRPC,
конфигурация, кеширование, отказоустойчивость, планирование, валидация, телеметрия, пробы и другая инфраструктура. Но его дизайн не зависит от идеи, что каждая технология в JVM-экосистеме должна
сначала быть переведена в специфичный для Kora DSL, прежде чем приложение сможет её использовать.

Вместо этого путь расширения намеренно мал.

```text
Нужна технология X
      ↓
Используйте её нативный Java/Kotlin-клиент
      ↓
Добавьте типизированную конфигурацию
      ↓
Раскройте клиент через @Module
      ↓
Подключите жизненный цикл / телеметрию / пробы, если требуется
      ↓
Инжектируйте и используйте обычным образом
```

Этот поток важен, потому что меняет то, что означает экосистема.

Экосистема — это не только набор интеграций, опубликованных мейнтейнерами фреймворка. Это также стоимость создания следующей интеграции самостоятельно.

Фреймворк с пятьюстами интеграциями, но дорогой моделью расширения всё равно может создавать серьёзное трение, когда требования приложения выходят за пределы каталога. Фреймворк с меньшей, но хорошо
нацеленной встроенной поверхностью может быть более гибким, если неподдерживаемые технологии естественно вписываются в ту же модель приложения, что и встроенные.

Поэтому полезная метрика — не просто:

```text
Сколько стартеров существует?
```

Она такова:

```text
Насколько дорог первый стартер, которого не существует?
```

Для Kora этот вопрос ведёт напрямую к его более широкой философии: он не пытается стать фреймворк-специфичной вселенной вокруг каждой технологии, которую может использовать бэкенд-инженер. Он пытается
сделать общий производственный путь первоклассным, сохраняя путь к необычной технологии коротким, явным и обычным.

## Скрытая стоимость за огромным каталогом стартеров { #hidden-cost }

Большой каталог интеграций — реальное преимущество. Было бы неправильно притворяться иначе.

Зрелый стартер может сэкономить часы или дни инженерной работы. Он может кодировать корректные значения по умолчанию, интегрироваться с конфигурацией, подключать метрики и трассировку, раскрывать
сигналы здоровья, координировать жизненный цикл, переводить исключения, поддерживать тестирование и обрабатывать тонкое поведение вендора, которое команды приложений не должны заново открывать.

Для общих и трудных технологий это чрезвычайно ценно.

Но количество интеграций — не свободная переменная. Каждая фреймворк-специфичная интеграция вводит ещё один слой, который кто-то должен проектировать, документировать, версионировать, тестировать,
выпускать и в конечном счёте мигрировать.

Типичный путь со множеством стартеров выглядит примерно так:

```text
Библиотека
   ↓
Стартер фреймворка
   ↓
Абстракция фреймворка
   ↓
Модель конфигурации фреймворка
   ↓
Приложение
```

Каждая стрелка может быть полезной. Каждая стрелка также может создавать семантическое расстояние от нижележащей технологии.

Предположим, у Java-библиотеки уже есть хороший клиентский API:

===! ":fontawesome-brands-java: `Java`"

    ```java
    var client = VendorClient.builder()
        .endpoint(endpoint)
        .credentials(credentials)
        .timeout(timeout)
        .build();
    ```

=== ":simple-kotlin: `Kotlin`"

    ```kotlin
    val client = VendorClient.builder()
        .endpoint(endpoint)
        .credentials(credentials)
        .timeout(timeout)
        .build()
    ```

Теперь представьте, что фреймворк решает, что приложения никогда не должны видеть этот API напрямую. Он вводит:

- собственную иерархию свойств;
- класс авто-конфигурации;
- интерфейс обёртки фреймворка;
- специфичную для фреймворка модель исключений;
- специфичный для фреймворка адаптер жизненного цикла;
- отдельный API настройки наблюдаемости;
- правила условной активации;
- логику совместимости версий;
- тестовые фикстуры;
- возможно, второй DSL для продвинутых опций.

Приложение может стать проще для счастливого пути, но вся система становится больше.

Разработчику теперь приходится понимать и нижележащую технологию, и интерпретацию её фреймворком.

Когда происходит что-то необычное, путь отладки может стать:

```text
конфигурация приложения
        ↓
привязка фреймворка
        ↓
условия стартера
        ↓
адаптер фреймворка
        ↓
обёртка фреймворка
        ↓
клиент вендора
        ↓
фактическое поведение сети
```

Это само по себе не плохо. Для технологий с трудной конфигурацией или опасными значениями по умолчанию обёртка может давать огромную ценность. Проблема появляется, когда это становится философией по
умолчанию для всего.

При достаточном масштабе экосистема фреймворка может стать фреймворком внутри фреймворка: сотни адаптеров, пересекающиеся конвенции, таблицы совместимости, правила жизненного цикла и диалекты
конфигурации, которые существуют в основном потому, что фреймворк решил опосредовать каждое отношение между кодом приложения и внешними библиотеками.

Kora выбирает более избирательный подход.

## Kora не должен владеть библиотекой, чтобы использовать её { #own-the-library }

Одно из самых важных свойств модели внедрения зависимостей Kora — компоненту не обязательно быть реализованным Kora.

Он просто должен стать компонентом в графе.

Это различие звучит очевидно, но архитектурно оно важно.

Предположим, приложению нужен SDK для продукта, о котором Kora никогда не слышал. Возможно, это поисковый аппарат, проприетарный движок правил, новое векторное хранилище, внутренний SDK компании,
нишевый брокер сообщений или специфичный для вендора API-клиент.

Если у библиотеки уже есть обычный Java-клиент, интеграция может начаться с этого клиента.

Специфичная для Kora часть — просто граница между построением и использованием.

Например:

===! ":fontawesome-brands-java: `Java`"

    ```java
    @Module
    public interface SearchVendorModule {

        default SearchVendorClient searchVendorClient(SearchVendorConfig config) {
            return SearchVendorClient.builder()
                .endpoint(config.endpoint())
                .apiKey(config.apiKey())
                .timeout(config.timeout())
                .build();
        }
    }
    ```

=== ":simple-kotlin: `Kotlin`"

    ```kotlin
    @Module
    interface SearchVendorModule {

        fun searchVendorClient(config: SearchVendorConfig): SearchVendorClient {
            return SearchVendorClient.builder()
                .endpoint(config.endpoint())
                .apiKey(config.apiKey())
                .timeout(config.timeout())
                .build()
        }
    }
    ```

С точки зрения остального приложения `SearchVendorClient` теперь — обычная зависимость графа.

===! ":fontawesome-brands-java: `Java`"

    ```java
    @Component
    public final class ProductSearchService {

        private final SearchVendorClient client;

        public ProductSearchService(SearchVendorClient client) {
            this.client = client;
        }
    }
    ```

=== ":simple-kotlin: `Kotlin`"

    ```kotlin
    @Component
    class ProductSearchService(private val client: SearchVendorClient)
    ```

Нет требования изобретать `KoraSearchVendorClient`, нет требования оборачивать каждый метод клиента и нет необходимости коду приложения извлекать клиент из какого-то общего реестра.

Граница интеграции — это фабричный метод.

Это даёт нам более простую топологию:

```text
Библиотека
   ↓
маленький интеграционный модуль
   ↓
Приложение
```

Важное слово — **маленький**.

Кастомный модуль может со временем стать изощрённым, но он может начаться почти без церемонии фреймворка. Интеграции нужно только добавить те заботы, которые приложение действительно требует.

## `@Module` — это основной механизм расширения { #module-extension }

В Kora `@Module` — это интерфейс, содержащий фабричные методы компонентов. Эти фабричные методы могут зависеть от других компонентов графа и возвращать новые компоненты в контейнер.

Этого достаточно, чтобы адаптировать очень большую часть Java-экосистемы.

Модуль может принимать:

```text
типизированную конфигурацию
учётные данные
HTTP-клиент
сериализатор
объекты телеметрии
исполнители
другие сервисы приложения
```

и возвращать:

```text
клиент вендора
пул соединений
объект сервиса SDK
реестр
адаптер
слушатель
воркер
```

Механизм намеренно близок к обычному построению.

Модуль — не плагинный рантайм. Не сервис-локатор. Не язык метаданных.

По сути, это типизированное объявление:

```text
Имея эти зависимости графа,
сконструируй этот компонент.
```

Например:

===! ":fontawesome-brands-java: `Java`"

    ```java
    @Module
    public interface AcmeModule {

        default AcmeClient acmeClient(
            AcmeConfig config,
            Credentials credentials) {

            return AcmeClient.builder()
                .url(config.url())
                .credentials(credentials)
                .build();
        }
    }
    ```

=== ":simple-kotlin: `Kotlin`"

    ```kotlin
    @Module
    interface AcmeModule {

        fun acmeClient(
            config: AcmeConfig,
            credentials: Credentials): AcmeClient {

            return AcmeClient.builder()
                .url(config.url())
                .credentials(credentials)
                .build()
        }
    }
    ```

Граф может валидировать эти зависимости на этапе компиляции. Если `AcmeConfig` или `Credentials` не могут быть предоставлены, приложение не ждёт запуска, чтобы обнаружить, что интеграция неполна.

Это делает кастомную интеграцию структурно похожей на встроенную.

Это важно, потому что механизмы расширения часто терпят неудачу, когда авторы фреймворков предоставляют чистую модель для официальных модулей, но совершенно другой запасной выход для пользовательских.
Официальная экосистема элегантна; кастомный код живёт в фабриках, реестрах, хуках бутстрапа или ручных держателях синглтонов.

Модель Kora не требует такого раскола.

Тот же граф, который держит компоненты фреймворка, может держать произвольный сторонний клиент.

## Конфигурация — не отдельный боковой канал { #configuration }

Сторонней интеграции нужна конфигурация, но это не требует изобретения новой системы конфигурации.

Kora может замапить секцию конфигурации в типизированный интерфейс с помощью `@ConfigSource`.

Например:

===! ":fontawesome-brands-java: `Java`"

    ```java
    @ConfigSource("clients.acme")
    public interface AcmeConfig {

        String endpoint();

        String apiKey();

        Duration timeout();
    }
    ```

=== ":simple-kotlin: `Kotlin`"

    ```kotlin
    @ConfigSource("clients.acme")
    interface AcmeConfig {

        fun endpoint(): String

        fun apiKey(): String

        fun timeout(): Duration
    }
    ```

Теперь сам объект конфигурации — часть графа.

Фабрика становится:

===! ":fontawesome-brands-java: `Java`"

    ```java
    @Module
    public interface AcmeModule {

        default AcmeClient acmeClient(AcmeConfig config) {
            return AcmeClient.builder()
                .endpoint(config.endpoint())
                .apiKey(config.apiKey())
                .timeout(config.timeout())
                .build();
        }
    }
    ```

=== ":simple-kotlin: `Kotlin`"

    ```kotlin
    @Module
    interface AcmeModule {

        fun acmeClient(config: AcmeConfig): AcmeClient {
            return AcmeClient.builder()
                .endpoint(config.endpoint())
                .apiKey(config.apiKey())
                .timeout(config.timeout())
                .build()
        }
    }
    ```

У этого есть несколько полезных свойств.

Конфигурация интеграции явна.

Конструктор клиента явен.

Связь между конфигурацией и клиентом явна.

Приложению не нужен специфичный для фреймворка слой перевода, который превращает конфигурацию Kora в другую абстракцию и затем, наконец, в нативный клиент.

Путь просто таков:

```text
application.conf
      ↓
AcmeConfig
      ↓
AcmeClient.builder(...)
      ↓
AcmeClient
```

Документация вендора остаётся полезной, потому что финальное построение всё ещё использует собственные концепции вендора.

Если документация вендора говорит:

> установите таймаут запроса в пять секунд

разработчику приложения не нужно сначала выяснять, как обёртка фреймворка переименовала это свойство.

Тонкая интеграция держит семантический разрыв малым.

## Почему применимость нативной документации — большое преимущество { #native-documentation }

Одна из скрытых затрат глубоких обёрток фреймворка — подмена документации.

Если фреймворк владеет абстракцией, разработчики больше не могут полагаться исключительно на документацию вышестоящей библиотеки. Им нужно понимать, какие части фреймворк раскрывает, какие меняет,
какие конфигурирует автоматически и какую версию нижележащей библиотеки модуль фреймворка сейчас поддерживает.

Реальный стек документации становится:

```text
документация вендора
        +
документация интеграции фреймворка
        +
документация конфигурации фреймворка
        +
заметки о совместимости
        +
возможно, заметки о миграции
```

Иногда эта сложность оправдана.

Но когда вышестоящий Java API уже хорош, адаптер может сохранить большую часть исходной ментальной модели.

Для тонкой интеграции Kora:

```text
Как настроить сжатие?
        ↓
Прочитайте документацию вендора.

Как создать клиент?
        ↓
Используйте builder API вендора.

Как поместить его в DI Kora?
        ↓
Одна фабрика @Module.

Как его закрыть?
        ↓
Используйте интеграцию жизненного цикла / AutoCloseable.

Как раскрыть готовность?
        ↓
Добавьте компонент пробы, если полезно.
```

Специфичные для интеграции знания малы и локальны.

Это создаёт ценное организационное свойство: команды могут нанимать или перемещать разработчиков на основе знаний Java-экосистемы, а не знаний специфичных для фреймворка адаптеров.

Разработчик, который уже понимает нативный клиент, большую часть пути уже прошёл к пониманию интеграции Kora.

## Жизненный цикл явный, а не скрытый в стартере { #lifecycle }

Построение — только часть производственной интеграции.

Многие клиенты владеют ресурсами:

- пулами соединений;
- циклами событий;
- файловыми дескрипторами;
- рабочими потоками;
- фоновыми обновлениями;
- постоянными каналами.

Их нужно запускать и, что важнее, корректно освобождать во время завершения работы.

У графа Kora есть модель жизненного цикла ровно для этого.

Если сторонний компонент сам реализует `AutoCloseable`, контейнер Kora может закрыть его, когда компонент освобождается. Если требуется более явное поведение инициализации и освобождения, интеграция
может использовать модель `Lifecycle` Kora или обернуть значение в `LifecycleWrapper`.

Концептуально:

```text
создать клиент
    ↓
инициализировать, если нужно
    ↓
приложение использует клиент
    ↓
начинается корректное завершение работы
    ↓
освободить / закрыть клиент
```

Например, интеграция может выглядеть так:

===! ":fontawesome-brands-java: `Java`"

    ```java
    @Module
    public interface VendorModule {

        default Wrapped<VendorClient> vendorClient(VendorConfig config) {
            var client = new VendorClient(config.endpoint());

            return new LifecycleWrapper<>(
                client,
                VendorClient::start,
                VendorClient::stop
            );
        }
    }
    ```

=== ":simple-kotlin: `Kotlin`"

    ```kotlin
    @Module
    interface VendorModule {

        fun vendorClient(config: VendorConfig): Wrapped<VendorClient> {
            val client = VendorClient(config.endpoint())

            return LifecycleWrapper(
                client,
                VendorClient::start,
                VendorClient::stop
            )
        }
    }
    ```

Остальное приложение по-прежнему инжектирует `VendorClient`.

Адаптер жизненного цикла остаётся на границе, где ему и место.

Это важный контраст с экосистемой со множеством стартеров, где поведение жизненного цикла может быть неявным внутри авто-конфигурации. Неявный жизненный цикл удобен, пока приложению не нужно понимать
порядок запуска, корректное завершение работы или почему ресурс остаётся живым.

Подход Kora поощряет автора интеграции делать владение видимым.

## Телеметрию можно добавить без замены клиента { #telemetry }

Наблюдаемость — ещё одна причина, по которой официальные интеграции могут быть ценны.

Производственный клиент в идеале должен предоставлять полезные метрики, трассировку и логирование. Официальный модуль фреймворка может стандартизировать эти заботы между приложениями.

Но отсутствие официальной интеграции не автоматически требует полной обёртки клиента.

Есть несколько способов инструментировать нативную библиотеку, сохраняя её нативной.

Если библиотека уже поддерживает OpenTelemetry, Micrometer, перехватчики, слушатели, фильтры запросов, хуки событий или колбэки метрик, интеграционный модуль может подключить их напрямую во время
построения клиента.

Концептуально:

```text
компоненты телеметрии Kora
          ↓
хуки нативной библиотеки
          ↓
нативный клиент
```

Например:

===! ":fontawesome-brands-java: `Java`"

    ```java
    @Module
    public interface VendorModule {

        default VendorClient vendorClient(
            VendorConfig config,
            OpenTelemetry openTelemetry,
            MeterRegistry meterRegistry) {

            return VendorClient.builder()
                .endpoint(config.endpoint())
                .tracer(openTelemetry.getTracer("vendor-client"))
                .metrics(meterRegistry)
                .build();
        }
    }
    ```

=== ":simple-kotlin: `Kotlin`"

    ```kotlin
    @Module
    interface VendorModule {

        fun vendorClient(
            config: VendorConfig,
            openTelemetry: OpenTelemetry,
            meterRegistry: MeterRegistry): VendorClient {

            return VendorClient.builder()
                .endpoint(config.endpoint())
                .tracer(openTelemetry.getTracer("vendor-client"))
                .metrics(meterRegistry)
                .build()
        }
    }
    ```

Если у API вендора нет полезных хуков, тогда адаптер или декоратор может быть оправдан.

Важный архитектурный принцип — инструментирование следует добавлять на самой узкой полезной границе. Фреймворку не нужно заменять весь клиентский API только для записи задержки.

Это часть того, что тонкие абстракции означают на практике: добавляйте интеграцию фреймворка там, где есть реальная ценность фреймворка, а не везде просто потому, что технология вошла в приложение.

## Здоровье и готовность — обычные компоненты графа { #health-readiness }

Операционная интеграция часто требует большего, чем телеметрия.

Сервису может понадобиться сообщать, что компонент готов, жив, инициализирован или временно недоступен. Модель проб Kora позволяет проверкам готовности и живости быть обычными компонентами.

Это означает, что неподдерживаемый клиент вендора может участвовать в той же операционной модели, что и встроенная инфраструктура.

Например:

===! ":fontawesome-brands-java: `Java`"

    ```java
    @Component
    public final class VendorReadinessProbe implements ReadinessProbe {

        private final VendorClient client;

        public VendorReadinessProbe(VendorClient client) {
            this.client = client;
        }

        @Override
        public ReadinessProbeFailure probe() {
            if (client.isReady()) {
                return null;
            }

            return new ReadinessProbeFailure("Vendor client is not ready");
        }
    }
    ```

=== ":simple-kotlin: `Kotlin`"

    ```kotlin
    @Component
    class VendorReadinessProbe(private val client: VendorClient) : ReadinessProbe {

        override fun probe(): ReadinessProbeFailure? {
            if (client.isReady) {
                return null
            }

            return ReadinessProbeFailure("Vendor client is not ready")
        }
    }
    ```

Kora агрегирует зарегистрированные пробы готовности.

Интеграции не нужен специальный «контракт стартера», чтобы стать видимой для Kubernetes или смоук-теста развёртывания. Ей нужно только предоставить компонент, использующий тот же операционный
контракт, что и остальное приложение.

Опять же, поверхность расширения остаётся малой:

```text
нативный клиент
   +
проба готовности Kora
   =
производственно-осознанная интеграция
```

Это повторяющийся паттерн во всей модели Kora.

Сторонней библиотеке не нужно превращаться в специфичную для Kora вселенную. Ей нужно несколько явных мостов в граф приложения.

## Интеграция может расти слоями { #integration-layers }

Один полезный способ понять этот подход — представить интеграцию, созревающую со временем.

Сначала приложению нужен только клиент.

### Этап 1: Построение { #stage-1 }

```text
конфигурация
     ↓
@Module
     ↓
нативный клиент
```

Затем приложение идёт в продакшен и нуждается в корректном завершении работы.

### Этап 2: Жизненный цикл { #stage-2 }

```text
конфигурация
     ↓
@Module
     ↓
нативный клиент
     ↓
Lifecycle / AutoCloseable
```

Затем эксплуатация хочет метрики и трассы.

### Этап 3: Наблюдаемость { #stage-3 }

```text
конфигурация
     ↓
@Module
     ↓
хуки телеметрии
     ↓
нативный клиент
```

Затем платформа развёртывания нуждается в готовности.

### Этап 4: Операционная интеграция { #stage-4 }

```text
конфигурация
     ↓
@Module
     ↓
нативный клиент
  ↙       ↘
телеметрия  проба готовности
```

Затем три других сервиса нуждаются в той же интеграции.

### Этап 5: Переиспользуемый модуль { #stage-5 }

```text
company-vendor-kora-module
        ↓
сервис A
сервис B
сервис C
сервис D
```

Ничто не требует, чтобы интеграция начиналась с Этапа 5.

Это важно, потому что большие экосистемы фреймворков часто поощряют команды думать в терминах «всё или ничего»: либо существует официальный стартер, либо кто-то должен построить что-то размером со
стартер, прежде чем технология будет ощущаться должным образом поддержанной.

Kora допускает гораздо более инкрементальный путь.

Стройте только ту поверхность интеграции, которая действительно нужна приложению.

## От локального адаптера к переиспользуемому модулю экосистемы { #reusable-module }

Если кастомная интеграция становится широко полезной, её можно выделить в собственный модуль.

Это может быть внутренняя библиотека компании:

```text
platform/
└── kora-vendor-client/
```

или интеграция с открытым исходным кодом.

Модуль может раскрывать обычный интерфейс модуля Kora, который приложения явно подключают.

Например:

===! ":fontawesome-brands-java: `Java`"

    ```java
    public interface VendorClientModule {

        default VendorClient vendorClient(
            VendorConfig config,
            VendorTelemetry telemetry) {
            // ...
        }
    }
    ```

=== ":simple-kotlin: `Kotlin`"

    ```kotlin
    interface VendorClientModule {

        fun vendorClient(
            config: VendorConfig,
            telemetry: VendorTelemetry): VendorClient {
            // ...
        }
    }
    ```

Затем приложение добавляет зависимость и подключает модуль к своему графу приложения.

Это создаёт другую модель роста экосистемы.

Вместо требования, чтобы каждая интеграция была благословлена и реализована централизованно командой фреймворка, знания интеграции могут двигаться наружу:

```text
один сервис
    ↓
локальный модуль
    ↓
общий внутренний модуль
    ↓
модуль сообщества / открытого исходного кода
```

Важное свойство в том, что модель приложения не меняется по мере созревания интеграции.

Локальная фабрика и переиспользуемый модуль используют одни и те же концепции DI.

Нет миграции из «режима ручной интеграции» в «режим интеграции фреймворка».

Эта непрерывность снижает стоимость экспериментов.

## Правильное сравнение — стоимость первой отсутствующей интеграции { #right-comparison }

Представьте два фреймворка.

У фреймворка A 400 официальных интеграций.

У фреймворка B — 80.

Соблазнительно немедленно заключить, что у фреймворка A более сильная экосистема.

Но предположим, приложению нужна интеграция номер 401.

Во фреймворке A отсутствующая технология требует:

```text
кастомный хук бутстрапа
кастомный биндер свойств
доступ к реестру бинов времени выполнения
абстракцию обёртки
ручную регистрацию жизненного цикла
кастомный контрибьютор здоровья
специфичный для фреймворка мост трассировки
```

Во фреймворке B отсутствующая технология требует:

```text
зависимость нативного клиента
типизированную конфигурацию
одну фабрику модуля
необязательную обёртку жизненного цикла
необязательную пробу
```

Какая экосистема сильнее для этого приложения?

Ответ больше не очевиден.

Лучшую метрику экосистемы можно записать так:

```text
Сила экосистемы
≈
покрытие общих потребностей
+
качество встроенных интеграций
+
стоимость неподдерживаемой интеграции
+
прозрачность модели расширения
+
потенциал переиспользования
```

Количество интеграций измеряет только первый член.

Стратегия Kora особенно интересна, потому что она пытается держать стоимость неподдерживаемой интеграции низкой.

Это не устраняет преимущество наличия официального модуля. Это меняет то, насколько разрушительно его отсутствие.

## Не каждая библиотека заслуживает абстракции фреймворка { #not-every-library }

В проектировании фреймворков есть тенденция предполагать, что интеграция равна абстракции.

Это не всегда так.

Иногда лучшая интеграция — просто построение плюс жизненный цикл.

Рассмотрим гипотетическую библиотеку обработки изображений:

===! ":fontawesome-brands-java: `Java`"

    ```java
    ImageProcessor processor = ImageProcessor.builder()
        .threads(4)
        .quality(HIGH)
        .build();
    ```

=== ":simple-kotlin: `Kotlin`"

    ```kotlin
    val processor = ImageProcessor.builder()
        .threads(4)
        .quality(HIGH)
        .build()
    ```

Что добавила бы обёртка фреймворка?

Если ответ в основном:

```text
переименовать методы builder
переместить ключи конфигурации
обернуть исключения
раскрыть те же операции под новыми именами
```

тогда абстракция может не создавать значимой ценности.

Она может только создавать второй словарь.

Полезная абстракция фреймворка обычно должна добавлять что-то существенное:

- валидацию на этапе компиляции;
- сгенерированный код;
- единую семантику телеметрии;
- транзакционное поведение;
- семантику повтора или отказоустойчивости;
- координацию жизненного цикла;
- интеграцию протокола;
- согласованный маппинг;
- существенное сокращение повторяющегося шаблонного кода;
- более безопасную или более простую доменную модель.

Если этого нет, использование нативной библиотеки напрямую может быть более чистой архитектурой.

Это различие помогает объяснить, почему философия тонких абстракций Kora важна. Фреймворк должен вмешиваться там, где может сделать систему материально лучше, а не просто потому, что может поставить
ещё один интерфейс перед библиотекой.

## Почему меньше обёрток может означать меньше семантического дрейфа { #semantic-drift }

Каждая обёртка создаёт возможность того, что абстракция и нижележащая технология будут эволюционировать с разной скоростью.

Вендор выпускает версию 7.

Она добавляет:

- новый режим аутентификации;
- новую политику повторов;
- новый алгоритм сжатия;
- новый асинхронный транспорт;
- новую опцию маршрутизации.

Если приложение использует нативный клиент, эти возможности доступны, когда обновляется зависимость клиента.

Если приложение использует абстракцию фреймворка, интеграции фреймворка может понадобиться намеренно раскрывать каждую возможность.

Путь версий становится:

```text
вендор выпускает фичу
        ↓
фреймворк обновляет зависимость
        ↓
фреймворк обновляет абстракцию
        ↓
фреймворк обновляет конфигурацию
        ↓
фреймворк выпускает интеграцию
        ↓
приложение обновляет модуль фреймворка
```

Опять же, эта задержка может быть оправдана, когда фреймворк предоставляет существенную дополнительную ценность. Но это всё равно стоимость.

Тонкая интеграция снижает эту поверхность совместимости.

Если модуль Kora в основном конструирует нативный клиент, приложение часто может двигаться с нативным клиентским API гораздо более напрямую.

Это может быть особенно ценно для SDK вендоров и быстро движущихся библиотек инфраструктуры.

## Встроенные модули всё ещё важны { #built-in-modules }

Было бы легко зайти слишком далеко с предыдущим аргументом.

Если кастомная интеграция проста, зачем фреймворку вообще поставлять какие-либо интеграции?

Потому что повторяющиеся проблемы инфраструктуры заслуживают общих решений.

Хороший официальный модуль может кодировать годы эксплуатационного опыта. Он может сделать телеметрию согласованной между сотнями сервисов. Он может обеспечить корректное завершение работы. Он может
генерировать повторяющийся код. Он может предоставлять валидацию на этапе компиляции. Он может стандартизировать обработку ошибок и облегчать тестирование.

Сам Kora явно следует этому принципу в своей базовой производственной поверхности.

Его встроенный стек покрывает категории, которые появляются снова и снова в бэкенд-системах:

```text
HTTP
Доступ к данным
Обмен сообщениями
Конфигурация
Отказоустойчивость
Телеметрия
Интеграции
```

Дело не в том, что «стартеры плохи».

Дело в том:

> **Фреймворк должен тратить свой бюджет абстракций там, где абстракция даёт долговечную ценность.**

Это естественно ведёт к более нюансированному различию между интеграциями, которые сильно выигрывают от первоклассной поддержки фреймворка, и интеграциями, где тонкий локальный адаптер вполне
адекватен.

## Где готовый модуль особенно ценен { #ready-made-module }

Есть категории, где «просто используйте нативный клиент» может недооценивать сложность.

### Безопасность { #security }

Интеграция безопасности редко бывает только построением объекта.

Аутентификация и авторизация часто взаимодействуют с:

- HTTP-маршрутизацией;
- контекстом запроса;
- идентичностями;
- маппингом ролей;
- валидацией токенов;
- ротацией ключей;
- ответами об ошибках;
- распространением;
- трассировкой;
- тестированием;
- оценкой политик.

Хорошо спроектированный модуль безопасности фреймворка может предотвращать тонкие и опасные несогласованности.

Это сильный аргумент в пользу первоклассной поддержки.

### Распределённая конфигурация { #distributed-configuration }

Клиент распределённой конфигурации может сначала выглядеть просто, но производственное поведение может включать:

- порядок бутстрапа;
- семантику наблюдения;
- переподключение;
- версионирование;
- динамическое обновление;
- согласованность;
- обновления графа;
- политику сбоев.

Официальная интеграция может координировать эти заботы с собственной конфигурацией фреймворка и жизненным циклом компонентов.

### Обнаружение сервисов { #service-discovery }

Обнаружение сервисов — это не просто клиент.

Оно влияет на:

- разрешение эндпоинтов;
- балансировку нагрузки;
- переиспользование соединений;
- состояние здоровья;
- повторы;
- обновление топологии;
- семантику DNS или реестра;
- конфигурацию клиента.

Зрелая интеграция фреймворка может дать реальную ценность, делая эти слои связными.

### Семантика распределённой трассировки { #distributed-tracing }

Добавить спана легко.

Правильно сделать распространение трасс, отношения родитель/ребёнок, семантические атрибуты, запись ошибок, поведение семплинга и границы контекста через целую технологию — труднее.

Официальная интеграция телеметрии может дать согласованность, которую маленький адаптер приложения может упустить.

### SDK вендоров со сложным поведением времени выполнения { #vendor-sdks }

Некоторые SDK вендоров скрывают:

- фоновые пулы потоков;
- мультиплексирование соединений;
- воркеры обновления;
- ротацию учётных данных;
- внутренние повторы;
- опрос топологии;
- ограничения завершения работы.

Хорошо сопровождаемый интеграционный модуль может кодировать корректный производственный жизненный цикл.

Эти случаи усиливают, а не противоречат модели Kora.

Фреймворк должен иметь сильные модули там, где проблема интеграции действительно сквозная или операционно тонкая.

Из этого просто не следует, что каждой используемой Java-библиотеке нужна специфичная для Kora обёртка, прежде чем она попадёт в приложение Kora.

## Не фреймворк для всего — правильный фреймворк для производственных бэкендов { #not-a-framework-for-everything }

Эта модель расширения раскрывает нечто большее о позиционировании Kora.

Kora, похоже, не пытается победить, максимизируя число галочек, которые можно поставить в таблице экосистем.

Его философия ближе к:

> **Не инструмент для каждой возможной ситуации. Отличный инструмент для чётко определённого класса проблем.**

Этот класс — производственные JVM-бэкенд-сервисы.

Фреймворк фокусирует свои сильнейшие первоклассные абстракции вокруг пути, который большая доля таких сервисов повторно нуждается.

```text
HTTP
 ↓
логика приложения
 ↓
доступ к данным / обмен сообщениями / RPC
 ↓
отказоустойчивость
 ↓
телеметрия
 ↓
производственный жизненный цикл
```

Это уже, чем «всё, что разработчики могут когда-либо построить на Java».

Эта узость может быть силой.

## Что обычно нужно производственному бэкенду { #production-backend }

Типичному сервису нужна некоторая комбинация:

- HTTP-сервера;
- HTTP-клиента;
- OpenAPI;
- JDBC или другого клиента базы данных;
- репозиториев и маппингов;
- Kafka или другой системы обмена сообщениями;
- gRPC;
- конфигурации;
- валидации;
- отказоустойчивости;
- кеширования;
- планирования;
- логирования;
- метрик;
- трассировки;
- готовности и живости;
- корректного завершения работы;
- поддержки тестирования.

Kora вкладывает первоклассные усилия в эти категории.

Домашняя страница фреймворка группирует его фокус похожим образом: HTTP, доступ к данным, обмен сообщениями, конфигурация, отказоустойчивость, телеметрия и интеграции. Его документация модулей
покрывает конкретную инфраструктуру, такую как Kafka, gRPC, S3, JDBC, Cassandra, планирование, кеш и наблюдаемость.

Было бы соблазнительно резюмировать это утверждением вроде:

> Kora покрывает 90 процентов типичных потребностей корпоративной бэкенд-интеграции.

Это может даже быть направленно разумным для многих организаций, но это не полезное инженерное утверждение без определённого образца нагрузки.

Что такое «типичное»?

Что считается интеграцией?

Какие отрасли?

Какие среды развёртывания?

Какие базы данных?

Какие облачные платформы?

Вместо опоры на произвольный процент более сильный аргумент наблюдаем:

> Kora намеренно покрывает категории, которые повторяются в производственных бэкенд-сервисах, и оставляет необычные технологические выборы доступными через ту же модель графа.

Это утверждение можно инспектировать напрямую.

## Фокус отличается от неполноты { #focus }

Есть важная разница между неполным фреймворком и сфокусированным фреймворком.

Неполный фреймворк говорит:

```text
Мы не поддерживаем X,
и нет чистого способа добавить X.
```

Сфокусированный фреймворк говорит:

```text
X не часть нашей встроенной поверхности,
но модель приложения позволяет вам интегрировать его напрямую.
```

Это очень разные ситуации.

Явная система модулей Kora, фабрики компонентов, маппинг конфигурации, модель жизненного цикла, пробы и композиция графа делают вторую модель правдоподобной.

Фреймворку не обязательно владеть технологией X.

Он должен предоставить достаточно поверхности интеграции, чтобы технология X стала хорошо ведущим себя участником приложения.

Вот почему фраза «маленькая экосистема» может вводить в заблуждение.

Фреймворк может иметь меньший **каталог**, не имея маленькой **достижимой экосистемы**.

Если практически любую обычную JVM-библиотеку можно сделать компонентом графа с несколькими строками фабричного кода, тогда практическая экосистема включает значительную часть самой Java-экосистемы.

Важный вопрос — сколько импеданса существует на границе.

## Java-экосистема уже является экосистемой { #java-ecosystem }

Java-фреймворки не существуют в вакууме.

У JVM уже есть зрелые библиотеки почти для каждой мыслимой категории инфраструктуры.

Существуют нативные клиенты и SDK для:

- баз данных;
- кешей;
- очередей;
- облачных сервисов;
- систем наблюдаемости;
- фича-флагов;
- поисковых движков;
- платёжных провайдеров;
- хранилищ секретов;
- провайдеров идентичности;
- объектных хранилищ;
- систем рабочих процессов;
- AI-сервисов;
- внутренних платформ компаний.

Фреймворк может ответить на эту экосистему двумя широкими способами.

### Модель A: Опосредование фреймворком { #model-a }

```text
Java-экосистема
      ↓
специфичные для фреймворка адаптеры
      ↓
специфичные для фреймворка абстракции
      ↓
приложение
```

Преимущество — единообразие.

Стоимость — ещё одна абстракция и слой совместимости.

### Модель B: Композиция фреймворком { #model-b }

```text
Java-экосистема
      ↓
явная композиция в граф приложения
      ↓
приложение
```

Преимущество — близость к нативной технологии.

Стоимость — приложению или платформенной команде иногда приходится писать маленький слой интеграции самостоятельно.

Kora сильно склоняется к композиции, когда первоклассная абстракция не оправдана.

Это разумная позиция для фреймворка, который делает акцент на прозрачности.

## Одна модель приложения для встроенных и кастомных компонентов { #one-application-model }

Особенно важное свойство — кастомным интеграциям не нужно жить вне обычной модели Kora.

Представьте сервис с:

```text
HTTP-сервером Kora
JDBC-репозиторием Kora
Kafka-консьюмером Kora
кастомным FeatureFlagClient
кастомным PaymentRiskClient
кастомным InternalSearchClient
```

Плохо спроектированная модель расширения фреймворка сделала бы эту архитектуру похожей на две системы:

```text
мир фреймворка
├── HTTP
├── JDBC
└── Kafka

ручной мир
├── фича-флаги
├── риск
└── поиск
```

Kora вместо этого может представить их в одном графе:

```text
Граф приложения
├── HTTP-сервер
├── репозитории
├── Kafka-консьюмеры
├── FeatureFlagClient
├── PaymentRiskClient
├── InternalSearchClient
├── телеметрия
├── пробы
└── жизненный цикл
```

Разница важна операционно.

Кастомные клиенты могут участвовать в порядке зависимостей.

Они могут участвовать в жизненном цикле.

Они могут потреблять типизированную конфигурацию.

Они могут быть зависимостями других компонентов.

Они могут раскрывать пробы.

Их можно декорировать или инструментировать.

Их можно заменять в тестах.

Они не второсортны просто потому, что Kora их не опубликовал.

## Фреймворк не должен заменять промежуточное ПО { #middleware }

Ещё одна полезная граница в философии Kora — различие между фреймворком и инфраструктурой.

Фреймворк должен помогать приложению использовать Kafka.

Он не должен пытаться стать Kafka.

Он должен помогать приложению использовать базу данных.

Он не должен изобретать совершенно новую семантику базы данных, если абстракция не зарабатывает свою сложность.

Он должен помогать приложению вызывать HTTP-сервис.

Ему не нужно заменять концепции HTTP проприетарной сетевой моделью.

Это кажется очевидным, но фреймворки могут постепенно накапливать достаточно абстракции, чтобы нижележащие технологии стали деталями реализации, которые разработчиков отговаривают понимать.

Это может делать простые случаи использования элегантными, а необычное поведение трудным для отладки.

Философия тонких абстракций Kora держит нижележащую технологию видимой.

JDBC остаётся узнаваемо JDBC.

Kafka остаётся узнаваемо Kafka.

gRPC остаётся узнаваемо gRPC.

Кастомная библиотека может оставаться узнаваемо собой.

Это снижает семантическое расстояние между производственным поведением и кодом, который инспектируют разработчики.

## Меньше моделей программирования снижают поверхность интеграции { #fewer-programming-models }

Широта также дорога, когда фреймворк поддерживает несколько конкурирующих способов решения одного класса проблем.

Например, фреймворк может поддерживать:

```text
блокирующий HTTP
реактивный HTTP
корутинный HTTP

JDBC
реактивный SQL
ORM
реактивный ORM

несколько стилей DI
несколько стилей конфигурации
несколько клиентских абстракций
```

Каждая дополнительная модель программирования умножает обязательства интеграции.

Интеграции базы данных может понадобиться блокирующий и реактивный варианты.

Телеметрии нужно распространяться через все модели выполнения.

Безопасности нужны адаптеры для каждой модели.

Транзакции могут вести себя по-разному.

Поддержка тестирования расширяется.

Документация ветвится.

Семантика AOP ветвится.

Kora 2 намеренно сужает эту поверхность, используя обычные синхронные сигнатуры Java и Kotlin на виртуальных потоках, а не поддерживая параллельные реактивные и suspend-контракты во всех модулях.

Этот выбор релевантен размеру экосистемы.

Сфокусированная модель программирования означает, что новым интеграциям нужно поддерживать меньше измерений фреймворка.

Кастомному клиенту не нужно:

```text
блокирующий адаптер
реактивный адаптер
корутинный адаптер
мост контекста между всеми тремя
```

Он часто может быть просто обычным синхронным компонентом.

Сокращение числа моделей программирования — поэтому не только решение о читаемости. Оно снижает комбинаторную стоимость роста экосистемы.

## Компромисс швейцарского армейского ножа { #swiss-army-knife }

Классическая метафора полезна.

Швейцарский армейский нож побеждает, потому что содержит много инструментов.

Если вам нужны лезвие, отвёртка, открывалка для бутылок, ножницы, напильник, штопор, пинцет и пила, удобно иметь их все в одном предмете.

Но у метафоры есть и другая сторона.

Каждый встроенный инструмент должен соответствовать физическим ограничениям ножа. Специализированная отвёртка может быть лучше для серьёзного завинчивания. Выделенная пила лучше для серьёзной резки.
Преимущество ножа — доступность и широта, а не обязательно оптимальный дизайн для каждой задачи.

Экосистемы фреймворков имеют похожее напряжение.

Фреймворк с приоритетом широты склоняется к:

```text
больше интеграций
больше обёрток
больше моделей конфигурации
больше поверхности совместимости
больше пересекающихся путей
```

Фреймворк с приоритетом фокуса может вместо этого стремиться к:

```text
общие производственные потребности
        ↓
тщательно спроектированные первоклассные модули
        ↓
тонкие абстракции
        ↓
простые кастомные интеграции
```

Это не доказывает, что сфокусированный фреймворк всегда лучше.

Это проясняет обмен.

Kora делает конкретную ставку: бэкенд-команды выигрывают больше от оптимизированного, связного ядра плюс дешёвой расширяемости, чем от попытки обернуть каждую возможную технологию.

## Бюджет абстракций { #abstraction-budget }

Полезный способ обсуждать этот дизайн — идея **бюджета абстракций**.

Каждая абстракция что-то стоит:

```text
концепции для изучения
документация для сопровождения
совместимость для сохранения
ошибки для исправления
версии для координации
поведение для отладки
пути миграции для поддержки
```

Фреймворк должен тратить этот бюджет там, где получает достаточную отдачу.

Например, сгенерированные репозитории могут оправдать абстракцию, потому что устраняют повторяющийся маппинг и сантехнику запросов, сохраняя явный SQL.

Декларативные HTTP-клиенты могут оправдать абстракцию, потому что фреймворк может генерировать построение запросов, маппинг, телеметрию и обработку ошибок.

Аннотации отказоустойчивости могут оправдать абстракцию, потому что политики повтора, таймаута, circuit breaker и fallback — сквозные заботы, которые выигрывают от согласованной модели.

Обёртка один-в-один вокруг вполне пригодного клиента вендора может не оправдать ту же стоимость.

Результат — фреймворк, чья поверхность растёт согласно рычагу, а не согласно полноте каталога.

Это более дисциплинированная стратегия экосистемы.

## Тест хорошей кастомной интеграции { #test-of-integration }

Как мы узнаём, действительно ли хорош путь кастомной интеграции?

Полезный тест — может ли разработчик объяснить всю интеграцию на одном экране.

Для обычного клиента ответ часто должен быть близок к:

```text
1. Добавьте зависимость.
2. Определите типизированную конфигурацию.
3. Сконструируйте клиент в @Module.
4. Добавьте поведение жизненного цикла, если клиент владеет ресурсами.
5. Подключите телеметрию через нативные хуки.
6. Добавьте готовность/живость, только если это операционно значимо.
7. Инжектируйте клиент.
```

Если этого достаточно, отсутствующий стартер — не крупный недостаток фреймворка.

Если вместо этого процесс требует изучения внутренних API компилятора, мутации контейнера, рефлексивной регистрации, недокументированных правил порядка или приватных классов фреймворка, тогда
экосистема действительно труднее для расширения, чем предполагает её каталог.

Различие практично и измеримо.

## Конкретный пример: интеграция неподдерживаемого клиента { #concrete-example }

Представьте, что у Kora нет официальной интеграции для гипотетического `NimbusClient`.

Нативный Java API:

===! ":fontawesome-brands-java: `Java`"

    ```java
    NimbusClient.builder()
        .endpoint(...)
        .token(...)
        .connectTimeout(...)
        .build();
    ```

=== ":simple-kotlin: `Kotlin`"

    ```kotlin
    NimbusClient.builder()
        .endpoint(...)
        .token(...)
        .connectTimeout(...)
        .build()
    ```

Маленькая интеграция Kora может начаться с типизированной конфигурации:

===! ":fontawesome-brands-java: `Java`"

    ```java
    @ConfigSource("clients.nimbus")
    public interface NimbusConfig {

        String endpoint();

        String token();

        Duration connectTimeout();
    }
    ```

=== ":simple-kotlin: `Kotlin`"

    ```kotlin
    @ConfigSource("clients.nimbus")
    interface NimbusConfig {

        fun endpoint(): String

        fun token(): String

        fun connectTimeout(): Duration
    }
    ```

Затем построение:

===! ":fontawesome-brands-java: `Java`"

    ```java
    @Module
    public interface NimbusModule {

        default NimbusClient nimbusClient(NimbusConfig config) {
            return NimbusClient.builder()
                .endpoint(config.endpoint())
                .token(config.token())
                .connectTimeout(config.connectTimeout())
                .build();
        }
    }
    ```

=== ":simple-kotlin: `Kotlin`"

    ```kotlin
    @Module
    interface NimbusModule {

        fun nimbusClient(config: NimbusConfig): NimbusClient {
            return NimbusClient.builder()
                .endpoint(config.endpoint())
                .token(config.token())
                .connectTimeout(config.connectTimeout())
                .build()
        }
    }
    ```

Теперь код приложения использует его:

===! ":fontawesome-brands-java: `Java`"

    ```java
    @Component
    public final class RecommendationService {

        private final NimbusClient nimbus;

        public RecommendationService(NimbusClient nimbus) {
            this.nimbus = nimbus;
        }
    }
    ```

=== ":simple-kotlin: `Kotlin`"

    ```kotlin
    @Component
    class RecommendationService(private val nimbus: NimbusClient)
    ```

Если клиент `AutoCloseable`, обычное освобождение графа может его закрыть.

Если ему нужен явный запуск:

===! ":fontawesome-brands-java: `Java`"

    ```java
    default Wrapped<NimbusClient> nimbusClient(NimbusConfig config) {
        var client = createNimbus(config);

        return new LifecycleWrapper<>(
            client,
            NimbusClient::start,
            NimbusClient::stop
        );
    }
    ```

=== ":simple-kotlin: `Kotlin`"

    ```kotlin
    fun nimbusClient(config: NimbusConfig): Wrapped<NimbusClient> {
        val client = createNimbus(config)

        return LifecycleWrapper(
            client,
            NimbusClient::start,
            NimbusClient::stop
        )
    }
    ```

Если важна готовность:

===! ":fontawesome-brands-java: `Java`"

    ```java
    @Component
    public final class NimbusReadinessProbe implements ReadinessProbe {

        private final NimbusClient client;

        public NimbusReadinessProbe(NimbusClient client) {
            this.client = client;
        }

        @Override
        public ReadinessProbeFailure probe() {
            return client.ready()
                ? null
                : new ReadinessProbeFailure("Nimbus is not ready");
        }
    }
    ```

=== ":simple-kotlin: `Kotlin`"

    ```kotlin
    @Component
    class NimbusReadinessProbe(private val client: NimbusClient) : ReadinessProbe {

        override fun probe(): ReadinessProbeFailure? {
            return if (client.ready()) {
                null
            } else {
                ReadinessProbeFailure("Nimbus is not ready")
            }
        }
    }
    ```

Если важна трассировка, используйте нативный перехватчик Nimbus или хук запроса при создании клиента.

Это уже производственно-качественный паттерн интеграции.

Стартер не требовался.

## Что должно стать общим модулем? { #shared-module }

Не каждую локальную интеграцию следует публиковать.

Полезное правило — выделять её, когда интеграция содержит знания, а не просто связывание.

Например, модуль — хороший кандидат на переиспользование, когда он стандартизирует:

- требуемые таймауты;
- аутентификацию;
- повторы;
- семантику трассировки;
- метрики;
- пулинг соединений;
- корректное завершение работы;
- правила готовности;
- схему конфигурации;
- общефирменные значения по умолчанию;
- тестовые фикстуры.

В этот момент интеграция больше не просто:

```text
new Client(config)
```

Она содержит операционную политику.

Эта политика заслуживает одной реализации.

Затем модуль может потребляться каждым сервисом, которому нужна технология.

Так экосистема растёт органически из производственного опыта, а не из спекулятивных обёрток.

## Внутренние экосистемы тоже важны { #internal-ecosystems }

Публичные Maven-артефакты — только один вид экосистемы.

У крупных компаний часто больше релевантных внутренних интеграций, чем публичных.

У них могут быть внутренние библиотеки для:

- идентичности;
- обнаружения сервисов;
- секретов;
- фича-флагов;
- внутреннего RPC;
- аудита логирования;
- комплаенса;
- метаданных развёртывания;
- специфичной для компании телеметрии.

Фреймворк, чья модель кастомных модулей проста, облегчает построение внутренней платформенной экосистемы.

Организация может создать:

```text
company-kora-security
company-kora-telemetry
company-kora-feature-flags
company-kora-service-discovery
company-kora-audit
```

Эти модули могут оставаться тонкими и специфичными для потребностей организации.

Фреймворку не нужно предугадывать каждую специфичную для компании систему инфраструктуры.

Ему нужна только модель приложения, к которой эти интеграции могут чисто присоединиться.

Это может быть важнее в корпоративных средах, чем сырое количество публичных стартеров.

## Явная интеграция также улучшает владение { #ownership }

Есть ещё одно тонкое преимущество локальных модулей: владение очевидно.

Предположим, приложение включает:

===! ":fontawesome-brands-java: `Java`"

    ```java
    @Module
    public interface FraudProviderModule { ...
    }
    ```

=== ":simple-kotlin: `Kotlin`"

    ```kotlin
    @Module
    interface FraudProviderModule { ...
    }
    ```

Разработчик может найти:

- как создаётся клиент;
- какую конфигурацию он использует;
- какая телеметрия подключена;
- как он завершает работу;
- какая проба представляет готовность.

Операционный контракт зависимости расположен в одном месте.

В высокоавтоматизированной модели стартеров это поведение может быть распределено по:

- зависимости;
- авто-конфигурации;
- переменным окружения;
- условным бинам;
- транзитивной конфигурации;
- скрытым значениям по умолчанию;
- специфичному для фреймворка инструментированию.

Автоматизация удобна, но явное локальное владение может сделать необычные производственные сбои легче для анализа.

Более широкий акцент Kora на сгенерированном и инспектируемом коде естественно сочетается с этим стилем интеграции.

## Фреймворк должен делать запасной выход лучше, чем счастливый путь в других фреймворках { #escape-hatch }

Зрелый фреймворк оценивается не только по своему идеальному пути.

Реальным системам в конце концов нужно что-то необычное.

Проприетарный SDK.

Старая клиентская библиотека.

Внутренний протокол.

Библиотека, выпущенная в прошлом месяце.

Вендор, чей официальный адаптер фреймворка отстаёт.

Миграция, где две технологии временно сосуществуют.

Качество запасного выхода становится важным.

В Kora запасной выход — на самом деле не запасной выход.

Это обычная композиция графа.

Это, пожалуй, одно из сильнейших свойств, которое может иметь фреймворк.

Необычный случай всё равно использует:

```text
типизированную конфигурацию
фабрики
DI
жизненный цикл
телеметрию
пробы
тестирование
```

Он остаётся внутри архитектуры приложения, а не обходит её.

## Под что Kora оптимизирует { #optimizing-for }

Собирая всё вместе, видимая цель Kora — не максимальная теоретическая применимость.

Это более узкая задача оптимизации:

```text
Производственный JVM-бэкенд
        ↓
общая инфраструктура
        ↓
валидируемый на этапе компиляции граф
        ↓
сгенерированный код
        ↓
тонкие интеграции
        ↓
синхронная модель на виртуальных потоках
        ↓
наблюдаемость и жизненный цикл
```

Фреймворк пытается сделать этот путь исключительно прямым.

Этот фокус имеет последствия.

Это означает, что у Kora может не всегда быть самый длинный список интеграций.

Это означает, что какой-то нишевой технологии может понадобиться маленький модуль, принадлежащий приложению.

Это означает, что командам иногда нужно понимать нативный Java-клиент, а не только обёртку Kora.

Но это приемлемые затраты, если фреймворк держит границу интеграции простой.

Выигрыш — меньше фреймворк-специфичных концепций между разработчиком и технологией, которая фактически работает в продакшене.

## Лучший способ оценивать экосистемы фреймворков { #evaluate-ecosystems }

При оценке бэкенд-фреймворка считайте интеграции, если хотите, — но не останавливайтесь на этом.

Задайте более широкий набор вопросов.

Сколько наших общих технологий имеют зрелую первоклассную поддержку?

Насколько хороши эти интеграции операционно?

Можем ли мы использовать нативный Java-клиент, когда официального модуля нет?

Сколько концепций фреймворка требуется, чтобы раскрыть этот клиент для DI?

Можно ли типизировать конфигурацию?

Можно ли управлять жизненным циклом ресурсов?

Может ли клиент участвовать в трассировке и метриках?

Может ли он раскрывать готовность?

Можем ли мы переопределить или настроить компоненты фреймворка?

Можно ли позже выделить локальную интеграцию в переиспользуемый модуль?

Могут ли разработчики продолжать использовать документацию вышестоящей библиотеки?

Заставляет ли фреймворк нас оборачивать нативный API?

Сколько специфичной для фреймворка поверхности совместимости мы создаём?

Эти вопросы дают гораздо более реалистичную картину, чем подсчёт имён стартеров.

## Реальная экосистема — это фреймворк плюс JVM { #real-ecosystem }

Эффективная экосистема Kora — не только:

```text
официальные модули Kora
```

Она ближе к:

```text
официальные модули Kora
        +
нативные JVM-библиотеки
        +
маленькие интеграционные модули Kora
        +
внутренние переиспользуемые модули
        +
интеграции сообщества
```

Это гораздо большая достижимая поверхность.

Ключ в том, что мост между этими слоями остаётся дешёвым.

Если бы мост был дорогим, различие было бы теоретическим.

Поскольку `@Module`, типизированная конфигурация, жизненный цикл компонентов, пробы и явный DI — это механизмы общего назначения, мост часто может оставаться лишь небольшим объёмом кода.

## Заключение { #conclusion }

Экосистему фреймворка не следует оценивать только по числу технологий, для которых кто-то уже опубликовал стартер.

Это число измеряет широту, и широта важна. Зрелые первоклассные интеграции ценны, потому что могут кодировать хорошие значения по умолчанию, наблюдаемость, жизненный цикл, тестирование, семантику
сбоев и годы производственного опыта.

Но широта — только половина истории экосистемы.

Другая половина начинается там, где заканчивается каталог.

Когда приложению нужна технология, которую фреймворк официально не поддерживает, становится ли фреймворк препятствием? Нужны ли команде внутренние API расширения, сложные хуки бутстрапа, иерархии
обёрток или отдельный механизм DI?

Или команда может использовать Java- или Kotlin-библиотеку напрямую, сконструировать её с типизированной конфигурацией, раскрыть её через маленький модуль, подключить жизненный цикл и телеметрию,
добавить пробу там, где полезно, и инжектировать её как любой другой компонент?

Kora спроектирован вокруг второй модели.

Его встроенные модули фокусируются на общей производственной бэкенд-поверхности: HTTP, доступ к данным, обмен сообщениями, RPC, конфигурация, отказоустойчивость, телеметрия, кеширование, планирование,
валидация и операционный жизненный цикл. Ему не нужно оборачивать каждый возможный SDK или библиотеку, потому что его граф приложения открыт для обычных компонентов.

Это даёт полезное различие:

```text
Отсутствующая официальная интеграция
        ≠
неподдерживаемая технология
```

Часто это просто означает:

```text
нативная библиотека
      +
маленький явный интеграционный модуль
```

Если интеграция становится важной в нескольких сервисах, этот модуль может созреть в общую инфраструктуру. Та же модель работает на обеих стадиях.

Вот почему силу экосистемы следует измерять не только тем, сколько интеграций уже существует, но и тем, насколько дёшево и прозрачно разработчики могут создать следующую.

Kora не пытается владеть каждой технологией, которую вы используете. Он пытается сделать использование этих технологий внутри графа приложения прямолинейным.

И этот принцип также объясняет его более широкую идентичность.

Kora не пытается быть фреймворком для каждого возможного приложения, модели программирования, SDK вендора, продукта промежуточного ПО или стиля абстракции. Он фокусируется на чётко определённом классе
работы: производственных Java- и Kotlin-бэкенд-сервисах.

Швейцарский армейский нож побеждает, имея инструмент почти для всего.

Kora выбирает противоположный подход: меньше тщательно выбранных инструментов, оптимизированных под задачи, которые бэкенд-инженеры выполняют повторно, плюс простой и явный способ добавить следующий
инструмент, когда он действительно нужен.

Это не отсутствие экосистемы.

Это другое определение её.
