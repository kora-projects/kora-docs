# Kora Skill как недостающий слой между документацией и ИИ-агентами { #kora-skill-as-missing }

**18 августа 2026**

Документация фреймворка писалась для людей.

Исходный код писался для компиляторов, сопровождающих и инженеров, которые умеют ориентироваться в кодовой базе.

Примеры писались, чтобы продемонстрировать конкретное применение.

Ни один из этих артефактов изначально не был задуман для ответа на новый вопрос, который становится всё более важным: **как автономный агент для написания кода должен понять фреймворк достаточно
хорошо, чтобы вносить корректные изменения, не реконструируя его соглашения по фрагментам публичных знаний из интернета?**

Именно этот пробел и делает официальный скилл фреймворка интересным. У Kora уже есть набор свойств, которые делают её необычайно дружелюбной к агентам для написания кода. Её граф приложения явный.
Внедрение зависимостей проверяется на этапе компиляции. HTTP-обработчики, репозитории, мапперы и AOP-инфраструктура генерируются как обычный исходный код. Диагностика компилятора даёт
детерминированную обратную связь. Фреймворк отдаёт предпочтение одному рекомендованному решению для каждой задачи и остаётся близок к Java, Kotlin, JDBC, Kafka, gRPC, HTTP и другим знакомым
технологиям. Текущая посадочная страница Kora v2 заходит настолько далеко, что делает разработку с помощью ИИ первоклассной частью позиционирования фреймворка: агент пишет код, компилятор отвечает,
агент изучает результат, быстро тестирует, а…

Но одной лишь прозрачности фреймворка недостаточно, чтобы решить все проблемы ИИ. Модель общего назначения может отлично знать Java и при этом неправильно понимать Kora. Она могла видеть более старые
API Kora в публичных репозиториях. Она может заимствовать соглашение Spring, потому что форма выглядит знакомой. Она может сгенерировать аннотацию, которая существует в другом DI-фреймворке, но не в
Kora. Она может понимать, что такое репозиторий, концептуально, но выбирать неканоническую реализацию Kora. Она может видеть сгенерированный код и неправильно интерпретировать, предназначен ли этот
код для редактирования. Она может помнить поведение Kora 1.x, изменяя проект на Kora 2.x.

Недостающий слой — это не больше исходного кода. Это **авторитетное руководство, ориентированное на машины**.

Именно эту роль и выполняет Kora Skill.

> **Документация писалась для людей. Исходный код писался для компиляторов и инженеров. Kora Skill добавляет недостающий машинно-ориентированный слой: официальное, курируемое описание того, как
фреймворк должны понимать и использовать ИИ-агенты для написания кода.**

Это не просто ещё один README с парой подсказок для промптов. Хорошо продуманный официальный скилл может закодировать текущее мировоззрение фреймворка: каноническую модель программирования,
предпочтительный путь для типовых задач, смысл сгенерированного кода, правильную последовательность отладки, правила, зависящие от версии, границы миграции и то, чего агент не должен *выводить* по
аналогии со внешне похожими фреймворками.

В результате получается новая композиция:

```text
Общие знания ИИ
        +
Официальный Kora Skill
        +
Текущий проект
        ↓
Агент, разбирающийся в Kora
```

Эта модель имеет последствия, выходящие далеко за пределы Kora. Она предполагает, что фреймворкам больше не нужно ждать, пока будущие поколения больших языковых моделей впитают их API косвенно из
публичного кода и архивов форумов. Они могут поставлять свой собственный актуальный опыт в виде версионируемого артефакта.

## Проблема: общие знания ИИ широки, но не каноничны { #problem-general-ai-knowledge }

Современная модель для написания кода уже много знает о бэкенд-инженерии. Она может рассуждать о конструкторах, интерфейсах, дженериках, HTTP, JDBC, SQL, Kafka, gRPC, повторных попытках, транзакциях,
OpenTelemetry и системах сборки. Она может также понимать общую идею внедрения зависимостей и генерации кода на этапе компиляции. Эти широкие знания чрезвычайно полезны для Kora, потому что фреймворк
намеренно остаётся близок к этим концепциям.

Проблема в том, что общие знания вероятностны, а не авторитетны. Модель выучила паттерны из множества фреймворков и множества версий. Когда контекст неполон, она выполняет достраивание паттернов.
Обычно это преимущество, но именно в коде фреймворка правдоподобное достраивание паттернов может стать опасным.

Агент видит:

===! ":fontawesome-brands-java: `Java`"

    ```java
    @Component
    public final class PaymentService {
        ...
    }
    ```

=== ":simple-kotlin: `Kotlin`"

    ```kotlin
    @Component
    class PaymentService {
        ...
    }
    ```

и может вывести поведение из Micronaut. Он видит контроллер HTTP на основе аннотаций и может дополнить его по соглашениям Spring. Он видит интерфейс репозитория и может предположить правила именования
Spring Data. Он видит AOP-аннотации и может импортировать допущения о прокси времени выполнения, которые не применимы к генерируемой модели подклассов Kora. Сгенерированный код всё же может
скомпилироваться достаточно плохо, чтобы выявить ошибку, но агент уже потратил итерацию.

Скилл, специфичный для фреймворка, может уменьшить эту неоднозначность ещё до первой правки.

## Выдуманные API фреймворка часто выглядят правдоподобно { #hallucinated-framework-apis-often }

Одна из самых раздражающих ошибок ИИ — это не откровенно абсурдный код. Это код, который выглядит ровно так, как что-то, что *должно существовать*.

Модель может выдумать:

===! ":fontawesome-brands-java: `Java`"

    ```java
    @KoraService
    ```

=== ":simple-kotlin: `Kotlin`"

    ```kotlin
    @KoraService
    ```

потому что у многих фреймворков есть стереотип сервиса. Она может сгенерировать:

===! ":fontawesome-brands-java: `Java`"

    ```java
    @Autowired
    ```

=== ":simple-kotlin: `Kotlin`"

    ```kotlin
    @Autowired
    ```

потому что эта аннотация чрезвычайно широко представлена в обучающих данных Java. Она может ожидать соглашение о репозиториях, принадлежащее Spring Data, использовать реактивный тип возвращаемого
значения, унаследованный от старой модели программирования, или выбрать устаревший API Kora, который часто встречался в публичном коде до крупного изменения версии.

Результат выглядит разумно. Именно поэтому он опасен. Модель не ошибается в Java. Она ошибается в **идентичности фреймворка**.

Официальный скилл даёт агенту более сильный источник идентичности фреймворка, чем статистическое знакомство.

## Скилл меняет иерархию источников истины { #skill-changes-source-truth }

Без руководства, специфичного для фреймворка, агент может неявно ранжировать информацию так:

```text
предварительные знания модели
        ↓
локальные примеры кода
        ↓
случайное извлечение документации
        ↓
обратная связь компилятора
```

Это может работать, но предварительные знания модели часто загрязнены соседними фреймворками и старыми версиями.

Скилл позволяет фреймворку инвертировать иерархию:

```text
официальный Kora Skill
        ↓
текущая официальная документация / примеры
        ↓
исходный код текущего проекта
        ↓
сгенерированный исходный код
        ↓
диагностика компилятора и тесты
        ↓
предварительные знания модели как фон
```

Модель по-прежнему использует то, что знает о Java, SQL, HTTP, Kafka и распределённых системах. Но допущения, специфичные для фреймворка, теперь привязаны к официальному актуальному контексту. Это
глубокое улучшение надёжности.

## Официальный скилл может частично заменить размер корпуса авторитетным контекстом { #official-skill-partially-replace }

У старых фреймворков есть историческое преимущество в системах ИИ. У них десятилетия публичного кода, книг, учебников, ответов на Stack Overflow, постов в блогах, материалов конференций и примеров на
GitHub. Языковые модели видели их повсюду.

У более молодого фреймворка представленность меньше. Исторически это означало, что модель просто знала о нём меньше.

Возникающая модель скиллов ослабляет эту зависимость. Меньший фреймворк может объединить:

```text
качественную документацию
+
запускаемые примеры
+
официальный исходный код
+
версионируемый скилл агента
```

и предоставить агенту ровно тот контекст, который ему нужен в момент выполнения.

Это приводит к сильному общему принципу:

> **Официальный скилл может частично заменить размер корпуса авторитетным контекстом.**

Он не устраняет ценность большой экосистемы. Производственный опыт, интеграции третьих сторон, независимые отчёты об ошибках и публичные знания по-прежнему важны. Но для узкого вопроса «может ли
ИИ-агент правильно использовать фреймворк сегодня?» актуальный авторитетный контекст может значить больше, чем то, сколько постов в блогах 2018 года модель впитала во время предобучения.

## Документация и скиллы решают разные задачи { #documentation-skills-solve-different }

Скилл не должен заменять документацию. Это различие принципиально.

Справочная документация отвечает на такие вопросы:

```text
Что означает @KoraApp?
Что делает @Component?
Как работает @Module?
Что такое ValueOf<T>?
Что такое All<T>?
Какие свойства конфигурации существуют?
```

Читатель сам решает, как интерпретировать и комбинировать эти факты.

Скилл агента может пойти дальше, потому что его аудитория — не человек, ищущий информацию. Его аудитория — машина, которая должна решить, какое действие предпринять дальше.

Скилл может кодировать рабочие правила:

```text
Предпочитай этот паттерн.
Не используй этот более старый паттерн.
Ищи сгенерированный исходный код здесь.
Компилируй, прежде чем строить догадки о поведении графа.
Используй синхронную модель Kora 2.
Не вводи реактивные контракты, если проект явно не требует другую библиотеку.
Используй модули для расширений.
Относись к сгенерированному коду как к инспектируемому результату, а не как к написанному вручную исходному коду.
```

Это не просто факты. Это инструкции для рассуждения.

## Документация говорит, что существует; скилл говорит агенту, как об этом рассуждать { #documentation-tells-what-exists }

Полезное разделение таково:

```text
Документация
→ факты и контракты

Руководства
→ рассуждения и рабочие процессы

Примеры
→ канонические реализации

Kora Skill
→ операционная модель агента
```

Слои усиливают друг друга. Документация даёт точные определения. Руководства объясняют, почему и когда. Примеры демонстрируют реальные сервисы. Скилл говорит агенту, как комбинировать эти источники
при решении задачи.

Это важно, потому что ИИ-агент не просто извлекает информацию. Он решает, какой файл изучить, какой паттерн скопировать, какой API избегать, когда компилировать, когда искать сгенерированный код и как
интерпретировать сбой.

Скилл может формировать эти решения.

## Kora Skill — это слой навигации поверх существующей истины { #kora-skill-navigation-layer }

Лучший скилл не должен дублировать всю документацию в один огромный промпт. Это создало бы ещё одно устаревшее хранилище знаний.

Его сильнейшая роль — навигация и интерпретация.

Хороший скилл может, по сути, сказать:

```text
По вопросам DI:
прочитай текущую документацию по контейнеру,
изучи @KoraApp / @Module / конструкторы,
скомпилируй,
затем, если необходимо, изучи сгенерированный код графа.

По вопросам репозиториев:
используй текущую документацию и примеры по репозиториям,
не выводи семантику именования Spring Data,
если маппинг неясен, изучи сгенерированную реализацию.

По конкурентности в Kora 2:
исходи из синхронных контрактов и выполнения на виртуальных потоках,
а не из старых реактивных/suspend-паттернов.

По работе с расширениями:
предпочитай модуль вокруг нативной библиотеки,
а не изменение внутренностей фреймворка.
```

Теперь скилл остаётся относительно небольшим, а реальный источник фактов живёт в документации, примерах, исходном коде и сгенерированном коде. Это лучшая архитектура, чем копирование руководства по
фреймворку в промпт агента.

## Скилл может кодировать каноническое предпочтение, а не только возможность { #skill-encode-canonical-preference }

Справочная документация часто должна нейтрально описывать несколько возможностей. Агенту нужно больше. Ему нужно знать, какое решение проект должен генерировать по умолчанию.

Философия Kora «одна задача — одно рекомендованное решение» особенно хорошо с этим сочетается.

Предположим, существует несколько технически возможных подходов:

```text
нативная библиотека
встроенный модуль Kora
пользовательская обёртка
низкоуровневый API
сгенерированный API
```

Документация может описать их все. Скилл может объяснить, какой путь каноничен для обычной разработки приложений, а какие пути — запасные выходы. Это снижает вероятность того, что агент сгенерирует
технически допустимый, но стилистически чуждый код.

## Низкая неоднозначность важнее для агентов, чем для людей { #low-ambiguity-matters-agents }

Старший инженер может мириться с несколькими допустимыми альтернативами, потому что понимает компромиссы. Автономный агент должен выбрать одну без накопленной истории проекта.

Если фреймворк предоставляет пять эквивалентных моделей программирования, агенту нужны дополнительные эвристики.

Если Kora предоставляет один рекомендованный путь, а скилл его подкрепляет, пространство решений сужается:

```text
один рекомендованный путь
        +
официальный скилл
        ↓
низкая неоднозначность
```

Это влияет не только на первоначальную генерацию кода. Это улучшает согласованность, стоимость ревью, сопровождение, введение в проект, автоматический рефакторинг и миграцию. Кодовой базе,
сгенерированной агентами, становится гораздо легче доверять, когда сам фреймворк даёт им узкую каноническую цель.

## Скилл может кодировать знания, которые не помещаются в Javadoc { #skill-encode-knowledge-fit }

Некоторые из самых важных знаний о фреймворке трудно выразить в справочнике по API.

Например:

```text
Предпочитай этот паттерн более старому.
Используй сгенерированный исходный код как первый запасной вариант при отладке.
Не создавай ещё одну абстракцию вокруг JDBC, если нет реальной причины в предметной области.
Используй виртуальные потоки вместо введения реактивного контракта приложения.
Расширяй через @Module вместо патчинга внутренностей фреймворка.
Сохраняй видимой нативную семантику Kafka.
```

Эти утверждения — не документация методов. Это **операционные знания**.

Исторически операционные знания жили в старших инженерах, командных вики, ревью кода, докладах на конференциях, тредах в Slack и неписаных соглашениях. Скилл создаёт машиночитаемое место для этих
знаний.

## Скилл может кодировать ожидания экспертов { #skill-encode-expert-expectations }

Это приводит к одной из самых сильных формулировок:

> **Скилл может кодировать не только то, что умеет Kora, но и то, как опытные инженеры Kora ожидают её использования.**

Это принципиально отличается от справочника по API.

Фреймворк — это больше, чем его доступные методы и аннотации. У него есть архитектурный замысел. Два разработчика могут использовать одни и те же API и всё же получить радикально разное качество кода,
если один понимает задуманную модель композиции фреймворка, а другой знает лишь синтаксис.

Скилл может передавать замысел.

## Операционные знания когда-то были племенными знаниями { #operational-knowledge-used-be }

Рассмотрим типичный рабочий процесс опытной команды.

Новичок пишет код. Старший ревьюер комментирует:

```text
Не используй этот API здесь.
Используй паттерн модуля.
В Kora 2 это должно быть синхронным.
Не оборачивай этот клиент; предоставь нативный клиент.
Проверь сгенерированный AOP-класс, прежде чем менять порядок аннотаций.
Это проблема графа, сначала скомпилируй.
```

Через несколько месяцев новичок усваивает эти правила.

ИИ-агенту нужен тот же цикл исправлений, но часть его мы можем перенести раньше. Вместо ожидания комментариев ревью официальный скилл может поместить эти ожидания в операционный контекст агента до
того, как он сгенерирует код.

Это организационный рычаг.

## Скилл превращает пассивные знания в действие { #skill-turns-passive-knowledge }

Документация пассивна. Человек или агент читает её и решает, что делать.

Скилл может операционализировать знания.

Разницу проще всего увидеть на примере репозитория.

Документация говорит:

```text
Репозитории Kora генерируются на этапе компиляции.
```

Агент, ведомый скиллом, может превратить это в:

```text
Создай интерфейс репозитория по текущему паттерну Kora.
Скомпилируй проект.
Если маппинг не удаётся, изучи диагностику компилятора.
Если поведение реализации неясно, открой сгенерированный исходный код репозитория.
Добавь целевой тест против реального контракта базы данных.
```

Информация превратилась в рабочий процесс.

Вот почему:

> **Документация объясняет Kora. Kora Skill операционализирует эти знания для агента.**

## «Исполняемые знания фреймворка» — полезная ментальная модель { #executable-framework-knowledge-useful }

Скилл — не исполняемый код в традиционном смысле, но это исполняемое *руководство*.

Агент читает инструкции и выполняет операции.

Цепочка такова:

```text
знания фреймворка
        ↓
инструкции агента
        ↓
правки в репозитории
        ↓
компилятор
        ↓
сгенерированный код
        ↓
тесты
```

Это делает скилл частью системы разработки. Это не просто учебный материал.

## Сгенерированный код Kora делает скилл более мощным { #kora-s-generated-code }

Многие фреймворки могли бы публиковать скиллы. У Kora особенно сильная комбинация, потому что скилл может направлять агента к конкретным сгенерированным артефактам.

Цикл становится таким:

```text
Kora Skill
        ↓
агент знает, где генерируется поведение фреймворка
        ↓
сгенерированный исходный код
        ↓
агент читает фактическую реализацию
        ↓
объясняет / исправляет конкретный проект
```

Это большое отличие от скилла, который может лишь повторять общую документацию. Kora может сказать агенту, где истина превращается в исполняемый исходный код.

## Скилл может обучать модели отладки { #skill-teach-debugging-model }

Например, официальный скилл может кодировать диагностическую процедуру для внедрения зависимостей:

```text
1. Определи зависимость конструктора или модуля.
2. Скомпилируй проект.
3. Прочитай диагностику графа.
4. Изучи @KoraApp / наследование модулей / теги.
5. Если разрешение всё ещё неясно, изучи сгенерированный код графа.
6. Не выдумывай поведение контейнера времени выполнения, которого нет.
```

Для AOP:

```text
1. Проверь порядок аннотаций и переопределяемость метода.
2. Скомпилируй.
3. Изучи сгенерированную обёртку/подкласс.
4. Следуй обычной семантике вызовов Java/Kotlin.
```

Для репозиториев:

```text
1. Прочитай контракт метода и запрос.
2. Скомпилируй сгенерированный маппинг.
3. При необходимости изучи сгенерированную реализацию.
4. Используй интеграционный тест для реальной семантики базы данных.
```

Это экспертиза фреймворка, закодированная как процедура.

## Сгенерированный исходный код становится реальным механизмом отладки ИИ { #generated-source-becomes-real }

Прозрачность Kora всегда помогала отладке человеком. Скилл делает эту прозрачность операционной для агентов.

Без руководства модель может не знать, что сгенерированный исходный код — правильное место для поиска. Она может искать в общей документации фреймворка или гадать по аннотациям.

Со скиллом сгенерированный код становится намеренной частью пути расследования. Это превращает пассивное свойство фреймворка в активную возможность ИИ.

## Скилл может предотвратить редактирование сгенерированного результата { #skill-prevent-editing-generated }

Это звучит тривиально, но важно в автоматизированных рабочих процессах.

Агент может найти сгенерированный класс, правильно определить ошибку и затем напрямую отредактировать сгенерированный файл, потому что это выглядит самым быстрым путём.

Официальный скилл может явно закодировать:

```text
сгенерированные исходники — производные артефакты
изучай их
не считай их источником истины для правок
меняй вместо этого объявление / модуль / входные данные процессора
```

Это предотвращает целый класс хрупких исправлений. Опять же, это операционные знания, а не документация по API.

## Обратная связь компилятора Kora естественно вписывается в скилл { #kora-s-compiler-feedback }

Текущая архитектура Kora уже рассматривает диагностику компилятора как основную поверхность обратной связи. Скилл может научить агента доверять этой поверхности.

Вместо догадок о поведении графа рабочий процесс становится таким:

```text
внеси минимальное изменение
        ↓
скомпилируй
        ↓
прочитай точную диагностику
        ↓
обнови гипотезу
```

Это особенно эффективно для ИИ, потому что языковые модели вероятностны, а диагностика компилятора детерминирована.

Скилл может сказать модели, когда перестать гадать и спросить компилятор.

## Скилл + компилятор сильнее, чем скилл сам по себе { #skill-compiler-stronger-than }

Это ключевое различие.

Скилл всё ещё может ошибаться. Он может устареть. Он может упустить крайний случай.

Поэтому архитектура не должна полагаться только на корректность инструкций.

Модель компиляции Kora обеспечивает проверку:

```text
скилл предлагает паттерн
        ↓
агент его реализует
        ↓
компилятор проверяет граф / сгенерированный код
        ↓
тесты проверяют поведение во время выполнения
```

Скилл направляет. Компилятор и тесты выносят решение.

Это надёжная система.

## Скилл может уменьшить «спрингизмы» { #skill-reduce-springisms }

Одна из самых практичных ценностей руководства, специфичного для фреймворка, — предотвращение чужеродных соглашений.

Java-бэкенд-модели имеют подавляющую представленность Spring. Это означает, что агент может спонтанно сгенерировать:

```text
@Service
@Autowired
ожидания репозиториев Spring Data
допущения о прокси Spring
соглашения о конфигурации Spring
```

даже в репозитории Kora.

Официальный скилл может сделать простое правило явным:

```text
Не переводи Kora в термины Spring.
Используй собственную модель компонентов, модулей, репозиториев, AOP и конфигурации Kora.
```

Такого рода руководство может резко улучшить качество кода с первой попытки.

## Скилл может уменьшить смешивание версий { #skill-reduce-version-mixing }

Смешивание версий — ещё более сложная проблема.

Модель может знать:

```text
Kora 1.x
Kora 2.x
```

не разделяя их чётко.

Текущий официальный репозиторий `kora-skills` иллюстрирует, почему версионируемые скиллы важны. На момент написания публичный пакет называется `kora-v1` и явно нацелен на линию Kora 1.x. Именование
репозитория намеренно оставляет место для будущего пакета `kora-v2`, когда линии 2.x понадобится отдельное руководство.

Это не мелкая деталь упаковки. Это демонстрация архитектуры машинно-ориентированных знаний о версиях.

## Версионируемые скиллы могут сделать эволюцию фреймворка безопаснее { #versioned-skills-make-framework }

Представь:

```text
скилл Kora 1.x
→ API и соглашения 1.x

скилл Kora 2.x
→ текущие синхронные контракты
→ модель, ориентированная на виртуальные потоки
→ текущие правила DI/конфигурации/репозиториев
→ текущая структура модулей
```

Теперь агенту можно дать корректное мировоззрение фреймворка для проекта, который он изменяет.

Модели больше не нужно выводить границы версий из статистической памяти.

Это снижает случайное смешивание API.

## Фреймворку больше не нужно ждать следующего цикла обучения модели { #framework-longer-has-wait }

Это одно из самых важных следствий эпохи ИИ.

Исторически фреймворк выпускал крупную версию. Разработчики осваивали её сразу. Языковые модели отставали, пока новый код не появлялся публично, документация не сканировалась, будущие обучающие
прогоны не включали её, и не выходило новое поколение моделей.

Эта задержка могла составлять месяцы или годы.

Версионируемый официальный скилл меняет сроки:

```text
релиз фреймворка
      +
документация
      +
примеры
      +
скилл
        ↓
агент получает актуальную модель немедленно
```

Это поддерживает сильный общий принцип:

> **Фреймворку больше не нужно ждать следующего поколения моделей, чтобы те «выучили» его новую версию. Он может поставлять собственные актуальные знания для агентов вместе с релизом.**

Это значительный сдвиг в инструментарии разработчика.

## Релизы фреймворка могут со временем включать знания для агентов как обычный артефакт { #framework-releases-eventually-include }

Зрелый процесс релиза мог бы относиться к руководству для агентов так же, как к документации и примерам.

Для каждого крупного релиза:

```text
артефакты библиотек
документация
руководство по миграции
примеры
скилл агента
```

всё развивается вместе.

Скилл может кодировать новые канонические API, удалённые паттерны, предупреждения о миграции, изменения в отладке, новые места сгенерированного кода и новые рекомендованные модули. Это превращает
совместимость с ИИ в поддерживаемую поверхность продукта, а не в побочный эффект покрытия публичного интернета.

## Скиллы создают новый вид поверхности совместимости { #skills-create-new-kind }

Как только фреймворк поставляет официальное руководство для ИИ, сопровождающим нужно относиться к нему серьёзно.

Устаревший скилл может быть хуже, чем отсутствие скилла, потому что у него есть авторитет.

Если фреймворк меняет API, а скилл продолжает рекомендовать старый путь, агент может уверенно генерировать неправильный код.

Поэтому обслуживание скилла должно быть версионируемым и ревьюироваться вместе с документацией.

Скилл — это не «просто текст промпта». Он становится частью совместимости фреймворка.

## Это предполагает CI для документации агентского руководства { #suggests-documentation-ci-agent }

Команды фреймворков уже тестируют код, примеры, фрагменты документации и сгенерированные артефакты.

Естественный следующий шаг — косвенно оценивать скиллы.

Например, сопровождающие могут хранить репрезентативные задачи:

```text
создай HTTP-контроллер
добавь JDBC-репозиторий
настрой Kafka-консьюмер
отладь неоднозначность DI
примени отказоустойчивость
мигрируй старый паттерн
```

и оценивать, следуют ли поддерживаемые агенты текущим соглашениям.

Цель — не детерминированный вывод на естественном языке. Цель — обнаруживать крупные регрессии в руководстве.

## Скилл может кодировать знания о миграции { #skill-encode-migration-knowledge }

Крупные миграции — это то место, где общие знания LLM становятся особенно рискованными.

Агент видит старый код и может сохранить устаревшие паттерны, потому что они внутренне согласованы.

Версионируемый скилл может сказать:

```text
Этот паттерн принадлежит Kora 1.x.
Для Kora 2.x используй эту замену.
Не сохраняй реактивные/suspend-контракты, которых больше нет в этом модуле.
Используй текущий API запуска/жизненного цикла.
```

Теперь знания о миграции становятся машиночитаемыми.

Это может резко улучшить крупные автоматические рефакторинги.

## Скиллы могут превратить руководства по миграции в процедуры { #skills-turn-migration-guides }

Руководство по миграции объясняет:

```text
старое понятие
→
новое понятие
```

Скилл может сказать агенту, как применить этот маппинг в масштабе репозитория:

```text
найди старый API
классифицируй использование
замени текущим паттерном
скомпилируй
следуй диагностике
запусти тесты
повтори
```

Это снова разница между справочными и операционными знаниями.

## Примеры становятся учебным материалом в момент выполнения { #examples-become-training-material }

Официальные примеры особенно сильны в сочетании со скиллом.

Модели не нужно, чтобы примеры присутствовали во время предобучения.

Скилл может направить её в текущий репозиторий примеров и сказать:

```text
Используй пример Java JDBC как канонический локальный паттерн.
Используй пример Kotlin HTTP для соглашений о контроллерах.
Предпочитай примеры, соответствующие текущей крупной версии.
```

Примеры становятся демонстрациями в контексте.

Это фактически **обучение фреймворку в момент извлечения**.

## Запускаемые примеры лучше случайных фрагментов { #runnable-examples-better-than }

Фрагменты из публичного интернета могут быть неполными или устаревшими.

Официальные примеры можно компилировать и тестировать против текущего релиза.

Это делает их более сильным доказательством.

Скилл может сказать агенту отдавать приоритет официальным примерам над случайными фрагментами GitHub при их конфликте.

Это форма контроля качества документации.

## Скилл может уменьшить интернет-фольклор { #skill-reduce-internet-folklore }

Без официального руководства агент может объединить старый ответ на Stack Overflow, случайный репозиторий GitHub, пример Kora 1.x, сторонний блог и соглашение Spring в одну правдоподобную, но неверную
реализацию.

Скилл может явно ранжировать источники:

```text
текущая официальная документация
текущие официальные примеры
текущий исходный код / сгенерированный исходный код
затем внешние материалы сообщества
```

Это уменьшает устаревшие паттерны и противоречивые советы.

Цель — не устранить знания сообщества. Цель — отличать каноническое поведение фреймворка от исторического фольклора.

## Официальные скиллы меняют ценность возраста фреймворка { #official-skills-change-value }

Двадцать лет возраст фреймворка создавал огромный документационный ров.

Более старый фреймворк накапливал:

```text
код
вопросы и ответы
книги
блоги
доклады на конференциях
консалтинговые знания
```

Модели, обученные на интернете, автоматически наследуют часть этого рва.

Более новый фреймворк стартует позади.

Официальные скиллы меняют это соотношение.

Меньший фреймворк может предоставить концентрированный авторитетный контекст непосредственно модели.

Разрыв не исчезает, но становится менее абсолютным.

## Возраст фреймворка менее важен, когда актуальные знания можно внедрить { #framework-age-matters-less }

Полезная формулировка такова:

> **Возраст фреймворка менее важен, когда актуальные авторитетные знания можно внедрить непосредственно в агента.**

Старые фреймворки по-прежнему выигрывают от зрелости экосистемы.

Но корректность ИИ для современной кодовой базы больше не зависит полностью от объёма исторического корпуса.

Это особенно важно для быстро развивающихся проектов.

Двухлетний API можно лучше представить агенту через точный скилл, чем через тысячи публичных примеров со смешанными версиями.

## Это может уменьшить исторический ров экосистемы { #reduce-historical-ecosystem-moat }

Конкурентный ландшафт меняется незаметно.

Раньше:

```text
20 лет публичного корпуса
        ↓
знакомство LLM
        ↓
лучшая генерация кода
```

против:

```text
маленький публичный корпус
        ↓
слабое знакомство LLM
```

Теперь меньший фреймворк может построить:

```text
маленький корпус
        +
качественная документация
        +
запускаемые примеры
        +
официальный скилл
        ↓
более сильная производительность агента
```

Историческое преимущество остаётся, но оно частично заменяемо.

Это стратегически важно для новых фреймворков.

## Скилл не отменяет потребность в хорошей документации { #skill-eliminate-need-good }

Этот момент должен оставаться явным.

Скилл, построенный на слабой документации, со временем превратится в хрупкую кучу инструкций.

Самая сильная архитектура такова:

```text
хорошая документация
        ↓
хорошие примеры
        ↓
хороший исходный код фреймворка
        ↓
хороший сгенерированный исходный код
        ↓
скилл учит агента, как по ним ориентироваться
```

Скилл — это множитель.

Он не может заменить отсутствующую истину.

## Скилл должен избегать превращения в теневой набор документации { #skill-avoid-becoming-shadow }

Если каждый факт скопирован в скилл, возникают две проблемы.

Во-первых, скилл становится большим и дорогим для загрузки.

Во-вторых, он расходится с документацией.

Лучший дизайн использует прогрессивное раскрытие.

Верхнеуровневый скилл содержит:

```text
основное мировоззрение
идентичность версии
канонические правила
приоритет источников
рабочий процесс отладки
маршрутизацию к доменным скиллам
```

Доменные скиллы затем направляют агента к соответствующим официальным ресурсам.

Это ближе к маршрутизатору знаний, чем к продублированному руководству.

## Текущий репозиторий Kora Skills уже предполагает эту структуру { #current-kora-skills-repository }

Официальный репозиторий организован в несколько доменных скиллов, а не в один монолитный файл.

Текущий публичный пакет включает скиллы, покрывающие такие области, как:

```text
DI
конфигурация
HTTP
OpenAPI
JDBC
Cassandra
Kafka
gRPC
телеметрия
AOP
тестирование
настройка проекта
```

плюс мета-скилл для совместимости агентов.

Эта структура отражает важный принцип проектирования: знания фреймворка должны загружаться в соответствии с задачей.

Задаче HTTP не нужен весь справочник по планировщику в контексте.

## Прогрессивное раскрытие важно для контекста агента { #progressive-disclosure-matters-agent }

Контекст LLM конечен.

Загружать каждую деталь Kora в каждую задачу было бы расточительно.

Система скиллов может изначально показывать ровно столько метаданных для обнаружения, сколько нужно, и загружать более глубокое руководство только тогда, когда оно релевантно.

Это создаёт иерархию:

```text
агент знает, что скиллы Kora существуют
        ↓
выбирает доменный скилл
        ↓
загружает целевые инструкции/ресурсы
        ↓
действует в проекте
```

Это гораздо более масштабируемо, чем один гигантский системный промпт.

## Скилл может обучать приоритизации источников { #skill-teach-source-prioritization }

Одна из самых ценных инструкций может быть удивительно простой:

```text
Когда источники противоречат друг другу, предпочитай:
1. официальную документацию текущей версии
2. текущие официальные примеры
3. текущий исходный код фреймворка/проекта
4. сгенерированный исходный код для фактической реализации
5. внешний контент сообщества
```

Это предотвращает огромный класс ошибок ИИ.

Модель больше не считает каждый извлечённый фрагмент одинаково авторитетным.

У команд фреймворков никогда не было прямого способа управлять этой иерархией.

Скиллы создают его.

## Скилл может научить агента тому, чего Kora не делает { #skill-teach-agent-what }

Негативные знания чрезвычайно ценны.

Модели часто нужно знать не только то, какие API существуют, но и какие допущения неверны.

Например:

```text
не предполагай стереотипы Spring
не предполагай семантику прокси времени выполнения
не предполагай DI на основе рефлексии
не предполагай реактивные контракты в модулях Kora 2
не редактируй сгенерированный исходный код напрямую
не выдумывай абстракцию там, где нативная библиотека и есть задуманный API
```

Документация часто фокусируется на поддерживаемых функциях.

Скилл может явно защищать от распространённых некорректных переносов из других фреймворков.

## Это идентичность фреймворка в машиночитаемой форме { #framework-identity-machine-readable }

Люди распознают код Kora культурно.

Они знают, что «выглядит как Kora».

Агенту нужно, чтобы эта идентичность была выражена более конкретно.

Скилл может кодировать предпочтительную архитектуру, предпочтительные имена, предпочтительный паттерн расширения, предпочтительный путь отладки и предпочтительную иерархию источников.

Это даёт модели специфичный для фреймворка стилевой априор.

Это машиночитаемый эквивалент вступления в опытную команду Kora.

## Скилл может улучшить ревью кода до человеческого ревью { #skill-improve-code-review }

Если агент использует канонические паттерны фреймворка с первой попытки, ревьюеры тратят меньше времени на исправление стиля фреймворка.

Они могут сосредоточиться на бизнес-логике, безопасности, согласованности данных и производительности вместо комментариев вроде:

```text
Не используй эту старую аннотацию.
Используй модуль.
Не вводи реактивный слой.
Не редактируй сгенерированный исходный код.
```

Это снижает стоимость ревью.

Для команд с интенсивным использованием ИИ это существенный выигрыш в продуктивности.

## Согласованность накапливается по всей кодовой базе { #consistency-compounds-across-codebase }

Агент, ведомый скиллом, многократно генерирует код по одним и тем же соглашениям.

Со временем по репозиторию становится легче ориентироваться и людям, и агентам.

Локальные примеры становятся чище.

Будущее извлечение улучшается.

Система создаёт положительный цикл обратной связи:

```text
официальное руководство
        ↓
согласованный сгенерированный код
        ↓
лучшие локальные примеры
        ↓
лучшие будущие решения агента
```

Это одна из самых практичных причин формализовать руководство фреймворка.

## Скилл может сократить и введение человека в проект { #skill-shorten-human-onboarding }

Хотя артефакт ориентирован на машины, люди выигрывают косвенно.

Новый разработчик может спросить:

```text
Объясни, как связан этот сервис Kora.
Почему эта зависимость не разрешается?
Где генерируется реализация этого репозитория?
Каков канонический способ сделать это в Kora 2?
```

Агент использует скилл, чтобы дать объяснение, основанное на официальных соглашениях.

Фреймворк фактически получает интерактивного наставника.

Это особенно полезно для меньших фреймворков, где не у каждой команды есть опытный инженер Kora.

## Агент может стать учителем фреймворка { #agent-become-framework-teacher }

Текущая посадочная страница Kora v2 уже демонстрирует эту идею напрямую: установи официальный скилл, спроси агента о Kora и позволь ему учить по официальным руководствам и примерам.

Это меняет потребление документации.

Вместо:

```text
разработчик
        ↓
поиск по иерархии документации
        ↓
чтение нескольких страниц
        ↓
сопоставление концепций с проектом
```

поток может стать таким:

```text
вопрос разработчика
        ↓
агент, ведомый скиллом
        ↓
официальная документация + примеры + проект
        ↓
объяснение, специфичное для проекта
```

Источник остаётся официальным.

Интерфейс становится разговорным и контекстным.

## Это не делает документацию устаревшей { #make-documentation-obsolete }

Агенту нужен стабильный материал, на котором можно основывать ответ.

Без хорошей документации разговорный слой превращается в спекуляцию.

Лучшая аналогия — база данных и движок запросов.

Документация — это долговечное хранилище знаний.

Скилл определяет, как агент запрашивает и интерпретирует её.

Агент предоставляет интерактивный интерфейс.

У каждого слоя своя задача.

## Скилл может кодировать «когда изучать сгенерированный исходный код» { #skill-encode-when-inspect }

Это особенно специфичное для Kora преимущество.

Не каждая проблема требует изучения сгенерированного исходного кода.

Скилл может научить правильному пути эскалации:

```text
простой вопрос по API
→ документация

вопрос о каноническом использовании
→ руководство / пример

сбой компиляции
→ диагностика

несоответствие поведения
→ сгенерированный исходный код

проблема времени выполнения с внешней системой
→ интеграционный тест / телеметрия
```

Это позволяет избежать обеих крайностей: никогда не смотреть на сгенерированный код и смотреть на него для всего.

Скилл становится маршрутизатором экспертизы.

## Он также может научить «когда не винить Kora» { #teach-when-blame-kora }

Тонкие абстракции означают, что многие сбои принадлежат нижележащей технологии.

Скилл может помочь различить:

```text
проблема маппинга репозитория Kora
против
проблема запроса PostgreSQL

проблема подключения Kafka в Kora
против
проблема ребалансировки Kafka

проблема интеграции gRPC в Kora
против
семантика дедлайнов gRPC
```

Это мощно, потому что говорит агенту, когда перестать искать в документации фреймворка и использовать знания нативной технологии.

Это ровно согласуется с философией тонких абстракций Kora.

## Скилл может кодировать философию фреймворка { #skill-encode-framework-s }

Документация по API редко говорит достаточно об архитектурной сдержанности.

Скилл может кодировать такие принципы:

```text
предпочитай семантику нативной технологии
избегай ненужных обёрток
используй один рекомендованный путь
расширяй через модули
держи зависимости явными
доверяй обратной связи компилятора
изучай сгенерированный исходный код, когда поведение важно
```

Эти принципы влияют на десятки мелких решений.

Без них агент может сгенерировать код, который компилируется, но не ощущается как Kora.

С ними он может создать архитектуру, согласованную с замыслом фреймворка.

## Скилл может нести «почему», а не только «что» { #skill-carry-why-just }

Агент надёжнее, когда понимает причину соглашения.

Например:

```text
Используй синхронные контракты в Kora 2,
потому что код приложения спроектирован вокруг виртуальных потоков,
а не потому, что асинхронное программирование запрещено повсеместно.
```

или:

```text
Предпочитай модули для внешних библиотек,
потому что они сохраняют явную интеграцию графа/жизненного цикла/конфигурации,
а не потому, что внешние библиотеки нужно сильно оборачивать.
```

Это предотвращает слепое применение правил.

Скилл может компактно кодировать эти обоснования.

## Это делает агента более адаптивным { #makes-agent-adaptable }

Чистые правила ломаются на крайних случаях.

Принципы обобщаются.

Если агент знает:

```text
Kora предпочитает тонкие абстракции, близкие к нативной технологии
```

он может принимать лучшие решения для новой библиотеки, о которой скилл никогда явно не упоминал.

Если он знает:

```text
сгенерированный исходный код — инспектируемый артефакт реализации
```

он может отладить результат нового процессора, который никогда раньше не видел.

Хорошие скиллы учат модели, а не только команды.

## Скилл — не замена проверке компилятором { #skill-replacement-compiler-verification }

Даже официальное руководство должно оставаться подчинённым фактической истине проекта.

Лучший цикл таков:

```text
скилл
→ выбирает вероятно корректный подход

компилятор
→ проверяет статические контракты фреймворка

сгенерированный исходный код
→ раскрывает фактическую реализацию

тесты
→ проверяют поведение
```

Эта многослойная проверка защищает от устаревшего или неполного руководства скилла.

Фреймворк не просит модель слепо доверять инструкциям.

Он даёт модели инструменты для их проверки.

## Вот почему Kora — особенно хорошая цель для скилла { #why-kora-especially-good }

Скилл фреймворка наиболее ценен, когда фреймворк предоставляет инспектируемое доказательство после инструкции.

Kora предоставляет.

Скилл может сказать:

```text
Используй этот паттерн.
```

Компилятор может сказать:

```text
Действительно / недействительно.
```

Сгенерированный исходный код может сказать:

```text
Вот что построил фреймворк.
```

Тесты могут сказать:

```text
Вот что приложение реально делает.
```

Это создаёт замкнутый цикл обратной связи.

## Скилл может уменьшить зависимость от Stack Overflow { #skill-reduce-dependence-on }

Меньший фреймворк часто сталкивается с критикой, что у него меньше ответов в вопросах и ответах.

Официальный скилл меняет часть этого уравнения.

Для базового использования фреймворка идеальный рабочий процесс — не:

```text
поиск в интернете
найти случайный ответ
угадать версию
скопировать код
```

Он становится:

```text
спроси агента
агент использует официальный скилл
агент читает текущую документацию/примеры
агент применяет результат к проекту
компилятор проверяет
```

Вопросы и ответы сообщества остаются ценными для необычных производственных случаев.

Они становятся менее необходимыми для рутинного канонического использования.

## Это контроль качества документации во время выполнения { #documentation-quality-control-at }

Скилл фактически даёт фреймворку способ сказать:

```text
Когда помогаешь с Kora, начинай здесь.
Предпочитай эти источники.
Не используй эти устаревшие допущения.
Используй этот порядок отладки.
```

Это форма контроля качества того, как ИИ интерпретирует экосистему.

Исторически у сопровождающих было мало контроля над тем, какой пост в блоге или ответ на Stack Overflow модель может усвоить.

Теперь они могут предоставить авторитетный контекст в момент извлечения.

## Скиллы могут стать новым артефактом распространения фреймворка { #skills-become-new-framework }

Более крупное следствие в том, что распространение фреймворка может эволюционировать.

Традиционно фреймворк поставляет:

```text
библиотеки
документацию
примеры
```

Следующее поколение может поставлять:

```text
библиотеки
документацию
примеры
знания о миграции
ИИ-скилл
```

Скилл — не аксессуар.

Это машинно-ориентированный интерфейс фреймворка.

Это новая категория опыта разработчика.

## У API фреймворков теперь есть человеческие и машинные потребители { #framework-apis-have-human }

Исторически дизайн API оптимизировался для:

```text
разработчика
IDE
компилятора
времени выполнения
```

Теперь есть ещё один потребитель:

```text
агент для написания кода
```

Агент читает метаданные иначе, чем человек.

Ему нужны каноническая иерархия источников, явное версионирование, предпочтительные паттерны, негативное руководство и процедуры отладки.

Скилл может предоставить ровно эти недостающие семантики, не искажая фактический API программирования.

## Это лучше, чем проектировать странные «AI-first» API { #better-than-designing-weird }

Существует соблазн делать фреймворки искусственно многословными или машинно-ориентированными, чтобы модели могли их понять.

Это не нужно.

Kora может сохранять чистые API Java/Kotlin для людей и компиляторов, предоставляя специфичное для ИИ операционное руководство через скилл.

Слои остаются раздельными:

```text
API
→ оптимизирован для программирования приложений

документация
→ оптимизирована для обучения/справки человеком

скилл
→ оптимизирован для рассуждений агента
```

Это лучшая архитектура, чем заставлять один артефакт обслуживать каждую аудиторию.

## Скиллы могут ускорить эволюцию фреймворка { #skills-make-framework-evolution }

Если сопровождающие знают, что актуальное руководство для агентов может поставляться с релизом, они могут испытывать меньше давления, сохраняя старые API лишь потому, что ИИ-инструменты знают их
лучше.

Скилл может явно сказать:

```text
Этот API удалён.
Используй текущую замену.
```

Модели не нужны годы накопления нового корпуса, прежде чем она сможет работать с изменённым дизайном.

Это может уменьшить один тонкий источник давления легаси.

## Но скиллы повышают ответственность сопровождающих { #skills-increase-maintainer-responsibility }

Выгода приходит с ценой.

Фреймворк, публикующий официальное руководство для агентов, теперь владеет ещё одной поверхностью совместимости.

Сопровождающие должны держать её синхронизированной с документацией, примерами, поведением релиза и руководствами по миграции.

Вводящий в заблуждение официальный скилл может очень быстро масштабировать ошибки, потому что агенты автоматизируют генерацию кода.

Это означает, что изменения скилла заслуживают ревью.

## К скиллу следует относиться как к коду { #skill-be-treated-like }

Не обязательно потому, что ему нужны модульные тесты в той же форме, а потому, что он влияет на производство.

Изменения должны иметь контроль версий, ревью, дисциплину релизов, осознание совместимости и репрезентативные оценки.

Если скилл говорит агентам использовать устаревший паттерн, это фактически регрессия опыта разработчика.

Артефакт заслуживает инженерной дисциплины.

## Метки версий важны { #version-labels-matter }

Текущее именование `kora-v1` в официальном репозитории скиллов — хороший пример этой дисциплины.

Оно избегает притворства, что один пакет вневременен.

Оно создаёт место для разных мировоззрений крупных версий.

Будущий пакет `kora-v2` может быть категоричным о Kora 2, не ломая агентов, работающих над проектами 1.x.

Именно так и должно работать версионируемое машинное руководство.

## Обнаружение проекта может стать частью скилла { #project-detection-become-part }

Зрелый будущий скилл мог бы изучать:

```text
версию BOM Kora
зависимости Gradle
имена пакетов
паттерны исходного кода
```

и выбирать правильные правила.

Это сделало бы руководство по версиям автоматическим.

Вместо того чтобы разработчик говорил модели:

```text
Это Kora 2.
```

агент мог бы определить это из репозитория и загрузить соответствующие знания.

Это очевидное направление для инструментария фреймворков.

## Скиллы могут быть композируемыми { #skills-be-composable }

Проект Kora может использовать JDBC, Kafka, gRPC, OpenAPI и отказоустойчивость.

Агенту не нужен один огромный документ с инструкциями.

Композируемые скиллы позволяют:

```text
основное мировоззрение Kora
+
скилл JDBC
+
скилл Kafka
+
скилл OpenAPI
```

загружаться для текущей задачи.

Это отражает модульность самого фреймворка.

## Архитектура скиллов может отражать архитектуру фреймворка { #skill-architecture-mirror-framework }

Эта симметрия привлекательна.

Kora говорит:

```text
используй только те модули, которые тебе нужны
```

Система агентов может сказать:

```text
загружай только те скиллы, которые тебе нужны
```

Модульность фреймворка и модульность знаний выравниваются.

Это уменьшает и зависимости времени выполнения, и зависимости контекста.

## Мета-скилл может маршрутизировать агента { #meta-skill-route-agent }

Текущий репозиторий скиллов уже включает концепцию мета-скилла.

Он может служить верхнеуровневой операционной моделью Kora:

```text
определи задачу
определи версию
выбери доменный скилл
выбери официальные источники
выполни рабочий процесс
скомпилируй/протестируй
```

Это гораздо мощнее, чем плоская коллекция промптов.

Это превращает ИИ-слой фреймворка в систему маршрутизации.

## Качество скилла становится частью DX фреймворка { #skill-quality-becomes-part }

Опыт разработчика раньше означал эргономику API, документацию, поддержку IDE, скорость сборки и отладку.

Теперь он также может означать:

```text
насколько точно агент работает с фреймворком
```

Если два фреймворка технически сопоставимы, но один может напрямую обучить агента своей текущей архитектуре, разница может стать значимой для команд, использующих автономную разработку.

Kora рано начала относиться к этому как к первоклассной задаче.

## Скилл может помочь малым командам масштабировать экспертизу { #skill-help-small-teams }

В небольшой организации может быть только один опытный инженер Kora.

Без машинного руководства этот инженер становится точкой эскалации для каждой незнакомой проблемы.

Официальный скилл позволяет экстернализовать большую часть ожидаемого рабочего процесса: как подключать модули, как отлаживать DI, как изучать сгенерированный код и как выбирать канонические API.

Агент становится ассистентом фреймворка первой линии.

Это не устраняет экспертов. Это освобождает их для по-настоящему сложной архитектуры.

## Это также уменьшает асимметрию введения в проект { #reduces-onboarding-asymmetry }

У опытных разработчиков Kora есть внутренний контекст, которого нет у новичков.

Скилл может сузить этот разрыв.

Новичок может задавать вопросы в контексте проекта и получать ответы, основанные на официальной модели.

Это полезнее общего поиска, потому что агент может связать руководство фреймворка с фактическим деревом исходного кода.

Это интерактивное введение в проект.

## Скиллы могут сохранять институциональную память { #skills-preserve-institutional-memory }

Знания о фреймворке часто исчезают, когда уходят сопровождающие или старшие инженеры.

Если знания существуют только в докладах и комментариях к ревью, они хрупки.

Скилл может зафиксировать канонические решения, распространённые ошибки, последовательности отладки, философию расширений и границы версий в долговечном артефакте.

Это делает институциональные знания переносимыми между командами и платформами агентов.

## Скилл может быть нейтральным к вендору на уровне агента { #skill-be-vendor-neutral }

Текущий официальный репозиторий поддерживает несколько сред агентов, а не один проприетарный ассистент.

Это стратегически важно.

Экспертиза фреймворка не должна быть привязана к одному вендору моделей.

Полезная абстракция такова:

```text
пакет знаний Kora
        ↓
совместимые агенты для написания кода
```

а не:

```text
знания Kora
        ↓
один проприетарный чат-интерфейс
```

Это отражает более широкое предпочтение Kora к открытым и инспектируемым технологиям.

## Переносимость агентов важна { #agent-portability-matters }

Организации будут менять ИИ-инструменты.

Одна команда может использовать Claude Code.

Другая — Codex.

Ещё одна — Cursor, Pi, OMP или будущие системы.

Если знания фреймворка упакованы в переносимый формат скилла, организация может менять агентов, не перестраивая экспертизу фреймворка с нуля.

Это недооценённое, но важное преимущество экосистемы.

## Переносимость скиллов предотвращает ещё один слой привязки { #skill-portability-prevents-another }

Было бы иронично, если бы фреймворк, сосредоточенный на прозрачной архитектуре, решал интеграцию ИИ через привязанную к вендору систему промптов.

Переносимая модель скилла избегает этого.

Артефакт знаний остаётся принадлежащим фреймворку.

Агенты становятся взаимозаменяемыми потребителями.

Это правильное долгосрочное направление.

## Скилл может научить агентов правильно использовать тонкие абстракции Kora { #skill-teach-agents-use }

Философия Kora достаточно тонка, чтобы общие модели легко могли чрезмерно абстрагировать.

Агент может ввести обёртку вокруг Kafka, потому что в корпоративном Java-коде часто есть обёртки. Он может создать ещё одну абстракцию репозитория поверх репозиториев Kora. Он может спрятать нативный
клиент за общим классом «менеджер».

Скилл может сказать:

```text
Предпочитай модель нативной технологии, если нет конкретной причины приложения добавлять ещё одну абстракцию.
```

Это защищает семантическую простоту Kora.

## Философию фреймворка трудно вывести только из типов { #framework-philosophy-hard-infer }

Типы говорят агенту, что возможно.

Они не всегда говорят, что желательно.

Публичный API может допускать несколько композиций.

Скилл может предоставить философию, которая помогает выбирать среди них.

Вот почему машинно-ориентированное руководство добавляет нечто действительно новое даже в строго типизированном фреймворке.

## Kora Skill может кодировать «что не абстрагировать» { #kora-skill-encode-what }

Это может стать одной из самых ценных его ролей.

Например:

```text
Не создавай нейтральные к фреймворку обёртки вокруг всего.
Не заменяй прямое рассуждение о JDBC/SQL выдуманным DSL.
Не скрывай семантику Kafka, если предметная область действительно этого не требует.
Не создавай второй DI-контейнер внутри Kora.
```

Это архитектурные ограничения.

Их трудно закодировать в компиляторе.

Они естественно помещаются в скилл.

## Скиллы заполняют разрыв между безопасностью типов и архитектурным суждением { #skills-fill-gap-between }

Компилятор может отвергнуть:

```text
отсутствующую зависимость
неверный тип
недействительный сгенерированный код
```

Он не может отвергнуть:

```text
ненужную абстракцию
неканонический паттерн
неверное архитектурное направление
```

Традиционно это ловили люди-ревьюеры.

Скилл даёт агенту часть этого архитектурного руководства до ревью.

Это и есть настоящий «недостающий слой».

## Полный стек агента Kora становится многослойным { #complete-kora-agent-stack }

Полезная модель такова:

```text
                ┌───────────────────────┐
                │     Kora Skill        │
                │ каноническое          │
                │ рассуждение           │
                └──────────┬────────────┘
                           │
        ┌──────────────────▼──────────────────┐
        │ Документация / Руководства /        │
        │ Примеры / Исходный код              │
        │ авторитетные знания фреймворка      │
        └──────────────────┬──────────────────┘
                           │
                ┌──────────▼───────────┐
                │ Текущий проект       │
                │ реальный локальный   │
                │ контекст             │
                └──────────┬───────────┘
                           │
                ┌──────────▼───────────┐
                │ Компилятор /         │
                │ сгенерированный код  │
                │ детерминированная    │
                │ истина               │
                └──────────┬───────────┘
                           │
                ┌──────────▼───────────┐
                │ Тесты / телеметрия   │
                │ проверка поведения   │
                └──────────────────────┘
```

Каждый слой решает свою задачу.

Скилл не заменяет ни один из нижних слоёв.

Он говорит агенту, как их использовать.

## Это мощнее гигантского промпта { #powerful-than-giant-prompt }

Гигантский статический промпт пытался бы вместить каждый факт фреймворка.

Это не масштабируется.

Многослойная модель лучше, потому что она может извлекать только то, что важно, изучать проект и проверять через компилятор.

Скилл вносит стратегию, а не энциклопедию.

Это делает его меньше, более поддерживаемым и более надёжным.

## Скиллы могут улучшить экономику поддержки фреймворка { #skills-improve-framework-support }

Команды поддержки снова и снова отвечают на одни и те же вопросы:

```text
Какой паттерн мне использовать?
Почему DI не работает?
Где генерируется эта реализация?
Как мигрировать этот API?
```

Официальный скилл может обрабатывать большую часть этих рутинных вопросов, используя текущие источники.

Сопровождающие могут затем сосредоточиться на новых ошибках, дизайне функций и сложных крайних случаях.

Это улучшает масштабируемость поддержки.

## Он также может улучшить отчёты об ошибках { #improve-bug-reports-too }

Агент, ведомый скиллом, может помочь разработчику составить лучшие отчёты о проблемах.

Вместо:

```text
Kora не работает
```

агент может собрать:

```text
версию фреймворка
минимальное объявление исходного кода
диагностику компилятора
фрагмент сгенерированного кода
шаги воспроизведения
```

Это облегчает работу сопровождающим.

ИИ-слой может улучшить обе стороны взаимодействия с поддержкой.

## Скиллы могут стать самодиагностикой фреймворка { #skills-become-framework-self }

Будущий скилл мог бы пойти ещё дальше.

Получив проект, агент мог бы проверить версию Kora, просканировать устаревшие паттерны, проверить конфигурацию сгенерированного исходного кода, выявить использование старых API, запустить целевые
задачи компиляции/тестирования и объяснить сбои.

Это превратило бы скилл фреймворка в лёгкий слой самодиагностики.

Ключ в том, что логика остаётся основанной на официальных знаниях фреймворка.

## Скилл может стать ассистентом миграции { #skill-become-migration-assistant }

Когда вырастет внедрение Kora 2, версионируемый скилл мог бы кодировать паттерны миграции с 1.x.

Рабочий процесс мог бы быть таким:

```text
обнаружь старый паттерн
        ↓
сопоставь с текущим эквивалентом
        ↓
отредактируй
        ↓
скомпилируй
        ↓
прочитай диагностику
        ↓
повтори
```

Это ровно тот тип повторяющейся, но чувствительной к контексту работы, в которой агенты хороши.

Сопровождающие фреймворка могут распространять экспертизу миграции напрямую.

## Это может снизить стоимость ломающих изменений { #reduce-cost-breaking-changes }

Ломающие изменения дороги отчасти потому, что каждая команда должна заново открывать процесс миграции.

Если фреймворк поставляет:

```text
руководство по миграции
+
скилл, осведомлённый о миграции
```

стоимость может упасть.

Это не делает ломающие изменения бесплатными.

Это меняет экономику поддержки.

Фреймворки могут развиваться чище, не оставляя пользователей полностью наедине с собой.

## Скилл даёт Kora канонический машинно-ориентированный голос { #skill-gives-kora-machine }

Человеческая документация уже даёт фреймворку канонический голос для разработчиков.

Скилл расширяет этот голос на агентов.

Это важно, потому что иначе агенты синтезируют идентичность фреймворка из того материала, который им удалось извлечь.

Официальный скилл говорит:

```text
Вот как Kora ожидает, что её будут понимать.
```

Это новая форма управления фреймворком.

## Канонический голос уменьшает противоречивые советы ИИ { #canonical-voice-reduces-contradictory }

Без официального руководства два агента могут по-разному ответить на один и тот же вопрос о Kora, потому что извлекли разные источники.

Со скиллом разброс должен сузиться.

Они всё ещё могут генерировать разный код, но архитектурные ограничения и предпочтительные источники остаются согласованными.

Это упрощает управление организациями с несколькими агентами.

## Скилл может ревьюироваться сопровождающими фреймворка { #skill-be-reviewed-by }

Ещё одно преимущество — подотчётность.

Если агент даёт плохой совет на основе случайного предобучения, нет очевидного места, где исправить проблему.

Если совет исходит из официального скилла, сопровождающие могут обновить руководство.

Исправление немедленно распространяется на совместимых агентов.

Это создаёт цикл обратной связи между сопровождающими фреймворка и поведением ИИ.

## Это новый вид поверхности управления опытом разработчика { #new-kind-developer-experience }

Команды фреймворков уже контролируют дизайн API, документацию, диагностику компилятора и примеры.

Скиллы добавляют:

```text
руководство по поведению агента
```

в этот список.

Это может стать стратегически важным по мере того, как всё больше кода пишется агентами.

Фреймворк, игнорирующий этот слой, может оставаться технически превосходным, пока агенты продолжают использовать его плохо.

## Риск: скиллы могут стать догматичными { #risk-skills-become-dogmatic }

Официальное руководство имеет авторитет, а авторитет может стать жёстким.

Скилл должен различать:

```text
рекомендованный выбор по умолчанию
```

и:

```text
единственное допустимое решение
```

Kora сама подчёркивает расширяемость.

Скилл должен это сохранять.

Например:

```text
Предпочитай встроенную модель репозитория для типового случая.
Если проект явно использует jOOQ по веской причине, работай с этой архитектурой, а не заставляй переписывать.
```

Машинное руководство должно поддерживать философию фреймворка, а не превращать её в слепое применение правил.

## Риск: скиллы могут отставать от реальности { #risk-skills-lag-behind }

Устаревший скилл может рекомендовать API, удалённые из текущего релиза.

Вот почему версионирование и синхронизация релизов важны.

Текущее версионируемое именование официального репозитория скиллов — хорошая основа.

Крупные линии Kora должны иметь чётко разделённое руководство.

Фреймворк должен избегать одного общего скилла «Kora», который молча смешивает поколения.

## Риск: скиллы могут скрывать проблемы документации { #risk-skills-hide-documentation }

Фреймворк не должен использовать ИИ-руководство, чтобы компенсировать отсутствие публичной документации.

Если скилл содержит важные факты, которых больше нигде нет, люди теряют прозрачность, а скилл становится скрытым хранилищем знаний.

Лучшее правило таково:

```text
факты живут в документации/исходном коде/примерах
скилл кодирует, как агенты должны их интерпретировать и применять
```

Это поддерживает здоровье системы знаний.

## Риск: специфичные для агента инструкции могут фрагментироваться { #risk-agent-specific-instructions }

Если каждая платформа агентов требует совершенно другой промпт Kora, сопровождение становится дорогим.

Переносимые форматы скиллов и общий пакет базовых знаний помогают.

Поэтому текущее направление мультиагентной упаковки важно.

Фреймворк должен поддерживать одну концептуальную прослойку экспертизы и адаптировать только поверхность установки.

## Скилл должен оставаться инспектируемым { #skill-remain-inspectable }

Как и сгенерированный код Kora, само руководство для агентов должно быть читаемым.

Разработчики должны иметь возможность изучить, что скилл говорит агенту, какие источники он предпочитает и какие соглашения кодирует.

Это важно для доверия.

Скрытый управляемый вендором промпт подорвал бы историю прозрачности.

## ИИ-слой Kora должен следовать собственной философии Kora { #kora-s-ai-layer }

Здесь доступна элегантная симметрия.

```text
явный
типизированный
прозрачный
сфокусированный
модульный
```

Её ИИ-слой знаний должен быть похожим:

```text
явные инструкции
версионируемые пакеты
прозрачные файлы
сфокусированные доменные скиллы
модульная загрузка
```

Эта согласованность усиливает продукт.

## Скиллы могут сделать «одна задача — одно решение» операционным { #skills-make-one-problem }

Фреймворк уже уменьшает неоднозначность, выбирая рекомендованный путь.

Скилл может подкреплять этот путь во время генерации кода.

Например:

```text
Нужен доступ к базе данных?
→ используй текущую модель репозитория Kora, если контекст проекта не говорит иное.

Нужна внешняя библиотека?
→ интегрируй через модуль/жизненный цикл/конфигурацию.

Нужно отладить поведение аспекта?
→ изучи сгенерированную обёртку.

Нужна параллельная блокирующая работа?
→ используй современную модель виртуальных потоков Java/Kora.
```

Это превращает философию в поведение агента.

## Результат — более похожий на Kora код { #result-kora-like-code }

Это звучит субъективно, но это важно.

Фреймворк наиболее здоров, когда код, написанный разными людьми, всё ещё ощущается структурно согласованным.

ИИ-агенты могут угрожать этому, импортируя паттерны из каждого известного им фреймворка.

Скилл сужает стиль.

Сгенерированный код становится более согласованным с написанными вручную сервисами Kora.

Это улучшает поддерживаемость.

## Экспертиза фреймворка становится распространяемой { #framework-expertise-becomes-distributable }

Исторически экспертиза воплощалась в людях.

Документация захватывала её часть.

Скиллы позволяют другой части стать напрямую потребляемой машинами.

Модель распространения становится такой:

экспертиза сопровождающих
        ↓

        ↓

        ↓
многие разработчики / репозитории

Это мощный множитель для небольшой команды фреймворка.

## Это особенно важно для масштаба Kora { #especially-important-kora-s }

У Kora нет огромного публичного корпуса Spring.

Это делает авторитетный машинный контекст более ценным, а не менее.

Сильный официальный скилл может помочь гарантировать, что ИИ-помощь основана на текущей архитектуре Kora, а не на случайной аналогии.

Это может материально снизить одно из недостатков внедрения меньшей экосистемы.

## Скилл может заставить фреймворк ощущаться лучше задокументированным, чем предполагает сырой размер корпуса { #skill-make-framework-feel }

Разработчику не важно, сколько страниц существует, если он может быстро получить правильный ответ.

Агент, ведомый скиллом, может синтезировать:

в один контекстный ответ.

Это повышает эффективную доступность существующей документации без раздувания её объёма.

Это рычаг, а не замена.

## Скилл — это компилятор знаний { #skill-knowledge-compiler }

Выходные данные:

Аналогия несовершенна, но полезна.

Kora уже переносит работу фреймворка времени выполнения в компиляцию.

Скилл переносит человеческую экспертизу фреймворка в машиноисполняемое руководство.

## Kora Skill завершает историю прозрачности фреймворка { #kora-skill-completes-framework }

Существующая архитектура Kora отвечает на:

```text

```

Скилл отвечает на:

```text
Как агент должен расследовать и интерпретировать это?
```

Эти два слоя усиливают друг друга.

Сгенерированный исходный код без руководства инспектируем, но может быть упущен из виду.

Руководство без сгенерированного исходного кода полезно, но всё ещё абстрактно.

Вместе они образуют практичную систему отладки ИИ.

Скилл добавляет:

Учитывая этот проект и эту задачу,

Это ровно тот недостающий машинно-ориентированный слой.

Скиллы могут сжать эти сроки.

Если фреймворк поставляет качественный официальный контекст с первого дня, совместимые агенты могут стать полезными немедленно.

Это снижает один барьер внедрения фреймворка.

Это также повышает важность дисциплинированной документации с самого начала.

Это тонкое, но значимое преимущество для поддерживаемости.

## Kora хорошо позиционирована для этой модели { #kora-well-positioned-model }

```

Скиллу не нужно компенсировать непрозрачный фреймворк.

Он может оркестровать прозрачный.

Вот почему идея сильнее для Kora, чем для фреймворка, где фактическое поведение существует в основном в скрытом состоянии времени выполнения.

## Текущее состояние — уже доказательство направления { #current-state-already-proof }

Текущая посадочная страница Kora v2 явно представляет официальный репозиторий Kora Skills как часть истории обучения и ИИ. Официальный репозиторий скиллов в настоящее время публикует пакет `kora-v1`
для поколения 1.x и намеренно оставляет место для отдельного пакета v2, а не притворяется, что один набор инструкций подходит для каждой крупной версии.

Это разделение важно.

Оно показывает, что машинно-ориентированную экспертизу фреймворка можно рассматривать как версионируемый продукт.

Концептуальная модель уже видна ещё до того, как полный слой скиллов Kora 2 созреет.

руководство по миграции

извлечение официальных примеров
руководство по рабочим процессам тестирования
```

оставаясь при этом прозрачным и переносимым.

Это гораздо ценнее шпаргалки с промптами.

## Финальная архитектура { #final-architecture }

Полный цикл разработки мог бы выглядеть так:

```text
Разработчик просит об изменении
        ↓
Агент, разбирающийся в Kora
        ↓
Официальный скилл выбирает канонический рабочий процесс
        ↓
Документация / руководства / примеры дают факты
        ↓
Агент редактирует текущий проект
        ↓
Компилятор проверяет контракты Kora
        ↓
Сгенерированный исходный код раскрывает точное поведение
        ↓
Тесты проверяют семантику времени выполнения
        ↓
Агент исправляет / объясняет
```

Каждый слой вносит доказательства.

Модель направляется, но ей не доверяют слепо.

Фреймворк прозрачен, но не вываливается целиком в контекст.

Разработчик получает результат, специфичный для проекта.

Это замечательно сильная архитектура для разработки с помощью ИИ.

## Заключение { #conclusion }

Документация была спроектирована в первую очередь для ответов на человеческие вопросы. Исходный код был спроектирован для выражения программы компиляторам и инженерам. Примеры были спроектированы для
демонстрации использования. Диагностика компилятора была спроектирована для отклонения недействительных структур. Сгенерированный исходный код был спроектирован для материализации решений Kora на
этапе компиляции.

ИИ-агенты для написания кода могут использовать все эти артефакты, но без руководства, специфичного для фреймворка, они всё ещё сталкиваются с трудной проблемой: они должны решать, каким источникам
доверять, какие соглашения актуальны, какие паттерны каноничны, какие исторические API устарели и какие внешне похожие идеи принадлежат другому фреймворку.

Kora Skill заполняет этот пробел.

Ему не нужно заменять документацию. Его роль интереснее:

> **Скилл не заменяет документацию. Он учит агента правильно по ней ориентироваться, интерпретировать и применять её.**

Это позволяет фреймворку предоставить машинно-ориентированную операционную модель. Скилл может сказать агенту, что конструкторы, `@Component`, `@Module` и `@KoraApp` определяют граф приложения; что
сгенерированный исходный код — это поверхность для изучения, а не для редактирования; что диагностику компилятора следует использовать как детерминированную обратную связь; что Kora 2 отдаёт
предпочтение синхронным контрактам и виртуальным потокам; что нативная семантика JDBC, Kafka, gRPC и HTTP должна оставаться видимой; и что расширения обычно должны входить через модель модулей, а не
через изобретение второго фреймворка внутри приложения.

Другими словами, он может кодировать не только API, но и экспертизу.

Эта экспертиза важна, потому что языковые модели общего назначения неизбежно несут смешанные априоры. Они отлично знают Spring. Они могут знать более старые версии Kora. Они видели случайный код
GitHub и сторонние примеры. Правдоподобный, но неверный API может выглядеть ровно как валидная Java.

Официальный скилл меняет иерархию источников истины. Он говорит агенту отдавать приоритет текущим официальным знаниям Kora, изучать текущий проект, обращаться к сгенерированному исходному коду и
позволять компилятору проверять результат.

Вот почему:

> **Официальный скилл может частично заменить размер корпуса авторитетным контекстом.**

Меньшему фреймворку больше не нужны миллионы публичных примеров, прежде чем ИИ сможет эффективно с ним работать. Качественная документация, запускаемые примеры, прозрачный исходный код,
сгенерированный код, точная диагностика и официальный скилл могут предоставить актуальную экспертизу непосредственно в момент выполнения.

Версионирование делает это ещё более важным. Текущий официальный репозиторий скиллов уже различает пакет `kora-v1` и оставляет место для отдельного руководства Kora 2. Эта модель указывает на будущее,
где релиз фреймворка не завершён, пока его машинно-ориентированные знания не обновлены вместе с бинарными файлами, документацией, примерами и заметками о миграции.

Скилл также делает философию сгенерированного кода Kora гораздо более мощной. Он может научить агента *как* расследовать реальное приложение:

```text
Найди сгенерированный граф.
Проверь, какой компонент удовлетворяет зависимость.
Изучи сгенерированную AOP-обёртку.
Открой реализацию репозитория.
Прочитай диагностику компилятора.
Проверь целевым тестом.
```

Прозрачность фреймворка становится активным механизмом отладки ИИ, а не пассивной архитектурной добродетелью.

Это меняет конкурентный ландшафт фреймворков. Старые экосистемы по-прежнему обладают огромными преимуществами в производственной истории, интеграциях, людях, книгах и публичных знаниях. Но размер
исторического корпуса становится менее решающим, когда актуальные авторитетные знания фреймворка можно внедрить непосредственно в агента.

Возраст фреймворка менее важен, когда фреймворк может научить модель тому, что истинно *сейчас*.

Это приводит к более широкому выводу:

> **Следующее поколение фреймворков может поставлять не только библиотеки и документацию. Оно может поставлять экспертизу, необходимую для их правильного использования. Kora Skill — шаг именно к такой
модели.**

И идею можно сформулировать ещё проще:

> **В прошлом разработчикам приходилось учить фреймворк. Теперь фреймворк может также учить агента, который помогает разработчику.**

Для Kora это необычайно естественное продолжение существующей философии фреймворка. Код явный. Граф инспектируем. Обратная связь компилятора сильна. Сгенерированный исходный код раскрывает реальную
реализацию. Абстракции узкие и канонические. Kora Skill добавляет недостающий слой, который говорит ИИ-агенту, как намеренно использовать все эти свойства.

Документация объясняет фреймворк.

Скилл учит агента, как им управлять.
